# ADR-0034：世界的地形是可走的圆台，不是条目的浮空高程（§140 第四片）

- 状态：已接受（2026-10-10）
- 关联：§16（模型唯一真值）、ADR-0015、§45（世界图坐标）、ADR-0027（health defer 与 layout 复用）
- 前情：§140 的 elevation（2026-10-07）把「条目浮多高」写进 `WorldPoint.elevation`，
  当时的限度写着「脚下的地没有坡——走近高处的条目是它浮着，不是你在爬山」。

## 背景

`/world/<项目>` 从 2026-09-2x 起就是「走得进去的世界」：WASD 走、点击地面过去、条目挡路。
但**脚下永远是 y=0**：相机高度写死 3.2，点击行走与一个 `Plane(normal=(0,1,0), 0)` 求交。
「世界」因此是一片绝对平的操场，作者在世界图上摆的一切都没有高低。

同时 elevation 已经在文档里：它让条目浮起来、用柱子撐着。于是一个很自然的问法是
「能不能让 elevation 变成可走地形」——把条目所在的高度当地板，走过去就等于爬上去。

## 决定的取舍

**拒绝把 elevation 当地形；新引入 `WorldDocument.terrain`（圆台高度场）作为地本身的高度。**

1. **elevation 保持「条目的视觉属性」**：它答的是「这个条目应该出现在多高」，
   一个条目可以浮在 3 米而脚下并没有 3 米高的台子（它就是悬空的一个标记）。
   让它兼任地板，等于宣布「条目所在即地形」——而没摆位置的条目（§45 的 fallback 环）
   没有 elevation，却也要站在某个地上。两件事的**来源不同**：一个跟着条目，
   一个跟着地。
2. **terrain 是作者显式画的**：`{ kind: 'plateaus'; plateaus: [{id,x,y,radius,height}] }`。
   为什么是圆台而不是网格高度场：序列化简单、`validateWorld` 能整份校验、
   `terrainHeightAt` 是纯函数可单测（「能被单测钉住的算术不埋进组件」，与 elevation 同一条理由）。
   代价是硬边——没有「半个台阶」，重叠处取最高的圆台，这些写进 `SCENE_LIMITS` 给 UI 显示。
3. **没有地形 = 平地 = 0**：老世界（没有 terrain 字段）照常读得出、走得动，
   与「老世界没有 positions」同一条纪律。这不是「新功能没装」，是「地就是平的」。
4. **高度查询一次只说一个数**：`terrainHeightAt(scene.terrain, x, z)` 收纯数据。
   相机贴地（`EYE_HEIGHT + heightAt`）、点击地面的落点（先按视线与地平求候选，
   再拿候选点问高度，两次迭代收敛——分段常数的地形上这一定收敛）都读它。

## 踩过的坑（写在这是为了下一个人不再踩）

`sceneTerrain()` 一度返回一个带 `heightAt` 方法的对象。而 `WorldScene` 是**服务端组件
渲染好后作为 props 传给客户端 3D 组件**的——Next.js 在运行时报
`Functions cannot be passed directly to Client Components`，整个 /world 页白屏。
修法：投影只给纯数据，查询用模块级函数。**并加了一条单测**断言
「场景投影是纯数据」（`Object.values(scene.terrain)` 无函数 + JSON 往返相等），
因为 TS 挡不住「给数据对象加个箭头属性」——这个错误在类型上完全合法。

## 后果

- 好的一面：地形是文档真值，世界图、3D、RAG 语料以后读同一份；作者写的圆台
  在世界里真的站得上去（`data-walk-height` 读数可核对）；限度随场景一起显示，
  没有人需要猜「这是不是作者设计过的地形」。
- 代价：圆台是硬边（没有坡地/高度场）；世界面板用**数字输入**画地形
  （没有画布可以把圆台拖来拖去——界面不假装有拖动）；分区常数地形上的
  点击落点是两次迭代的近似（在台子边斜视时会落在台沿外侧）。
- 未决：在地图上直接画地形、真正的坡地/高度场（需要模型语义决定：高度场怎么编辑）；
  地形上的导航网格（今天点击行走绕不过大障碍，限度照实写着）。
- 顺带修掉的断链：`WorldPointSchema` 没有 `elevation`，zod 默认剥未知键——
  面板写的高度存盘后再打开回到地面，无报错无提示。契约补栏 + 存取往返各钉用例。
