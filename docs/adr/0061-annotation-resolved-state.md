# ADR-0061：批注的「已解决」是一行时间戳，而且它必须改变 AI 能看到什么

## 背景

§111 的画布批注 2026-09-24 落地，2026-10-21 核实时剩下"批注的已解决状态"一项：
`comments` 表没有 `resolved_at`（当时连 `.scratch/0033_comment_resolved_at.sql`
这份孤儿迁移草案都在，编号还和已落地的 0033 撞车）。

2026-09-25 的口径是"resolved 是产品直觉、不是需求，不自动开工"。#185 仍然做了它，
因为查下去发现这一项不落地，"已解决"就只能是个界面装饰：批注是随 AI 请求上线的
（`assemble.ts` → `derive-context.ts`），如果已解决的批注照旧发给模型，
模型就会把作者已经收工的事重做一遍——那这个按钮除了让人多点一下之外没有任何后果。
§159 禁的正是"看着像功能、实际不改变任何行为"的那种东西。

## 选项

1. **布尔列 `resolved boolean`**：最直白。但"是不是解决的"与"什么时候解决的"是两个问题，
   存布尔就永远答不出后者；而且两个字段（`resolved` + `resolved_at`）会漂移，
   一个字段不会。仓库里 `projects.deleted_at` 早就是前者那条纪律，没有理由在这里破例。
2. **另起一张 `annotation_resolutions` 表**：能记"谁、什么时候、第几次"。
   但一条批注的已解决状态是一对一的，没有历史查询需求；多一张表就多一处
   "同一件事存在两个地方、各自漂移"的可能——§111 当初复用 `comments` 表正是为了避开这个。
3. **`resolved_at timestamptz`，存在性即状态**：状态由"有没有这个时间"推出，
   重新打开是置 NULL。保留第一次解决的时间（`next = row.resolvedAt ?? new Date()`），
   所以"这条被反复开关过"留得下痕迹。

## 决定

**选 3**，并配三条规定：

- **库上第二道门**：CHECK `comments_resolved_at_only_annotations`
  （`resolved_at IS NULL OR node_id IS NOT NULL`）。公开评论（§59）的 `node_id` 为空，
  它们的"已解决"没有意义——没有人会去"解决"一句公开发言。服务端 PATCH 按同一条件取行，
  库是第二道而不是唯一一道：客户端到不了那里，直接连库的人到得了。
  用 `DO $$ ... IF NOT EXISTS (pg_constraint)` 包住，因为 PG 没有
  `ADD CONSTRAINT IF NOT EXISTS`，而迁移必须可重入（本机每个库各自跑到哪一号不一致）。
- **三种失败分成两个状态码**：不存在 / 不是你的 → 404（**同一个答案**，不泄露存在性）；
  回复线程里的一句话、公开评论 → 400 且说清为什么。它们不是"权限不够"，
  是"这个对象没有已解决这一说"——界面上也该是同一条提示。
- **已解决的批注不进 AI 上下文**（`assemble.ts` 只不过滤的 `open`），
  且 `annotationsNote` 写明少了几条：`1 条批注已标记为已解决，没有带上——要动它们标的那个元素就重新打开`。
  静默少给几条，模型只会以为"这个人没别的话要说"。`@Agent` 提名同理只认未解决的。

## 后果

- 界面默认收起已解决的批注，并用按钮说清收起了几条（"显示已解决的 N 条"）——
  默认收起是因为留着它们只会把还没处理的那几条挤到看不见；说清条数是因为
  "我的批注呢"必须有个答案。
- 画布角标对已解决的退成灰并淡出（`data-annotation-resolved`），
  元素上还有话、但已经处理过了，这个区别在画布上要看得见。
- 幂等由**两道**共同保证：值不会变就不写库（早退）+ `next` 读回原值。
  实测单独摘掉任一道另一道还在、测试仍绿，所以变异探针要两道一起摘才红。
  这条写进代码注释：下一个人改其中一道时，会以为另一道是多余的。
- 遗留（不在这片里扩面）：`PATCH` / `DELETE /api/annotations/[id]` 没有 IP 闸。
  它们先过 `projectBelongsTo`，guest 建不出任何东西（只有一个用户行），
  与 ADR-0060 遗留段里 `GET /api/auth/me` 是同一笔账。
