# ADR-0049：§147 的增量重解在编辑器里从来没跑过——查出来的三处与修法

- 状态：**草稿（红线数字待填）**
- 日期：2026-10-21
- 关联：§147、§16、§146、§150、§159、ADR-0048（首屏那一刀）、`docs/PERFORMANCE.md`「2026-10-21」那几节

## 背景

§147 的增量重解从 2026-10-10 接线（中途因"与全量不等"撤回过一次，2026-10-20 把两份实现合并成
`runLayout` 让"相等"由构造保证），到 2026-10-21 加跨帧的测量缓存——三天的活，
**在编辑器里一次都没跑过**。

怎么查出来的：**探针法**。增量路会**沿用上一帧那个对象**
（`resolved[id] = entry` → 同一个对象），全量路会重算出一份**新的**。
所以改一个节点之后，**没被改**的那个节点的 entry 是不是**同一个对象**，
就是"走没走增量"的铁证——比任何计数器都硬（计数器只说"解了几次"，不说"省没省"）。
探针结果：**false**。也就是说，§147 的全部收益数字都是在一条**没接上电的线路**上量出来的。

## 根因（三处，互相独立，缺一个都还是全量）

1. **"是不是同一份文档"用错了判据。**
   补丁走**写时拷贝**：`applyPatch` 每次都返回**新的文档对象**
   → 用对象身份判断"上一帧那份解是不是这份文档的"**永远为假**
   → `prev` 恒为 null → 增量路不可达。
   （`docs/PERFORMANCE.md` 里那句"doc 身份一并判"当年是对的：那时还没有写时拷贝。）
2. **改动集合登记在布局求解之后。**
   `design.execute` 会**同步**触发 commit → 布局就在那一刻求解 →
   求解时改动集合还是空的 → 又是一次全量。AI 事务更糟：**完全没登记**；
   undo/redo 登记得太晚（同样晚于求解）；`jumpTo` 走批量逆补丁，也没登记。
3. **有些 op 的改动集合"算不全"。**
   `removeComponent` / `removeAsset` 会**扫遍所有页面**去解引用
   （定义没了，引用它的实例一起解开；资产下架了，引用它的填充一起剥掉），
   而那些被解开的节点**不在 op 里**；`jumpTo` 一次跨多条历史，逆补丁也不逐条登记。

## 修法

1. **文档代数**（`DesignStore.generation`）：**整份换掉**时 +1，**打补丁**时不变。
   "同一代数 + 同一页"就等价于"同一份文档的上一帧"。
   （`abortTransaction` 整份换回快照，也要 +1。）
2. **先登记，后变更**：`execute` / `undo` / `redo` / AI 事务都在变更**之前**登记改动集合。
3. **算不全就不假装算全**：`removeComponent` / `removeAsset` / `jumpTo` → 那一轮**强制全量**
   （`layoutForceFull`）；`restoreAsset` / `restoreComponent` 的节点清单则登记进改动集合。
4. **结构变了不能沿用**（design-model 侧）：`canReuse` 补一条**孩子表比对**——
   沿用会把上一帧那个**节点对象**整个带过来（孩子表是旧的）→ 增量解与全量解**不相等**。

## 顺带修掉的两个"内容变了却沿用旧对象"的缺口

- **token**：测量缓存的键只看「节点 id + 约束」，而字号/间距/字体名都来自 token 解析 →
  同一事务里既改 token 又改别的节点 → 受影响的节点拿回旧尺寸（**画布高度是错的**）。
  修法：token 表的指纹进测量签名（库的注释早就写着"签名包括 tokens"，实现里一直没有）。
- **陈旧内容**：`removeAsset` 解引用、`restoreAsset` 放回引用 → 那些节点不在改动集合里 →
  画布画出旧内容。

## 后果

- **正面**：§147 的收益第一次**真的**在编辑器里发生（数字见 `docs/PERFORMANCE.md`）。
- **负面（必须说清）**：增量路从"没接上电"变成"一直在跑"，
  于是**它自己的正确性问题第一次会被用户看见**——所以这一格补了 5 条用例
  （对象身份、换文档、结构变更、陈旧内容 ×2），并把 e2e 全量重跑了一遍。
- **边界**：增量对**首屏**依然零帮助（首屏没有"上一帧"可复用）——那一格要别的解法（ADR-0048）。
- **仍然欠的**：扁平一万节点文档里，增量的位置复用率仍然是 0
  （改任一个节点 → 其余 9999 个兄弟全部移位）→ 收益主要来自**测量缓存**（尺寸没变就别重量）。

## 接上电之后：增量路自己藏着两个坑（7 倍的反向效果）

修完上面三处、把增量路真正接上电之后，**浏览器里量出 7 倍的反向效果**：
属性写入总延迟 **848ms（增量开） vs 142ms（增量关）**，慢的那截全在 `layoutMs` 本身。

原因不在"省下的计算"，在增量路**自己多出来的那部分**：

1. **平方级的形状检查**：`place` 里写成了
   `children.every((c) => prevEntry.children.includes(c.id))`
   → 一万个孩子 → 5000 万次比较 → 那 800ms 就是它。
2. **比的不是同一件事**：`prevEntry.children` 是**按 parentId 建的** resolved 孩子表
   （文档里的孩子常常没有 parentId → 那个数组常常是空的），
   而 `children` 是**文档结构** → 拿它们比，判据从根上就错。
3. **污染上一帧**：往"沿用来的"父节点里 push 孩子 → 上一帧那份解被这一帧改了
   → 下一帧拿它当基准就是错的。

**修法**：形状检查改成**逐项比文档里的孩子表**（O(n)，比的是同一件事）；
沿用来的父节点不再接收 push；测量缓存的"约束变体"加上界（8 条）。

**修完（同一份真文档、模型层）**：全量 **27-41ms**（测量 9999 次）vs 增量 **16-29ms**（测量 7 次）。

**这一段要记住的**：**"接上电"不等于"能用"**——一条三年没人跑过的路径里，
可能藏着平方级的写法；它平时不显形，是因为**没人让它跑过**。
所以修好接线之后必须**立刻重新量**，而且要量开/关两轮（只量"开"会得到一个更慢的结果却以为是自己赚的）。

## 红线（数）

同一个构建、开/关交替各量两轮（10000 档、生产构建、带分段计数）：

| 10000 档「属性写入 → 画布更新」 | 增量**开** | 增量**关** |
|---|---|---|
| 第 1 轮 | **41.4ms**（45.5 / 37.3）· 求解 17-22ms | 78.7ms（103.8 / 53.6）· 求解 44-82ms |
| 第 2 轮 | **49.4ms**（59.8 / 38.9）· 求解 18-35ms | 127.6ms（106.8 / 148.4）· 求解 84-124ms |

**增量路快 2~3 倍**，两轮方向一致（开→关→关→开交替量，顺序效应已排除）。
模型层同一份真文档：全量 27-41ms（测量 9999 次）vs 增量 **16-29ms（测量 7 次）**。

**怎么量 A/B（同一个构建）**

`NEXT_PUBLIC_NEXUS_INCREMENTAL_LAYOUT` 是**构建期内联**的 → 换一次值就得重新 build 一份
→ 又变成"量两次不同的构建"（今天的教训：那种比较会被机器当时的负载带偏）。
所以给 store 加了一个**运行期覆盖**（`globalThis.__NEXUS_INCREMENTAL_LAYOUT__`），
`scripts/perf-browser.mts` 用 `PERF_INCREMENTAL=0/1` 注入 → **同一份构建**量两次。
