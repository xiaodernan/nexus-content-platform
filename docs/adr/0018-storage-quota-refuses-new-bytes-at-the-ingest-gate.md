# 0018 — storage 配额在唯一的摄取门里拒绝新字节，不驱逐已有素材

日期：2026-09-28 ｜ 关联：§133 订阅档位、§134 Credit System、§80 文件上传安全、§16 设计模型为唯一真值、§159 不做假 API / 假 payment、ADR-0014、ADR-0017

## 背景

ADR-0014 把 §133 的五件事里**只有 AI usage 一格**做成了会真拒绝的拦截，另外四格（storage / generation /
team collaboration / publishing）当时的处置是"照实在界面上标成还没有拦截方"。这不是偷懒，是当时唯一诚实的
做法：把表格上的数字说成生效的限制，就是 §134"消费透明"的反面。

storage 那一格今天可以真做了，因为它的两个前提都已经在库里：

- 字节确实由平台管着（§80 的摄取门 + 对象存储），`assets.bytes` 是每次写入时量出来的真数；
- 档位上限已经在 `PLAN_LIMITS` 里，界面也在按它显示。

## 决定

1. **用量是派生的**：`storageUsageBytes(ownerId) = SUM(assets.bytes)`，按**所有者**跨项目合计。
   库里没有"已用存储"这一列可以改——与余额（ADR-0014）、快照、搜索索引同一条纪律：
   两份真值迟早会有一份是错的，而错的那一份没人解释得清。
2. **门放在 `uploadImageAsset` 里，不放在路由上**。它是全链路**唯一读字节**的地方（§80），
   用户上传与 §38 生成走的是同一道门。挂在路由上会漏掉生成那条路——而"生成也会占空间"恰恰是
   这条配额最容易被绕过的一侧。
3. **只拒新写入，不做驱逐**。放不下时拒绝这一次写入，已经在库里的素材一张都不删。
   自动删用户的图是最坏的一种"限额"（它把一个容量问题变成了数据丢失），腾地方必须是作者自己的动作。
4. **复用不受影响**：checksum 命中的重复上传在门**之前**就返回了——那份字节已经在库里，
   再算一次占用等于对同一份字节收两次费。
5. **拒绝的话里必须带数字**：档位、上限、已用、这一次还要。与 `refusalFor` 同一条口径——
   "存储满了"与"Free 档上限 200MB，已用 198MB，这一次还要 4MB"是两种可读性，后者才能让人决定删什么。
6. **拒绝要能被分开识别**：`UploadRejection.code` 区分 `invalid_image` 与 `storage_exhausted`，
   路由给 400 与 413。混成一个状态码，用户会去改文件名，而真正该做的是删素材。

## 两处口径，因为它们直接影响数字

- **软删的项目仍然算**：`softDeleteProject` 只标记 `deleted_at`，字节还躺在存储里，
  所以删项目腾不出空间。真腾空间要有一条资产清理（今天没有），在那之前把软删项目排除掉
  就是"账面上有空间、实际写不进去"。
- **没有项目归属的资产不算**：今天没有这种写入方（头图走 `avatar` 那条独立的表）。
  将来若出现，`storageUsageBytes` 的 join 要跟着改——这是那条 inner join 存在的理由。

## 后果

- 上传超配额返回 `413 storage_exhausted`；生成那条路返回同一个 code，路由同样给 413。
- `/credits` 页上 storage 从"还没有拦截方"那一列挪到"会真拦"那一列（`ENFORCED_PLAN_AXES`），
  并多一行"已用 X / 上限 Y MB"。两列加起来仍然等于 §133 那五件事，有单测钉着。
- **没有购买、没有加空间入口**：放不下时给的是"删掉一些素材"，不是"升级档位"——支付没接（§159），
  档位今天只能由服务端代码改。
- **这道门不预扣**（与 ADR-0014 那一条同源的松）：两个并发上传各自读到"还放得下"就都能通过，
  合计可能略微越过上限。负余量在下一页上看得见，而修它需要按所有者的锁或预留表；
  在那之前把这个松写在文档里，而不是假装它不存在。
- 剩下两格（team collaboration / publishing）仍然只有数字，仍然在 `UNENFORCED_PLAN_AXES` 里。
