# 0024 — 导出这份 zip：自己写 store、回执走 HTTP 头、导入留到下一片

日期：2026-10-01 ｜ 关联：§144 NO LOCK-IN、§16（模型是唯一真值）、§163 `build.status`、§164 Build complete、§159、ADR-0019（公开 API 的鉴权口径）

## 背景

原文 §144 给了四件事：`export design` / `export code` / `export assets` / `delete account`。
前三件缺的**不是能力**：设计文档读得出来（`loadDocument`），代码生成早就能用
（`generateProject()` 产出 `GeneratedFile[]`），资产的原始字节也取得回来（`openAssetForOwner`）。
缺的是"把它交到用户手里"那一步——在那之前，"作品属于用户"（§145）只写在页面上。

这一步同时卡着另外两句话：§164 的第四类通知（Build complete）以前挂在"没有来源"那张单子上，
理由正是"平台没有会完成的构建操作"；§163 的 `build.status` 也只有发布链路一个生产者。
所以这一格的产物不是"一个下载按钮"，而是**第一个真会走完的构建动作**。

要定的三件事：用什么打 zip、包里的数字怎么到达界面、这一片做到哪为止。

## 选项

1. **装一个 zip 库**（`jszip` / `archiver`）。省事，但为一个"把若干文件并排放进容器"的需求
   多引一个依赖就要多一份供应链要审；而本仓已有手写小协议的先例（S3 客户端、PNG 合成）。
   另外 `jszip` 默认按当前时间打时间戳，"同一份内容两次导出字节一致"这条断言反而要绕它。
2. **走公开 API v1 的 JSON 出口**（ADR-0019 那条）。它给的是模型，不给代码与资产，
   而 §144 要的是"把作品整体带走"。而且那是 token 鉴权的机器接口，不是浏览器里点下来的下载。
3. **自己写一个只支持 store（不压缩）的 ZIP 写入器**（选这个）。
   格式只需要 PKZIP 的最小子集：本地头 + 数据 + 中央目录 + EOCD；不做 zip64、不做目录项。

## 决定

- **只 store，不 deflate**。包里主要是代码与 JSON，体积不是瓶颈；deflate 要额外处理
  "压缩后反而更大"与比特序，收益不抵复杂度。真要压，改 `method` 那一格即可，格式其余部分不动。
- **时间戳固定成 1980-01-01 00:00**。同一份内容每次导出的字节必须一模一样——
  否则没法断言"这份 zip 里有什么"，而"导出的是不是当时那份设计"正是这件事要证的。
  （README 里那句生成时间是**故意**可变的：它是"什么时候导的"，不是内容。）
- **zip slip 在写入侧就判**（`safePath`：绝对路径、`\`、盘符、`..`、空段一律抛）。
  资产名与代码路径都带着用户输入，等解压方去发现就晚了。
- **三样是一次请求的三种勾选，不是三个端点**：`GET /api/projects/<id>/export?parts=design,code,assets`。
  原文那句"NO LOCK-IN"说的是作品整体，把三件拆成三个入口只会让人少导一样。
- **归属在动字节之前判，不属于你统一 404 而不是 403**（与资产取字节同一口径：403 会泄露"这个 id 存在"）。
- **回执走 `x-nexus-export-receipt` 头，不让界面自己数**。客户端要数包里有几个文件就得重新解一遍 zip，
  而"导出完成"这句话不能等到那时才敢说；拿不到回执就**只报字节数，不补一个看起来对的构成**（§159）。
  这与任务 id 走 `x-nexus-task` 头是同一个先例：服务端数过的数字由服务端带出来。
- **库里有一行、存储里的字节取不回来 → 不算导出失败，但要点名**。缺的每一项进 README 的"缺了什么"一段，
  通知按 `warning` 而不是 `success`。作者拿着 zip 走人之后才发现缺图，那时候平台已经没机会告诉他了。
- **包里不放 `.nexus/` 那层机器可读结构**，因为还没有能读它的一方。
  *（这一条没撑过第二天：2026-10-02 补上了 `.nexus/manifest.json`，2026-10-03 导入侧真的来读了——见文末补记。）*
  `docs/TESTING.md` 第 12 条（导出 ZIP 含 `.nexus/`、能在干净实例导入还原）**仍然算欠**，
  这一片只结 §144 前三件；`docs/RUNTIME.md` 那句"所有导出必须能被另一个实例重新导入"
  在导入落地之前是一句还没兑现的要求，不是一句现状描述。
- **导出是投影，不是快照**。不含历史快照、分支、撤销栈、知识索引与语料、对话、审核记录——
  这三行限度同时写进 README 与 Studio 面板，不只在代码注释里。

## 后果

- §164 那张"没有来源"的单子第一次空下来。**空单子也要留着那张单子**：
  它留着，下一个人加第五类通知时才有个地方记"这一类还没有来源"；删掉它，
  "没有来源"这件事就又变成只有代码知道的事。页面标题因此是分叉的（0 条时说"都有来源了"），
  而不是"这 0 类还没有真实来源"那种读起来像故障的措辞。
- §163 的 `build.status` 有了第二个生产者，Studio 顶栏那行实时读数从此不必等发布才有值。
- 体积：store 不压缩，4000 节点档那份包的实际字节数记在 `docs/ROADMAP.md` 当日段，
  与 `content-length` 同一个来源。真嫌大再加 deflate，格式不用动。
- 下一片的形状已经定了：读侧要防 zip bomb 与超大条目，`.nexus/` 里要有格式版本，
  导入要在**干净实例**上还原（不是在同一库里复制一份），配额按导入后的字节判。
- `delete account` 仍是这四格里唯一没动的，也是 ROADMAP 明写"判决书在写之前不要动手"的那一格。

## 补记（2026-10-03）：导入落地了，格式因此从 v1 走到 v2

上面那句"在导入落地之前是一句还没兑现的要求"今天开始还。落的是
`apps/web/src/server/domain/import.ts`（写库前的判据全在 `inspectPackage()`，不碰库）+
`POST /api/projects/import`，证据与三条判决的推理记在 `docs/ROADMAP.md` 末节
「§105/§144 第二片」，这里只补这份 ADR 必须改口的两处：

1. **`.nexus/` 那一层从"没人读所以不放"变成"有读端，所以它得带版本号"**，并且版本号是**判据**而不是装饰：
   导入侧先认 `formatVersion`，按**相等**判，认不过整包拒收。为什么不"往后兼容地试着读"：
   一份形状变了的包会在某个字段上解析成功，然后导出一份**不完整的项目**，而没人知道少了什么——
   那种"导入成功但图不见了"比一句"这是 v1，请重新导出"难查得多。
2. **v1 的包今天导不回来，是那一版缺信息，不是读端写坏了**：`assetRefs`
   （包里那个路径 = 模型里哪一个资产 id）是"字节换号"的唯一凭据，v1 没有这一层。
   导回来的项目必须指向**自己**那份字节（页面/组件/资产 id 在库里都是全局主键，共享一行会让
   "删项目"级联删掉别人的素材，§27/§80），所以这一层不是可选元数据。

那份"下一片的形状"清单，今天的实际状态：

- 读侧防 zip bomb 与超大条目 —— **已在**（`apps/web/lib/zip-read.ts`，三档上限 + 压缩比 + 逐条目 CRC，
  判据在导入之前跑完）。
- `.nexus/` 里要有格式版本 —— **已在**（v2）。
- 配额按导入后的字节判 —— **已在，且没有新代码**：资产逐张走 `uploadImageAsset` 那道摄取门，
  问的是**导入者**的用量；放不下不会回滚整包，而是项目还在、少的那一张进 `assetFailures` 点名。
- 导入要在**干净实例**上还原 —— **还没跑过**。今天证的是"同一实例导回成一个新项目"：
  代码里没有源实例耦合（id 全换号、字节重新摄取、kind 从清单读），但没有第二个库来跑这一遍。
  在它跑通之前，`docs/TESTING.md` 第 12 条的后半句继续算欠，`docs/RUNTIME.md`
  那句"另一个实例"也继续是要求而不是现状。
  *（这一条在 2026-10-04 跑通了，见文末第二则补记。）*

还有一寸是界面：**Studio 上还没有"导入"这个按钮**，`POST /api/projects/import` 的
401 / 403 / 413 / 415 / 201 到今天没有任何一条被真请求证过（这一片的测试全打在 domain 层）。
路由里"没登录回 401"是显式判空 `currentUserOrNull()` 才可达的那一条——
`requireUser()` 在没有 cookie 时**抛错**，未登录的请求拿到的是 500，注释与 ADR 许诺的 401 永远走不到。
导出路由同一天换成同一个写法。
*（界面入口与这五条状态码在 2026-10-03 落地，见 `docs/ROADMAP.md`「§144 导入的界面入口 + 真 HTTP 状态码」。）*

## 第二则补记（2026-10-04）："另一个实例"终于有了第二个库

上面那句"还没跑过"跑通了。载体是 `scripts/two-instance-roundtrip.mts`（`npm run two:instance`），
它把"另一个实例"拆成三件互相不能替代的事：**另一个库**（跑前 `drop` + `create` 出 `nexus_two_instance_b`
再迁移 22 条）、**另一个存储目录**（B 那个在跑之前整个删掉）、**另一个进程**（三个孩子各自只拿到自己那一侧的
env，连接池互相看不见）。两侧之间唯一的通道是磁盘上那一份 zip 字节——与作者手里拿的是同一个东西。

判据由父进程比对，跑出来是 7 条全绿：新项目 id 与源不同、归属是 B 侧那个新用户、
文档摘要逐字相同（757 字对 757 字）、资产字节 sha 相同（`9f05a9262dad…`）、
B 侧资产数为 1、A 侧导出后没被动过、B 的存储目录里确实躺着一张自己那份 PNG
（`projects/<B 项目 id>/<新资产 id>.png`，与 A 侧 3 张路径无一重合）。
zip 28141 字节，解压后 27283 字节，3 个代码文件按 §16 不进库。

摘要里**故意把 uuid 归一掉**：换号是这一片的正确行为（id 不是内容，§16），
把它算进判据就等于要求"复制出一模一样的主键"，那在同一个实例里是撞主键。
所以"图还在"看的是填充的**形状**与字节的哈希，而不是填充里那个 id。

两条臂证明这些判据不是空转：

- `NEXUS_TWO_INSTANCE_SKIP_ASSETS=1`（导出的包里没有 assets 那一份）⇒ B 侧**非零退出**，
  并说出服务器自己那一句"包里没有这个资产的字节，导入后这张图的引用会断"。
- 第一版的 `B_STORAGE_IS_OWN_COPY` 打的是 `b.note !== undefined`——那是**空判据**（孩子进程总会写 note，
  哪怕 B 侧一份字节都没落盘）。它被换成父进程自己数目录、自己哈希文件，才第一次真的能红。

仍然欠的只剩两件，都不是这一片能顺手补的：**413**（要一份真 >128MB 的包，本机只剩约 2.5GB 空闲内存，
domain 层那条"整包字节超上限 → 整包不落库"已经证过）与 `delete account`（§144 第四格，唯一动别人数据的那一格，
ADR-0025 已判，尚未实现）。

## 第三则补记（2026-10-29）：那一节的读数已经过期，以及"绿过一次"不是见证

上面第二则补记的 7 条判据、22 条迁移、`NEXUS_TWO_INSTANCE_SKIP_ASSETS=1` 那一档臂，**今天全都不成立**。
不是当时写错，是**它过期时没有人知道**：这三个月里 `import.ts` 长出了分镜换号与角色换号两段代码，
那条脚本一次也没再跑。这条 ADR 里"另一个实例"的载体因此重做了一遍（逐条读数见 `docs/EVALUATION.md` 第二十一片）：

- **判据 7 → 20 条**，走满 design / assets / 分镜 / 角色四层；引用完整性与文案等价分开判。
  `B_EMPTY_BEFORE_IMPORT` 从"父进程说它是空的"改成 B 侧孩子在导入前逐表 `count(*)` 的实测。
- **五趟臂每趟都跑**（`NEXUS_TWO_INSTANCE_SKIP_ASSETS` 这个开关从此不存在）：
  由同一份好包剪出五份改过的包，各自导进一份全新的 B，实测分别红 16 / 10 / 5 / 5 / 7 条。
  判据的归类规则也立起来了：每趟只点名该红的那几条，其余按定义必须照旧绿，名册对不上就失败——
  这一条当场纠正了我自己（`no-design` 点名 10 条、实测红 16 条，而"该红的 10 条全红"那句当时是真的）。
- **三趟探针**补上臂红不到的那三条判据，其中一趟把本 ADR 依赖的产品代码里一条真缺陷带了出来：
  `domain/projects.ts` 的 `isSlugConflict` 沿 `cause` 链走（#151 的教训），循环条件只挡 `null` 不挡 `undefined`，
  而链一般两层就到底 ⇒ **任何非 slug 的库错误**（外键、检查约束、别的唯一索引）在到达调用方之前
  就被换成一句 `Cannot read properties of undefined (reading 'cause')`。
  把 A 侧用户 id 递给 B 侧导入那一趟实测到的正是这句话，而不是 `projects_owner_id_users_id_fk`。
  修好之后同一趟读到 `[23503] … violates foreign key constraint "projects_owner_id_users_id_fk"`，
  见证落在 `apps/web/test/projects.integration.test.ts`（真库，旧代码上实测红）。
  **这一条与本 ADR 有关**：路由那 403/401/400/415/201 已经在真 HTTP 上各证过一次（见上面第一则补记的日期段），
  数字本身是对的；但归属这类违例落进 `createProject` 之后，服务端拿得出的"原因"会是这句 TypeError，
  而不是库里那句外键——**报出来的状态码对、附在日志与错误响应里的原因不对**，这正是排查最费时间的形状。

依旧欠的：**413** 那一格 2026-10-07 由 `npm run probe:413` 结掉（见 ROADMAP 当日段），
`delete account` 仍在 ADR-0025 名下没实现。新增一条欠账，写清楚：**这条演练脚本不在 `npm test` 里，也没有 CI 跑它**
（要第二个库、每趟 `drop` + `create` + 迁移 45 条、一跑约 3 分钟）。门砌好了，踢它仍要人——
下一次动 `import.ts` / `export.ts` 的人应当先跑这一条，而不是先信这一节的绿。
