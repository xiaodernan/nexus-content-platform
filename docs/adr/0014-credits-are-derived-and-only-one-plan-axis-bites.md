# 0014 — 额度是派生出来的账，不是可改的一列；档位五格里今天只有一格有执行方

日期：2026-09-26 ｜ 关联：§133 订阅档位、§134 Credit System、§159 不做假 API / 假 payment、§160 DEMO MODE、ADR-0012

## 背景

§133 要五档（Free / Pro / Creator / Studio / Enterprise），§134 要"用户看得到四类额度（AI / Image / Video /
Compute），并且**所有消费透明**"。动手前这两条一格都没实现：库里没有任何额度的概念，界面上没有任何地方
说"这次生成花了多少"。

要做的时候有三个决定会决定后面所有代码的形状：

1. **余额存哪儿**。存成 `users.credit_balance` 一列最省事，但它和流水是两份真值：
   发放、扣减、退款、失败回滚，任何一处忘了同步，余额页上就是一个谁也解释不了的数，
   而且没有一条日志能回答"这个数是怎么来的"。
2. **要不要做充值**。§133 写的是订阅档位，§134 写的是"看得见 + 透明"，两句都没要求接支付。
   但一个"加点额度"的按钮比一条拒绝生成的提示好卖——所以它必须被明确排除，
   否则下一次有人来接支付时，界面上已经有一个正在兑不了现的入口。
3. **五档上限怎么落**。§133 说档位按 AI usage / storage / generation / team collaboration / publishing
   五件事设计。今天全实现要造队列配额、存储配额、并发发布闸门四套新逻辑；
   只把数字印在界面上，则是"表格上的限制"冒充"生效的限制"。

## 决定

- **余额只有派生这一份**：`balance = SUM(delta) WHERE user_id AND kind`。库里 `credit_ledger`
  没有任何"当前余额"可写，触发器 `credit_ledger_append_only` 把**直接**打在这张表上的
  UPDATE / DELETE 全部挡掉（更正 = 新写一行 `source='adjust'`）。与快照、搜索索引那几处
  "能派生就不存储"是同一条纪律。
- **一次任务只扣一行**由库保证：部分唯一索引 `(task_id, kind) WHERE task_id IS NOT NULL`。
  不靠调用方自觉，因为写终态的地方有两个（`finishTask` 与审批通过时的 `decideApproval`）。
- **发放的幂等键是月份**：`(user_id, kind, period) WHERE source='plan_grant'`。
  发放发生在"打开余额页 / 跑一次生成之前"，**不是**每月 1 日的定时任务——本机没有常驻 cron，
  写成定时发放就是承诺一个不存在的东西。第一次看账发一轮，第二次一行都不多发。
- **不做充值、不做余额可点**。`adjustCredits` 存在但没有任何 HTTP 路由通向它（它的用途是让测试
  能造出"余额为 0"这个状态，从而真的走到那道拦截）。
- **只实现一格拦截**：`refusalForRun` 接在 `/api/ai/run` 与 `/api/ai/jobs` 的提交之前（任务行落库之前），
  额度为 0 就 `429 credits_exhausted`。另四格的上限数字照实在页面上标成"还没有拦截方"
  （`ENFORCED_PLAN_AXES` / `UNENFORCED_PLAN_AXES`，并且有一条单测钉住"两加起来等于 §133 那五件事"）。
- **只有成功的生成扣点**：失败与"等人裁决"都不扣。审批通过是要扣的——那份补丁此刻真的落了画布。
- **计量单位是"一次任务"，不是 token**。本机没有真 provider key，所有生成走模板（§160），
  拿不到真 token 数；编一个"本次消耗 1,234 token"就是 §159 禁止的那种假。

## 外键动作与只追加触发器会打架，这条不是想出来的

第一版触发器无条件挡掉所有 UPDATE / DELETE，跑集成测试时立刻红了两处：

- `delete from agent_tasks ...` 要按 `ON DELETE SET NULL` 把账本里的 `task_id` 置空，被触发器挡下 →
  从此全库删不掉一行任务；
- `source='generation' ⇒ task_id IS NOT NULL` 这条表级 CHECK 与 SET NULL 语义直接冲突：
  表级 CHECK 分不清"插入时就没写"与"后来被摘掉"。

现在的形状是：触发器只在 `pg_trigger_depth() > 1`（即由别的表派生的引用完整性动作）时放行，
并且放行条件写死成"除 `task_id` / `project_id` 之外各列一模一样、且这两个指针只会变 NULL"；
"generation 必须指着一次真任务"挪到 INSERT 分支里判（那里看得见 `TG_OP`）。
**放行这条本身有用例**（删任务后余额不变、指针为 null、而直接发同样一条置空语句仍然被挡），
不是注释里说说。

## 后果

- 得到：余额页与流水永远对得上（余额是那张表的和）；每一次消费能追到一次真任务；
  "额度用尽"是一个真会发生的状态而不是文案（集成测试用 `adjust` 造出 0 余额，断言拒绝、
  再 +1 点断言放行——反向对照改变的是被断言的那个量）；`@smoke §134` 在真浏览器里跑一次生成，
  看到 AI 那一格从 100 掉到 99、那一行写着"DEMO 模板"并指着命令栏报出的任务号。
- 付出：**并发可以把余额跑到负数**。这道门不预扣（预扣要一个能回滚的事务边界，把 provider 调用整个
  包进库里的一笔事务，今天没有，写了就是假的）。负余额在流水里看得见，这一版接受这个松并把它写在
  `credit-ledger.ts` 的注释里。
- 付出：**Image / Video / Compute 三类今天只有发放、没有消耗方**（§38 图像、§40 视频那条路还没接）。
  页面上每一格自己写着"今天没有消耗方"，不拿 CPU 时间给 compute 编一个数。
- 付出：档位数字（存储 / 团队成员 / 并发发布）今天不生效。要接哪一格，得先有那件事的真实计量方
  （存储配额要先有按字节统计的地方，今天只有资产表，没有"这个人一共占了多少"的读取方）。
- `users.plan` 只有一列，没有改档位的界面：改档位=服务端代码里 `UPDATE users SET plan`，
  这条也要在看的人面前是清楚的（页面上"没有充值入口"那一行就是干这个的）。
