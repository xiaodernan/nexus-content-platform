# ADR-0025：注销账号是"关上门"，不是"拆掉房子"——软删用户，作品按已发布与否分流

日期：2026-10-02 ｜ 状态：**已决定，尚未实现**（判决书先写下来） ｜ 关联：§144 NO LOCK-IN、§145（作品属于用户）、§108（用户历史用 Snapshot）、§164、§80、§133/§134、ADR-0014、ADR-0016、ADR-0019、ADR-0024

> 这份 ADR 只有决定，没有实现。§144 的四件事里，`export design / code / assets` 已经落地（ADR-0024），
> `delete account` 是**唯一动别人数据**的一格，所以按 `AGENTS.md` §193-194 的口径：
> **破坏性操作与法律/商业判断先写判决书，不动手**。下面每一条都写清"为什么"，因为将来执行的人
> 大概率不是写这份的人——他要能照着做，而不是重新猜一遍。

## 背景

原文 §144 给了四件事，最后一件是 `delete account`。今天它一件都没有：

- `/api/account` 只有 `PATCH`（改显示名与简介），**没有注销**；
- `users.deletedAt` 这一列建库就有、到处被 `isNull` 过滤，但**全仓没有一个写入方**
  （`deletedAt: new Date()` 只有 `projects.ts` 在写）。也就是说软删的**读路径**早就铺好了，
  唯独没有"执行软删"的那个动作；
- 审计与通知那两处**已经在按"注销后"的样子写**（"已注销的用户"、`actorId` 留着名字为 null）——
  代码里已经预设了这个功能存在，而用户点不到它。

同时有三条现成的事实决定了这份判决书怎么写：

1. **`projects.ownerId` 是 `onDelete: 'restrict'`**（`schema.ts` 第 155-157 行）。
   这不是风格问题，是**数据库自己会挡住硬删**：只要这个人名下还有一行项目（含已软删的），
   `DELETE FROM users` 就会被外键拒绝。硬删不是"多写几行代码"，是要先把作品全删掉。
2. **`sessions.userId` 是 `cascade`**，而 `sessions` 是**只存哈希**的会话表（§80）。
   会话随用户行消失是安全的，但这也意味着"吊销全部会话"最省事的做法恰恰是最危险的那种。
3. **`projects` 的软删先例已经很完整**（`softDeleteProject`）：确认词必须逐字等于项目名、
   判定做在服务端而不是靠 UI 弹窗、公开页从那一刻起 404、但发布行/快照/评论都还在，恢复后原样回来。

## 选项

1. **硬删**：`DELETE FROM users` + 级联清掉一切。
   - 被外键 `restrict` 挡住；就算先删项目，也等于**把别人的历史一起抹掉**——
     别人给这个人的作品点过的赞、留过的评论、Remix 出来的副本、审计行，全部失去主语。
2. **软删，但立刻释放邮箱与 handle**：`deletedAt = now()`，同时把 `email` / `handle` 置空。
   - 好处是同一个邮箱能重新注册；代价是**审计与通知里的"已注销的用户"变成一句真的查不到的话**，
     而且唯一索引 `users_email_key` 建在 `lower(email)` 上，置空后还得允许 NULL——
     今天 `email` 是可空的（游客），所以技术上做得到，但等于把"这个人来过"这件事从库里擦掉。
3. **软删，保留邮箱与 handle 占位**（本 ADR 选它，见下）。

## 决定

选 **3：软删用户行，作品按"有没有发布过"分流**。

### 一、用户行只软删，不做硬删

`deletedAt = now()`，邮箱与 handle **原样留着**。理由：

- 审计行里那句"已注销的用户"要**指得到一个人**。把 email 置空之后，那句提示就变成一句查无实据的话，
  而审计的全部价值在于事后能回答"这件事是谁做的"。
- **唯一索引不改成部分索引**：软删之后同一个邮箱**不能**再注册一个新账号。这条看着像缺点，
  其实是保护——同一邮箱能重新注册，就意味着"注销"可以被当成"换个身份重来"的洗白通道，
  而平台对作品做过审核、对账号做过封禁，这些结论会跟着邮箱一起被洗掉。
  真要重新开始，今天已经有另一条路：游客身份（`users.guest`）。
- **handle 同样留着**：`/n/<handle>/...` 是这个人在公开世界的地址，把 handle 放给下一个注册者，
  等于把别人作品的门牌号发给了陌生人。

### 二、作品按"有没有发布过"分流

| 作品状态 | 注销后 | 为什么 |
| --- | --- | --- |
| 从没发布过 | **一并软删** | 它是这个人的私有草稿，主人走了就没人再看得见它 |
| 已发布过（有 publication 行） | **留在原地，公开页继续可达** | 见下 |

已发布的作品**不跟着账号一起消失**，理由有两条，缺一条这个决定就不成立：

- **§145 说"作品属于用户"**，但用户已经明确表达过"我要把它发出去给人看"。注销的意思是
  "我不想再用这个平台了"，不是"我要求所有看过它的人再也看不到"。
  把公开发布过的东西一键变成 404，是**对第三方读者的一次无声删除**。
- 已经有人点过赞、留过评论、Remix 过。那些行为的主体不是这个账号，把被点赞的作品删掉，
  等于让别人的历史记录指向一片空白（§108 的同一句：历史不该跟着一次撤销消失）。

**但要在公开页上写清它的作者已注销**：作者名显示为"已注销的用户"，而不是继续挂一个
点进去是 404 的名字。这一条与审计那处的写法同源（`actorName ?? '已注销的用户'`）。

### 三、注销要做的六件事（实现时的清单）

1. **确认词做在服务端**，与 `softDeleteProject` 同一口径：必须逐字输入自己的 handle
   （不是"确定吗"三个字）。只在 UI 里放弹窗等于没有审批。
2. **先给一次导出机会**。§144 的前三件刚落地，注销入口旁边必须能一键导出——
   这一条是 §144 作为一个整体的意思："你可以把东西带走，然后关门"。
   **不做强制**：要求"必须先导出才能注销"会把一次告别变成一场手续。
3. **吊销全部会话与 API 凭据**：`sessions`（只存哈希，删行即可）与 `api_tokens` 全部 `revoke`。
   注意今天的 `revokeCurrentSession()` 只吊销**当前这一个**会话，注销要用的是"全部"那一档。
4. **软删私有项目**（无 publication 行的），**保留已发布的**（publication 行不动，
   公开页继续 404 之外的正常服务）。
5. **审计**：写一行 `user.delete`，`allowed: true`，detail 里带上
   "软删了几个私有项目 / 保留了几个已发布作品 / 吊销了几个会话与凭据"——
   与 ADR-0021 那条同源：事后读审计的人不必再翻当时的代码。
6. **实时与通知**：注销那一刻要停掉这个用户频道的推送（会话已吊销，但已开的 SSE 连接还活着）。

### 四、不可逆，但留一条恢复的路

`deletedAt` 是软删，所以**运营侧**在收到申诉时可以清掉它（`restoreProject` 已有先例）。
但**用户界面里不提供"取消注销"**：一个"我刚才注销了，撤销一下"的按钮会让"注销"变成
一次可以反悔的点击，而它本来是一次告别。运营恢复是例外通道，不是产品功能。

## 后果

- **好处**：注销从"没有"变成一个**有判定、有审计、有出口**的动作，而且不会顺手拆掉别人的历史。
  已发布作品继续可达，读者与 Remix 者的历史不断链。
- **好处**：与 §144 的前三件连成一个完整的意思——**先能带走，再能关门**。
- **代价（明说）**：注销后同一个邮箱**不能**再注册。这是刻意的（见决定一），
  但它会让一部分"我就想重新开始"的用户被挡住，出路是游客身份或换一个邮箱。
- **代价**：已发布作品的作者名会永远显示"已注销的用户"。这是诚实的代价，
  不是可以靠"留一个假名字"绕过去的东西。
- **代价**：这一格**不能只做一半**。软删用户却忘了吊销会话/凭据，等于"用户以为走了、
  其实凭据还能用"——那比不做更糟。上面第三节那六件事是一个整体，少一件都不算完成。
- **仍然欠**：真正的数据保留期限（多久之后可以硬删、由谁执行、要不要留一份归档）
  属于运营与合规决策，**这份 ADR 不做**——它只决定"注销那一刻发生什么"。
