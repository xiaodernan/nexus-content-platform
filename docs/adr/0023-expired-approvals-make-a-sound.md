# 0023 — 过期要出声：一条 `approval` 通知，写在 CAS 赢家那一路

日期：2026-10-01 ｜ 关联：§74 审批门、ADR-0022（到期收敛）、§164 通知中心、§163 实时事件

## 背景

ADR-0022 落地时自己留了一句限度：**过期只改状态**。于是这件事在库里发生了、在账本上记下了，
但在人的世界里没有痕迹——用户只有下一次自己打开审批面板，才会发现那张卡片不在了。
而"打开面板"这个动作本身就是收敛的触发者之一，也就是说
**"没人来看"这一种失败，永远不会被通知给任何人**。

这和 ADR-0022 的动机是相互打脸的：给挂起加有效期，是为了不让一份没人看过的旧补丁还能落地；
可作废之后如果没人知道，用户拿到的实际体验就变成"我上次没来得及决定，回来那个决定凭空消失了"。
需要定的是：要不要给它一个声音，以及声音从哪一处发出来。

## 选项

1. **只在界面上显示"最近作废过什么"**。不新增事件类型，但仍然要求用户再来一次才看得见——
   等于把问题原封不动退回去。
2. **邮件 / 浏览器推送**。语义最贴"通知"两个字，代价是整片新基础设施：今天没有 SMTP，
   也没有 VAPID 密钥，为一条过期消息去搭外发通道不成比例（而且外发消息本身要过 §74 那道门）。
3. **走 §164 通知中心 + §163 实时事件**（选这个）。新增一类 `approval` 通知，
   收件人是任务创建者，`emit` 本来就幂等（`dedupe_key` 上 `ON CONFLICT DO NOTHING`），
   实时事件推创建者自己的用户频道。没有新通道，只有新的一类事件。

## 决定

- **只有一处出声**：`convergeExpiredApproval` 里 CAS 真的写进那一次才 `emit`。
  四个入口都会收敛，四个入口同时读到过期也只有落下终态那一路走得到这里；
  第二道保险才是 `notifications.dedupe_key`。两道分别用一条臂量过：
  把"只看赢家"毁掉（无条件 `emit`）**全绿**——那说明它是 belt，不是唯一在数的那一层；
  把键从 `approval:<taskId>` 换走**红一片**——那说明键才是真正承重的那一层。数字见 `docs/ROADMAP.md` 当日段。
- **收件人取自 `agent_tasks.created_by`**，不是触发收敛的那个会话的用户。查不到创建者或项目就一条都不写：
  状态照样收敛（那是库的事），但没人的收件箱可以塞。
- **"扣下几处"读不出来就不说个数**，而不是报 0。那句标题写的是"这份被扣住的补丁不会落地"，
  处数只是附带信息；一个凭空的 `0` 会被读成"其实什么都没扣"，那是看着像真话的假话。
- **TTL 的人话读法只留一个函数** `ttlLabel`（`lib/notify-plan.ts`）：审批卡片那一行、
  账本里那句作废理由、通知标题三处都从它取。两处各抄一遍 `Math.round(ms / 3_600_000)`，
  改一次常量就会出现一个说"24 小时"一个说"0 小时"——小于一个档位还往下退一档，而不是四舍五入成 0。
- **通知的名单也只留一份**：`NOTIFICATION_KINDS` 那个 Record 同时喂写侧规则与读侧 `isKind`。
  加一类忘了登记会在 typecheck 就红（`levelOf` 的 switch 以 `never` 收尾），
  而不是等到读回来被报成"未分类"——后者是一句"这条通知我不认识"的假话。

## 后果

- 用户不必回来打开面板才知道"那份挂起没人裁决、已经作废"；卡片链接指向 Studio，
  因为那份补丁本来要落在画布上，而不是公开页。
- **收敛从此有副作用**（写一行通知、推一条事件）。这让"它只会被真正赢的那一次执行"变得更要紧，
  而不只是更干净——所以这一片的臂一半钉的是"谁出声"，另一半钉的是"出声几次"。
  代价也记一句：`emit` 抛出来的话，那一次读会跟着失败（没有 `try/catch` 兜它）。
  这是选的不是疏忽——终态已经落库、通知却没写进去的话，界面上会出现"已作废但没人知道"，
  正是这一片要修的那个病；把它咽掉就等于把病重新藏起来。真出现稳定的读失败再改成"落一行欠账、读的时候补"。
- 仍然欠的：邮件与浏览器推送那一路没有；跨实例那半还在 ADR-0010 / §163 的欠账里
  （今天这条实时事件只在同实例的总线上推得动，但**通知行**是写进库的，换实例也还在收件箱里）。
- 记一笔过程上的教训：第一条臂（`approvalCount` 读不出来时报 0）**第一遍活了**——
  单元用例只把 `approvalCount: null` 手工搭给规则，毁掉生产端"什么时候给 null"没人管得住。
  补的用例走真路径（改任务行的 `result` 形状，再收敛，再读写进库的那条通知）。
  口径写进 `docs/TESTING.md`：生产端与消费端必须在同一个用例里见过面，否则臂测的是我搭的假事件。
