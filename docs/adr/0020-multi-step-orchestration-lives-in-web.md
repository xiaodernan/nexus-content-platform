# ADR-0020：§112 的多步编排落在 web 层，第一片只读、计划由确定性配方生成

日期：2026-09-29 ｜ 状态：已采纳（第一片：四步只读配方） ｜
关联：§112、§113、§25、§26、§73、§134、§150、§160、§163、§164、§179

## 背景

§112 要求多 Agent 协作（Product 出计划 → 各 Agent 分步执行 → 交接 → 汇总），§25 要求"复杂任务先生成计划"，
`agent_tasks` 表从 0000 建库起就带着 `plan` 列。但直到 2026-09-29，**全库没有一处写它**：
账本里每一行都是"一次同步 provider 请求"，没有一行是"一份计划被分步跑完"。于是两件事同时悬着：

- §112 的编排没有执行方。名册有了（§73 写入方是 `scripts/db-seed.mts`）、`@提及`解析有了、
  `design.patch` 那道门有了——但"谁来按计划一步接一步地跑"没有；
- §164 的 `Agent task complete` 因此一直没有真终态可发，只能挂在收件箱"没有来源"的清单上。

## 选项

1. **放在 ai-service**。它已经有真作业队列，"分步"看起来该归它。但每一步的产物要落业务库、
   要发实时事件、要写任务账本与通知——这几样都是 web 这一侧的职责（`ARCHITECTURE.md`：
   AI Service 不写业务库）。放过去等于让 ai-service 隔着一条 HTTP 去改业务库，或者把这条边界挪走。
2. **让模型来规划**。这才是终态，但今天没有真 provider：生成的计划只能是模板假装模型给的，
   而那正是 §159 禁止的"假 AI"。
3. **web 层的执行器 + 确定性配方**（本决定）。计划由一份写死的配方生成（四个步骤，各自声明依赖与所需能力），
   每一步的执行方都是本机真的算得出来的东西；"这一步该谁做"由 §73 的名册说了算。

## 决定

- 编排落在 `apps/web/src/server/agent/runtime.ts`；计划本身在 `apps/web/src/lib/agent-runtime.ts` 的**纯规则层**
  （不碰库、不碰网络），所以"计划对不对"能在毫秒级断言，而"跑完留下什么账"由打真库的用例管。
- **计划先验后跑**：`validatePlan` 挡空计划 / 超过 24 步 / 未知步骤 / 重复 id / 缺依赖 / 自依赖 / 成环。
  半跑的计划比没跑更糟——用户会以为剩下的几步也在做，所以整份不合格就整份不开跑。
- **能力由名册说了算**（§73 同一口径）：每一步声明它要求的 `requires`，开跑前拿名册核对；
  名册里没有这个 Agent、或它没声明这条能力，**整份拒收**并说清缺什么。
- **拒收发生在建任务行之前**（同 §134 的额度拒绝口径）：一条从没跑起来的作业不该在账本里留一行——
  "我点了但什么都没发生"与"跑了、失败了"是两件事。五种拒收各有自己的码与状态：
  `no-document`(404) / `roster-empty`(409) / `capability`(409) / `credits`(429) / `invalid-plan`(500)。
- **第一片只读**：四种步骤（结构盘点 / 上架元信息 / 发布门禁 / 汇总）都不改设计模型、不发布、不生成像素，
  所以这一片没有 §150 的可撤销事务可记，也不可能把工作区改坏。将来加会改模型的步骤时，
  那一步必须自己走 Command（§150）并把撤销凭证带回来，不许在执行器里直接写库。
  （2026-10-11 加了第五步 `game`：它不直接写库，产物留在任务行里等用户点「接受」，
  且只许创建不许覆盖——两种落地形状的取舍见 **ADR-0035**。）
- **失败往下传**：某一步失败之后，依赖它的步骤是 `skipped` 并写着被谁牵连——**不是 `failed`**：
  它们根本没跑过。跳过也不发 `agent.step`（没开始过的步骤发一条"失败"就是编），只发一条活动说明。
- **事件是加速器，库是权威**（ADR-0010 后果第 4 条）：每一步推 `agent.plan` / `agent.step` / `agent.activity`，
  同时把计划写回 `agent_tasks.plan`；界面刷新后读的是 `GET /api/projects/<id>/agent` 那一份。
  POST 返回的也是"从库里读回来的那一行"，与 GET 同一形状——"提交时看到的与刷新后不同"因此结构上不可能。
- **中间进度刻度有真来源**（§163）：每跑完一步推一格 `generation.progress`，
  分子是**已到终态**（成功或失败）的步数、分母是计划里的总步数，两个数都从 `plan` 那一份数出来（`progressOf`），
  不是 0.2/0.5/0.9 那种插值；被牵连跳过的那一步不发这一条（它什么都没做）。
  事件形状的构造点只有一个——`agent-tasks.ts` 的 `publishTaskProgress`，编排与同步请求共用它：
  生产者各自拼一份，"progress 恒在 0..1、kind 说得清是哪一类"就得每个生产者各证一遍。
- **capability 如实记**（§160）：计划来自确定性配方 → 整条作业记 `capability: 'demo'`，
  界面常驻 "DEMO 规划" 标识、通知标题里也写。而每一步的读数（页数、门禁分、语料块数）是真的——
  §160 只标"过程是模板给的"，不替结论打折。
- **门禁分不另算一套**：发布门禁那一步复用发布时同一个 `analyzeHealth`（§179）。
  另算一套的话，界面上的分与挡下发布的分迟早对不上。
- **§113 的交接只给声明过的上游**：每一步拿到的是它 `dependsOn` 那几步的产物名与结论摘要；
  把整份项目上下文塞给每一步等于没有交接。汇总那一步只读上游，不重新查一遍库。
- **断在半路的行，读的时候收敛**（ADR-0011 同一口径）：编排在 web 进程里同步跑完，
  一行 `running` 挂着超过 5 分钟只可能是进程被重启或被杀。只碰没有 `provider_job_id` 的行——
  有作业号的那些归 §162 的消费者管，两边不抢同一行。

## 后果

- §164 的 `Agent task complete` 第一次有了真终态；`UNBACKED_NOTIFICATIONS` 只剩 `Build complete` 一类
  （它要的"会完成的构建操作"本身还不存在，所以不是"还没排上期"）。
- 成功那一次走 `finishTask` 这**同一处**扣点（§134）；失败与被跳过的作业不扣。
- `agent_tasks.plan` 有了唯一写入方（`recordPlan`），读回来仍是 `AgentPlanSchema` 那一份形状，
  计划不会长出第二个版本。
- 测试注入点：`runReadinessCheck` 收一个只给测试用的 `runners`，用来把"失败往下传"那条链路真跑一遍
  （§159：没跑过的不算做完）。生产路径不传它。
- 观测到的边界（别读成缺陷）：这一轮的计划不是模型给的，接上真 provider 规划之前 `capability` 只能是 `demo`；
  四步都是只读，所以它只能**指出**问题，不能**修**——它不会写快照、不会改文档、不会发布。
