# ADR-0047：首屏那份文档不该进 HTML（§147 的 10000 档首屏）

- 状态：**草稿（待取舍）** —— 建议先做**可开关**的一版，把两个数摆出来再定去留
- 日期：2026-10-21
- 关联：§147、§146、§16、§159、ADR-0015（整份文档的规模门）、§68（上下文由服务端现算）

## 背景

§147 至今更痛的那一半不是"选中响应"，是**10000 档的首屏**：
生产构建下「导航 → HTML 到手」要 **7.2 秒**（`docs/PERFORMANCE.md` 的分段读数），
其中「最后一个脚本到手 → 第一个节点画出」还有 2.3 秒（水合、首屏求解、首次绘制都在这一截）。

2026-10-21 凌晨把那 7.2 秒的账量清楚了（`scripts/first-paint-cost.mts`）：

| 服务端这一段 | 10000 档（10.7MB jsonb / 10000 行） |
|---|---|
| 数据库读（`design_nodes` 每节点一行） | **1019ms** |
| 组装（**最朴素的下界**，应用那条路还多一层 drizzle 行映射） | **≥ 36ms** |
| JSON 序列化 | **267ms**，体积 **9.37MB**（**gzip 只要 0.17MB**） |
| **服务端合计** | **约 1.3 秒** |

于是：
- **传输不是瓶颈**（gzip 后 0.17MB）；
- 服务端自己只花 **1.3 秒**；
- **剩下的约 6 秒在 Next 的 RSC 序列化**——
  `apps/web/src/app/studio/[projectId]/page.tsx` 把整份文档读出来当 prop 传下去
  （`loadDocument(projectId)` → `<StudioShell initialDocument={…}>`），
  Next 要把 9.37MB 的对象转成 Flight 载荷再塞进 HTML。**这一段与"这份文档有多大"成正比。**

顺带记两条事实（量的过程里查清的）：
① `loadDocument` **不是**读一个大 jsonb，而是**分 4 张表读、在 Node 里组装**
   （`projects` / `pages` / `design_tokens` / `components` / `assets` / `design_nodes`）；
② 节点是**每节点一行**（`design_nodes.data` jsonb），10000 档就是 10000 行；
   数据库层自己只要 235ms（`psql`），走 node-postgres 的行解析是 1019ms。

## 选项

1. **什么都不做**（现状）。
   拒绝：那 6 秒是"把 9.37MB 塞进 HTML"的代价，而它**换来的东西客户端本来也要取**
   （`StudioShell` 里 `studio.load(projectId)` 那条路是**早就存在的老路径**，
   `initialDocument` 只是让它少一次往返）。
2. **首屏不带文档，改走客户端那条老路**（方向 A）。
   `page.tsx` 不再 `loadDocument` → `initialDocument` 为 undefined → 首屏 HTML 变成骨架（几十 KB）
   → RSC 序列化那 6 秒直接消失；客户端水合后 `studio.load(projectId)` 取文档（≈1.3 秒）。
   **净省约 4.7 秒**（6 − 1.3），代价是**画布晚到约 1.3 秒**（首屏先出骨架）。
3. **SSR 只渲染视口内的节点，其余按需取**（方向 B）。
   布局本来就该在客户端算（10000 节点 23~64ms），所以首屏可以只带"够画第一屏"的那部分。
   优点：不牺牲体验（画布立刻出）。代价：要"部分文档"这个新能力（分页 + 合并 + 一致性）——
   **那是另一个量级的工程**，而且它要动写路径（保存时怎么合并、按什么粒度拉）。
4. **把整份文档改成"一页一行 jsonb"**（存储形状）。
   读 1 行而不是 10000 行 → 读与组装都塌下来。
   拒绝（现在）：**存储迁移**要动写路径、快照、导入导出、分支复制、§102 的 `.nexus` 格式——
   是另一个量级的工程，而且它把"首屏慢"换成了"迁移风险"，不该在深夜做。

## 建议

**先做方向 A 的可开关版本**（`page.tsx` 一个 env 开关，构建期生效）：
默认保持现状（SSR 带文档），开关打开时不带 → **把两个数都量出来**（首屏 HTML 多大、多少 ms），
再由**产品**在"少 4.7 秒"与"画布晚 1.3 秒"之间拍板。
守则 §159 的要求在这里是具体的：**不许先改了再报"快了"**——
两个数要来自**同一台机器的同一时段**（今天已经吃过一次"两次不同构建不能比"的亏，见 `docs/PERFORMANCE.md`）。

方向 B 作为方向 A 的**后继**：如果 A 的取舍不被接受（画布晚到不可接受），那 B 就是正解，
但它要单独一片（"部分文档"这个能力）。

## 后果

- **正面**：10000 档首屏从 7.2 秒量级降到 **2.5 秒量级**（1.3 秒取文档 + 水合与首屏求解）；
  而且这一刀**不动存储、不动写路径、不动布局**——它是"少塞一份不需要的东西进 HTML"。
- **负面**：首屏画布晚到（骨架先出）；SSR 那条路对**SEO/首屏快照**的影响要评
  （Studio 是登录后的应用页，搜索引擎不看它 → 影响应该很小，但**要确认**）。
- **边界**：这一刀**不解决**「最后一个脚本到手 → 首帧」那 2.3 秒（水合 + 首屏求解 + 首次绘制）；
  那一截要另看（其中首屏求解 10000 节点是 23~64ms，不是大头）。
- **仍然欠的**：10000 档**首帧**（不是 HTML 到手）那 2.3 秒的段位归因（要带分段计数再量一轮）。
