# ADR-0106：第二条复杂度轴——把单桶 O(limit) filter 从页眉注释变成门

- 状态：accepted
- 日期：2026-11-12
- 版本片：v673
- 关联：ADR 0104（v671，桶数维度的摊还复杂度门 + 仍欠③点名"O(limit) 是 stated bound, not gated"）、ADR 0094 X4（门不许惩罚正当改动）、ADR 0105（v672，同族的操作计数 / A-B 纪律）、ADR 0076/0077（限流桶上界与摊还清扫）、§137 guest 自动签发

## 背景：v671 的门只数 Map 操作，对单桶数组内部完全失明

v671 给 `MemoryRateLimiter` 上了两道确定性门，量的是**桶数维度**：顶到 `maxBuckets` 后每次只淘汰一只（摊还 O(1)，逐笔 Map 操作数零方差）、两档上界 8/4096 单笔淘汰成本相等。它数的是 `Map.prototype.get/set/delete/[Symbol.iterator]` 的调用次数。

但 `hit()` 里还有**第二条、与桶数正交的复杂度轴**，v671 一道门都没碰：

```ts
const previous = this.buckets.get(key);
const window = (previous?.hits ?? []).filter((t) => t > cutoff); // ← 每次滑动窗口扫一遍桶内时间戳
const allowed = window.length < limit;
```

`filter` 扫的是**单只桶的 `hits` 数组**，成本 O(桶内时间戳数) ≤ O(limit)。`filter` 一次 Map 操作都不触发，所以 v671 的 Map 计数器对它**结构性地看不见**。有人把这句换成双重循环 O(limit²)、或嵌套 filter、或图省事扫全镇所有桶，v671 所有的门仍全绿（Map 操作一字未变）。

而要命的是**这笔成本什么时候付**：`allowed=false`（撞上上限）时不再 `push`，但 `filter` **照扫满 limit 条**。也就是说，这道限流闸在**最该省成本的洪水期，每请求反而付满 O(limit)**——和页眉反复强调的"闸不能比自己挡的东西先倒下""防内存耗尽不许自己变成一次放大攻击"是同一条纪律，却恰好没有门。这道闸正对着 §137 guest 自动签发那种**免成本写入口**（一个新访客 = 一只新桶），被 distinct 身份压着打时正是它自己最贵的时刻。

ADR 0104 的"仍欠③"已经把这条轴点名在案：`O(limit)` 是**有界成本**（limit 由调用方给、封顶；页眉"限度"段已声明单桶内存 ≤ `limit×8`），记为界不是事故，**但没有做成门**。本片还的就是这条欠账。

## 决定：不改生产源码，把"有界"从注释变成门

先说**不做什么**，因为判断比动手重要：O(limit) 是设计内的有界成本，不是缺陷。把它"优化"掉（例如换成 O(1) 环形缓冲 / 双指针裁剪）会碰限流判定的核心语义（与 Redis 驱动逐条对齐的三条：被挡不计入、严格大于 cutoff、retryAfter 取最早到期），而 parity 腿本机跑不全（无真 Redis）。在没有端到端回归余量的共享宿主上顺手换掉热路径算法，风险大于收益。所以**本片一行生产源码都不改**，只把 v671 留下的那句"stated bound, not gated"兑现成 gate。

做法：包 `Array.prototype.filter` 数**回调被调用了几次**（＝滑动窗口扫过的时间戳数），`vi.spyOn` 自动还原、先存原方法再转发防递归套娃，同步区间前后清零（与 v671 的 `mapOpCounter` 同手法）。确定性探针实测（时钟冻结、同一只键）：

| 场景 | filter 回调数 | 无关 filter 基线 |
|---|---|---|
| 空桶首笔 | 0 | 0 |
| 满桶 limit=64 单笔 | **64** | 0 |
| 撞上限连量 5 笔 | **恒 64**（零方差） | 0 |
| limit=8 / 64 / 512 满桶单笔 | **8 / 64 / 512**（精确线性） | 0 |

契约门 `ds-complexity-contract.test.ts` +2 条，判据**只钉"O(1) 正当优化也会绿"的形状**：

1. **封顶门**：满桶后逐笔回调数**零方差**（挡"数组无限累积"），且被 `limit + 常数` **封顶**（挡 O(limit²) / 扫全桶）。
2. **正交门**：同一只满桶在 **8 桶 vs 4096 桶**的表里逐笔回调数**相等**（挡"退化成扫全镇所有时间戳"，那条会随桶数暴涨）。

**刻意不钉"必须随 limit 精确线性增长"**：那会把将来把 O(limit) 降到 O(1) 环形缓冲的正当优化判红（ADR 0094 X4）。`limit` 这条轴的线性读数只**归档**（见下），不做门。判据钉的是"有上界 + 不随桶数涨 + 逐笔不漂"，这三条同时有牙又不惩罚正当改动。

## 实测：墙钟只归档，且这次是同进程相邻规模对照

`scripts/ds-benchmark.mts` 加第 4 组"单桶满桶命中 vs limit"（8/64/512，`windowMs=1h` 确保整段不过期），**同一次进程内**跑，读相邻规模比例（比 v672 那种跨进程 before/after 可信得多）：

| limit | p50 us | ns/op | 相对 limit=8 |
|---|---|---|---|
| 8 | 13.15 | 18,278 | 1× |
| 64 | 17.92 | 22,423 | 1.23× |
| 512 | 56.93 | 64,003 | 3.5× |

数据 8× 时只慢 1.23×、64× 时只慢 3.5×——**线性增长，没有 O(limit²) 那种"64× 数据 → 数千× 时间"的塌缩**，与探针的精确回调数（8/64/512）吻合。注意单桶命中 ns/op（18k–64k）比 `TtlLru` 命中（~0.4–0.6k）高一个量级：那是 `hit()` 里 `increment`、Map delete/set、Promise 分配等**与 limit 无关的固定开销**——正因如此 limit 8→64 才只慢 1.23×。这个分解如实写进 PERFORMANCE.md，**不把墙钟当门**（本机共享宿主墙钟不稳，v672 已被 +695% 假 8× 教过一次）。JSON 存档 `docs/evidence/ds/bench-single-bucket-limit-v673.json`。

## 变异臂：5 RED + 2 GREEN，含两条诚实记录的"没红成/判据边界"

`docs/evidence/ds/complexity-arms.mjs` 加 4 条臂，与契约门同一计数器 / 同款判据，`node` 直跑 **7/7 as-expected（5 红 + 2 绿）**：

- **M5（GREEN，诚实记录，非有牙臂）**：假设退化"hits 无限累积"——实测**不可达**：真 `MemoryRateLimiter` 在 `allowed=false` 时不 `push`，即便 `filter` 不再滤过期，hits 也被 limit 卡死在 limit 条（逐笔恒 8，零方差）。门判绿是**正确的**：它守可达的退化，O(limit) 的有界性本就有**两道保险**（filter 裁过期 + allowed 封 push）。这与 v671 那条"固定上界扫全表"没红成同类——不伪造一条有牙臂自欺，也顺带划清门5 的边界：它证的是"成本不会随累积漂"，不是"成本最小"。
- **M6（RED）**：外层 filter 每个回调里再嵌一次 filter ⇒ 单笔 272 次回调（limit=16），封顶门红。
- **M7（RED）**：把所有桶时间戳拼起来 filter ⇒ 8 桶扫 8 / 4096 桶扫 4096，正交门红。
- **M8（GREEN，正面臂）**：把 O(limit) 主动降到 O(1) 环形裁剪（每笔恒扫 8 格、从不累积）⇒ 两条门都绿。**这条专门证明门不惩罚正当优化**（ADR 0094 X4 的正面见证，不是"没红成"的托辞）。

**判据边界（如实记）**：契约门数的是"`filter` 回调次数"这个**代理量**。它可靠抓住"混进 O(limit²) 的嵌套 filter""扫全镇""逐笔漂"这类退化，但**抓不住把线性扫描藏进不触发 filter 回调的循环**（如内层 `for...of`）——M6 的首版正是用 `for-of` 做内层，实测只数到外层 64 次而判绿，查清后改成嵌套 `filter` 才落在门的射程内。这道门的射程是 "filter 扫过的时间戳数"，不是"全部 CPU 指令"；要守后一类需另配门（本片记为界，不冒充已覆盖）。

## 零回归与门

契约门 **8/8**（原 6 + 新 2）；全套 7 文件 **73/73**（v672 的 71 + 2）；变异臂 **7/7 as-expected**；web 测试域与 tools 域窄 tsc 各 **exit 0**（tsconfig 只含改动文件 + 导入图、关 incremental）；eslint 三文件足堆（`--max-old-space-size=2048`）**exit 0**（全项目 tsc/eslint 在本机 ~0.3GB 空闲仍 SIGTERM，资源不是红）。窄 tsc 抓到一个真实类型错（`...args: never[]` 让 `args[0]` 推成 `undefined`，改 `unknown[]` 收口），是**门在做功**，不是噪声。

## 仍欠（如实记）

1. 墙钟读数是**单宿主单次** `scale=1`，没有固定 CI 机型上的多会话均值；p50 13→18→57us 是这台 win32/node22 的读数，不是跨机器 SLA。要看跨机器可比需固定 runner + 多轮。
2. 判据数的是 `filter` 回调这个**代理量**，抓不住藏进非-filter 循环的 O(limit²)（见上"判据边界"）；若要守死"单桶命中 CPU 上界"，需配一条数数组元素访问（而非仅 filter 回调）的门，或上 profile 级证据。
3. 本片**只门不改**：把 O(limit) 真正降到 O(1) 环形缓冲 / 双指针裁剪是明确的后续候选，但要等 parity 腿本机可跑（真 Redis 或等价契约），别在共享宿主上顺手换限流核心算法。
4. `limit` 由调用方给、封顶，本片的封顶门上界是 `limit + 32`（absorbs observability 等无关 filter 基线）；若将来那部分基线随桶数/时间漂移，正交门/零方差门会先红——那是**正确**的（说明有别的成本混进被测区间），但需知道它的语义，别误判成 flaky 去放宽判据。

## 纪律沉淀

- **复杂度不止一条轴**：v671 钉了"桶数维度"，v673 补了"单桶 limit 维度"——两者正交，一张数据结构的 O(1) 承诺要问"对**哪几个会长维度**成立"，别让一个维度的门制造"全绿"的错觉。
- **stated bound 要变 gated bound**：页眉/ADR 里"记为界不是事故"的成本，只要它落在**最该省成本的时刻**（这里是洪水期），就值得一道只钉"有界 + 正交 + 不漂"的门；钉法必须让降成本的 O(1) 优化仍绿。
- **没红成的臂也是证据**：M5 的"退化不可达"和 v671 的 M2 一样，如实记录并解释门为何判绿，比硬凑一条红臂更有信息量——它同时暴露了设计里的第二道保险（allowed 封 push）。
