# ADR-0056：搜索的相关度用「四档确定性分」，不做向量

## 背景

§165 全平台搜索落地时（2026-09-25）页面上写着一条限度：**「相关度排序——子串匹配没有打分，组内按更新时间排」**。
那是一条诚实的限度，不是推托：当时匹配走 pg_trgm 子串，没有任何打分，组内次序纯粹是 `updated_at DESC`。

今天能补上它，是因为**子串匹配本身给得出一个说得清的相关度**：匹配落在哪儿（标题 / 详情）、
落在标题的哪儿（完全一样 / 开头 / 中间）。这不是猜出来的相关度，是可以复述出来的。

## 选项

1. **维持按更新时间排**：零成本，但"搜到一个词，最相关的那条排在第 7 位"是常态；
   排序不表达匹配强度，只表达"谁最近动过"。
2. **TF-IDF / 向量距离（§49 那一套）**：相关性更强，但要么要 provider（今天没有真 embedding），
   要么要一套语料统计与索引（今天没有）。而且**算出来的分说不清**——
   界面上写不出"为什么这条排第一"，就等于把平台的判断藏起来（与 trending 同一句纪律）。
3. **四档确定性分**：标题与查询完全一样 > 标题以查询开头 > 标题里有 > 只在简介/摘要/正文里有。
   每一档都能被复述，代价为零，不需要任何外部依赖。

## 决定

**选 3**，并且把口径原话写在搜索结果页上（`SEARCH_ORDER_METHOD`）。

- **分数算在 SQL 里**（`case` + `greatest`），不是取回来再排。
  这一条是关键的：SQL 那边有 `limit`（每组 8 条 + 1 条用来判断"还有更多"），
  如果先按时间取再在取到的几条里排，**最相关的那条可能压根没被取到**——
  那"按相关度排"就是一句空话。
- **标题列与详情列分档**：详情里的命中最多 1 分，低于"标题里有"（2 分）。
  不分开的话"只在简介里有"与"标题里有"会并列，那就不是四档了。
- **同分时按更新时间新→旧**（今天的行为保留为次序，而不是被丢掉）。
- **口径写在页面上**（`data-search-method`），"没覆盖什么"那一条同步改口：
  明确说**不看词频、不看词在标题里的位置、不看点击与热度**。

## 后果

- 好的一面：搜同一个词，**最像的那个名字排在最前**，不再由"谁最近动过"决定；
  口径写在页面上，界面上的序只是"我们这套四档排出来的"，不是"平台公认最相关"。
- 代价（明说，不装）：这套分**说不出**"为什么这条比那条好"之外的更多信息——
  一个标题里出现三次的词与出现一次是一样的；标题里靠后的词与靠前的也是一样的。
  真要那两样，得有词频与位置统计（或者向量），那是另一片。
- 用户打的 `%` `_` `\` 仍是字符（打分与匹配用同一套转义），不会出现"搜 `%` 命中半个平台"。
- 每一组（项目 / 用户 / 世界 / 游戏 / 角色 / 设计稿 / 组件 / 资产 / 分镜）都接上了同一个打分函数，
  口径只有一处 ⇒ 不会出现"这一组按相关度、那一组按时间"。

## 凭证

`apps/web/test/search.integration.test.ts` 多 2 条（打真库）：
- 四档次序（含"只在简介里匹配的那条被故意设成**最新更新的**"——按时间排它会排第一，
  这条断言钉的是"相关度优先于时间"）；
- 页面上写着的口径与代码里排出来的一致，且"没覆盖什么"里不再留"没有相关度排序"这句旧话。
