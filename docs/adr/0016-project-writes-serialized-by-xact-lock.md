# ADR-0016：同一项目的文档写入用事务级 advisory lock 串行，而不是改成 upsert

状态：采纳（2026-09-27）
关联：任务 #64、`docs/TESTING.md`（并发用例的跑法）、`apps/web/src/server/domain/projects.ts`

## 背景

`writeDocument` 写一份文档的方式是**整删重插**：删掉本项目全部 `pages` / `design_nodes` /
`design_tokens` / `components`，再按传进来的文档逐行插回去。单看一次事务是自洽的（同一事务里删+插，
回滚就当作没发生），但两个并发事务各自从同一份旧文档出发时：

```text
A 删完 → B 删完 → A 插 p_x → B 插同一个 p_x ⇒ pages_pkey 冲突，整个 PUT 报 500
```

这不是假想。2026-09-26 生产日志里抓到过一次 `PUT /api/projects/9404a93d…: Failed query: insert into "pages" …`，
而库里那个项目仍是原本那 1 页 8 节点 —— 事务回滚得干净（没有半写状态），但用户侧是**一次保存失败**。
触发场景很日常：Studio 有自动保存，两个标签页、或者脚本与人工同时在写同一个项目。

2026-09-27 用 `apps/web/test/document-concurrent-write.integration.test.ts` 把它跑成了确定性红：
3 个并发 `saveDocument`（各带 600 个节点），**不加任何锁时连跑 5 遍，5 遍全红**，
红的原因就是日志里那道 `insert into "pages"` 冲突。

## 选项

- **A. 改成 upsert（按行 diff）**。要正确做就得算"文档里哪些节点被删了"，
  那需要上一份真值（现在库里那份可能已经不是发出这次 PUT 的客户端看到的那份了）。
  改动面大，而且把"整份文档替换"这个明确语义换成"三行 diff 猜你想改哪几行"。
- **B. 乐观并发（updatedAt / 版本号不匹配就拒）**。语义最诚实，但今天是**服务端内部互相踩**，
  不是两个客户端在编辑冲突；而且客户端还没有版本字段可回传，加了就是一整套冲突 UI（那是 §163 之后的活）。
- **C. 同一项目的写入在事务里串行**（本 ADR 采纳）。一行 `pg_advisory_xact_lock(hashtextextended(projectId, 0))`，
  事务提交/回滚自动释放，不改任何事务语义，也不跨项目挡。

## 决定

`writeDocument` 开头拿项目级事务锁：

```ts
await tx.execute(sql`select pg_advisory_xact_lock(hashtextextended(${projectId}, 0))`);
```

放在 `writeDocument` 而不是各个调用方，是因为它有两个调用点（`createProject` 与 `saveDocument`），
锁的范围属于"怎么写文档"这件事本身，新调用点不该各自决定要不要锁。

## 后果

- 并发保存不再失败：同一用例加锁后**连跑 5 遍 5 遍绿**。语义不变——最后完成的那个事务整体胜出，
  读回来永远是**某一份完整文档**，不会混两份、不会半截。
- 代价与未挡住的：
  - 同项目写入被排队，一次大文档保存会推迟另一次（实测 600 节点一次的保存是几十毫秒量级，可接受；
    10000 节点那一档要重跑才知道，见 `docs/PERFORMANCE.md`）。
  - **这条测试挡不住"锁范围写错"**：把 key 写成常量 `0` 会让所有项目的保存全局串行，用例照样绿。
    它靠的是这一行代码 + 本 ADR，不是靠断言。真要钉得做跨项目并发计时对照，那条在本机负载下会飘。
  - 锁只在单个 Postgres 实例内有效；多实例部署仍然依赖同一个库，前提不变。
- 与 §147 的关系：这是"整份文档替换"的写放大问题的**下半截**（并发），
  上半截（一次保存为什么要写 10000 行）留给增量保存，那条做完之后这条锁仍然是对的。
