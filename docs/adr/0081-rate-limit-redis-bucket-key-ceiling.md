# ADR-0081：Redis 那半的键基数也要有上界——名额用完交给本机窗口判，而不是把闸门关掉

状态：已采纳（2026-11-03）
关联：ADR-0076（Redis 滑窗驱动；它的后果 7 收了"单只键的寿命"，本文件收"键的条数"）、
ADR-0077（进程内那半的上界；它的**仍欠 2** 就是这一片去还的那一格）、
`apps/web/src/server/security/rateLimitRedis.ts`、`apps/web/test/rate-limit.redis.integration.test.ts`、
`scripts/rate-limit-two-process.mts`、`docs/SECURITY.md`「认证与授权」限流那条、`docs/ENVIRONMENT.md` 的 Redis 那条

## 背景

上一片（ADR-0077）把进程内那张 `Map` 收了口，收尾时把自己的另一半欠账写得很清楚：

> **Redis 侧的键基数没有上界保护**（ADR-0076 仍欠 1）：这一片把进程内那半边收了口，
> 那一半边靠 TTL 收尾，活跃 (路由,身份,IP) 组合的数仍由真实流量决定。

那句"TTL 收尾"管的是**一只桶的寿命**：每次命中 `PEXPIRE windowMs`，长时间没人打的键自己消失。
它管的了寿命、管不了**条数**。今天这台 Redis 上的实测读数是

```
maxmemory            0
maxmemory-policy     noeviction
evicted_keys         0        expired_keys  247
used_memory_human    1.65M
容器 HostConfig.Memory 0（docker stats：4.746MiB / 7.66GiB）
```

也就是：Redis 侧一个字节都没被限住，逐出计数是 0（从来没有东西被逐出过），
过期回收确实在跑（247 条）。所以"靠 TTL 收尾"这句话在今天这台机器上的完整含义是
**"只要还有人按时打它，键就自己没了；不打的话……也没有人把它怎么样"**。

免成本造新键那句话在这里同样成立，而且比进程内那一版更要紧：桶键的形状是 `路由|身份|IP`，
而 §137 的 guest 身份由中间件用客户端可见 cookie **现签**——"来一个新访客"就是"多一只桶"，
不需要登录、不需要凭据。这道闸要挡的正是免成本写入口，而它自己就是一个免成本写 Redis 键的入口。

麻烦的是这台 Redis 不只服务限流：实时总线（`realtime/redisBus.ts`）、审计游标、
并行会话的 e2e 窗口都住在同一台上。于是键空间被压住之后的后果取决于策略，而两个方向都不是我要的：

- 若配 `allkeys-lru`：我的桶会**被别人**的内存压力逐出。那是丢窗口，方向是**更松**，
  而且读数在 Redis 自己的 `evicted_keys` 里，不在这个进程里——我的闸会安静地失去记忆。
- 若配 `noeviction`（今天这台就是）：涨的是我的键，**写不进去的是所有人**。
  总线发布失败、审计写不上，报错的名字却不叫"限流"。

所以这一格的正解不是给那台机器做容量规划（那是别人的运维），是**这条驱动在自己这一侧
把自己能写下的键数钉住**。

## 选项

1. **只靠 TTL**（改之前的样子）。单键寿命收了口，条数由流量决定。
   拒绝的理由不是"不优雅"：洪水的形状是"每人打一次"，那种桶一辈子只被命中一次，
   `PEXPIRE` 让它活满一个窗口，而窗口内新键的造速没有上界。
2. **把那台 Redis 配成 `maxmemory` + `allkeys-lru`**：把闸的容量问题外包给一台共用机器，
   代价是窗口会被逐出（更松）且逐出的是所有人的键。方向错，而且不是我这一侧能负责的。
3. **名册 + 到上界淘汰别人的桶**（照抄进程内那一版的 LRU）：
   淘汰一只**还在窗口里**的桶＝白送那个身份一次额度。进程内那一版之所以敢这么定价，
   是因为它没有别处可以挪窗口——那台进程的内存就是它的全部世界。
   这里有一个别处可以挪（本机那份 `MemoryRateLimiter`），所以这一版没道理付同一笔价。
   这也是与上一片最实质的分歧，不是遗漏。
4. **名册 + 到上界不新建，新键交给本机窗口判**（本条）。
   拒绝新建不等于放行：那条请求仍然被挡，只是挡它的是"每台各数各的"那份窗口——
   正是 ADR-0076 后果 1 已经明码标价过的那次降级。既不新增键，也不动任何人的既有窗口。
5. **把闸挪到边缘层 / 按前缀分片**：这是"一台 Redis 该住多少个子系统"的正解，
   不在这一片，记进下面仍欠。

## 决定

选 4。四条，前三条是机制，第四条是顺手还的一笔旧债。

**一、一条名册，分数就是那只桶自己的到期时刻。**
`${keyPrefix}__bucket_index__`，成员＝桶键名，分数＝`最后一次记录的命中 + 它的窗口`。
关键在于**两边用同一个数**：`ZADD bucket now member` / `PEXPIRE bucket windowMs` /
`ZADD index now+windowMs bucket` 三条写在同一次往返里，而**被挡下的那次既不写窗口也不写名册**。
于是 `ZREMRANGEBYSCORE index -inf now` 扫掉的正好是"已经不在了或马上不在"的桶——
名册不会虚增，也不会虚减（臂 N4、N5 各红一次，见臂表）。
名册自己也要有寿命，`INDEX_TTL_MS = 90 分钟`：不是按窗口续（那样一分钟那档会把一小时的名册
拖成自己的寿命），而是"最宽窗口（1 小时）再放一半"。名册掉了不危险——判定读的是桶键的 `EXISTS`，
名册只用来数条数，掉了下一次命中会把它重新登记，代价只是上界从那一刻起重新数。

**二、腾位子按每次命中做。** 不像进程内那一版攒 256 次扫一趟。
差别是故意的：那里攒着的代价只是"过期桶多活一会儿"，这里攒着的代价是**过期条目占住名额、
把合法的新桶挡在门外**——那正是这一条要防的形状。同一趟 Lua 里两条 `ZREMRANGEBYSCORE`，
往返次数不变（臂 N1：不扫 → 位子腾不出来，新桶被误挡）。

**三、上界只管"新建"。** 已经在数东西的那只桶不参与这一判。
把它赶走才是真的白送额度（选项 3 的理由），而它占的那只键本来就在自己到期的路上。
`EXISTS bucket == 0 且 live >= maxBucketKeys` 才拒。默认 `DEFAULT_MAX_BUCKET_KEYS = 50_000`
——与进程内那一版同一个数，理由是每只桶多带一条索引成员（成员名就是键名，约百余字节开销），
量级同一档；而且**换驱动时"这张表能有多少只桶"这句话不需要改口**，
parity 那一族用例钉的正是两个驱动逐条同答案，写成两个数就多一条没人检查的口径差。
拒新建时 Lua 返回判决 `2`，JS 侧把它读成 `over-cap` 并交给 `fallback`，
`nexus_rate_limit_driver_fallbacks_total{reason="over-cap"}` 记一笔——
**不开新指标**：观测里已有的出口说得出这件事（`fallbackCount` 与同一个 counter），
新指标要新学一个旋钮，而运维那时要问的是同一个问题。

**四、退回日志按原因各一分钟一条（这一格从 §32 起就该有）。**
`countFallback` 原来是**每请求一行** `console.error`：Redis 连不上 + 有人在刷 ⇒ 一道挡免成本
写入口的闸自己开了一条每请求一次的磁盘写，而它挡的对象正好成本比它低。
进程内那一版在 2026-10-31 已经为同一件事把淘汰日志压到一分钟一条（ADR-0077 后果 3），
这一版照做并且**按原因各计各的**——`command-failed` 压住了一行不该顺手把 `over-cap` 那行也压掉。
压的只是字，不是账：counter 仍然逐笔，"看得见地坏"是"每坏一次都有一个数"，不是"每坏一次都有一行字"。

限度（别把这一节读成"Redis 侧有了容量规划"）：上界管的是**这条驱动写下的键数**，
不管那台机器上别人写了什么，也不管 Redis 自己的惰性逐出节奏。

## 后果

**1）名额用完期间，新身份的额度是"每台各数各的"。** 方向上这比共享窗口**更松**
（两台机器上同一只没建成的桶各能放 `limit` 次），代价明码写在 ADR-0076 后果 1，不是这里新引入的。
它换来的是"闸不比自己挡的东西先倒下"，而且不是往更松的方向滑到底：被拒的那条**仍然被挡**，
`OVER_CAP_STILL_GATES` 那一格（演练里）钉的就是这句话——被拒新建的键连打三次（限额 2）给出「放放挡」。
真正要治的是"上界在涨"这件事本身，正解是给那台 Redis 做容量规划或分片，**不是把这个数调大**。

**2）上界是构造参数，不是环境变量。** 与 ADR-0077 后果 6 同一条理由：真要调这个数的人都在
多实例部署，那种部署的正解不在这里。它也因此只在测试与演练里被用小值（这是这一格能被证的前提）。

**3）名册让每次命中多两条 `ZREMRANGEBYSCORE`。** 往返次数不变（还是一次 `EVAL`）。
配对交错探针（`.scratch/s34-latency2.txt`，每档 200 对，同一连接同一毫秒级间隔）：

```
名册=0     老 p50 1.96 p90 4.32 max 15.01 | 新 p50 2.00 p90 4.22 max 39.21 | 配对差 p50 0.05 p90 1.20
名册=500   老 p50 1.99 p90 5.19 max 61.05 | 新 p50 1.86 p90 5.07 max 55.26 | 配对差 p50 -0.05 p90 1.00
名册=5000  老 p50 2.45 p90 21.86 max 164.16 | 新 p50 2.87 p90 20.70 max 56.28 | 配对差 p50 0.05 p90 5.41
```

能钉的只有一句：**配对差 p50 是 0.05ms，且没有随名册长度出现台阶**。
不能钉的那句也写出来：这台机器上的绝对往返是 2–20ms 且随负载漂（第一版探针 `.scratch/s34-latency.txt`
把两个脚本各跑 60 次再比，同一份代码两次跑出来的结论方向能反过来——所以换成配对交错才敢记账）。

**4）`reset(key)` 现在两件事一起做**：`UNLINK` 那只桶 + `ZREM` 名册里那条。
只做前者会留下一个"桶没了但名额还占着"的幽灵，直到它的到期时刻才松；
对上界满着的那段时间，差别就是"新桶能不能建"。臂 N6 红在这一格。

**5）名册住在同一个前缀下，所以 `reset()`（无前缀参数那一趟 SCAN）会连它一起清。**
这是要的，不是遗漏：名册会自己长回来，代价只是上界短暂少算几个（`INDEX_TTL_MS` 那里写了同一件事）。
但**测试与演练必须把它从"桶键"里剔掉**——否则"这个前缀里有几只桶"变成"桶 + 一张数桶的表"，
自己数自己。`keysUnderPrefix()` 里那一句 `!k.endsWith(BUCKET_INDEX_SUFFIX)` 就是为这一格存在的。

**6）`bucketKeysTracked` 是诊断字段，不是指标。** observability 只有 counter 与 histogram，
没有 gauge，所以"现在有几只桶"这句话只能读那台 Redis 的 `ZCARD`（测试与演练都直接读那台）。
字段留着的理由是它让**被拒的那一台**能自证"我看到的名册是满的"，与父进程 SCAN 的权威读数对得上
（演练里 `CEILING_INDEX_MATCHES_BUCKET_KEYS` 钉的三个数是：名册 2 条 / 真实桶键 2 只 / 被拒那台自报 2 条）。

## 验证

常驻门在 `apps/web/test/rate-limit.redis.integration.test.ts` 新增的 `桶键的上界` 一组（7 条）：
① 名额用完时新桶建不出来、但那条请求仍被本机窗口挡住（不是免检）；
② 上界只管新建（已经在数东西的那只照样往 Redis 的窗口里记，也照样被它挡住）；
③ 整窗过期的条目腾出位子（等一等，新桶又能建了）；
④ 名册说的条数＝那台 Redis 上真的有的桶数（含被挡那次不给名册续命）；
⑤ 名册自己也有寿命（它不能变成一只永久的键）；
⑥ `reset(key)` 把名册里那条一起摘掉：名额立刻还给新桶；
⑦ 退回按原因各一分钟一行，而逐笔的账一条不落。

## 第三十六片补的那一组：满额时两台同时撞（2026-11-05）

`scripts/rate-limit-two-process.mts` 的 `④″`。它不改生产代码——改的是**问哪一句**。

**为什么必须并发，而 `④′` 的先后跑不够**：`④′` 问的是"名额按什么顺序发给谁"，所以一台一台来。
而"上界是共享的还是每台各一份"这一句，单机上两种实现给得出**完全一样**的「放 放 挡」——
它只在两台合计上分岔：正确的合计是 `2×限额`（两台各被自己那台本机窗口判），
错的那版合计是 `1×限额`（两台落进同一条 Redis 窗口，因为每台自己数得出名额）。
判据因此钉 `allowedOf(两台) === 2×限额`，而不是任何一台的序列。

**为什么还要一条对照**：只看见"合计翻倍"，另一种读法是"两个进程天生不共享任何东西"。
对照不换形状、只换名额（同一对进程、同一只键、各打 3 次，上界换成 10）⇒ 键建得出来、
两台落到同一条共享窗口 ⇒ 合计回到限额本身。两条合起来才把那句"翻倍来自名额用完"钉住。

绿的那一遍（`npm run ratelimit:two-process`，**22 个真进程、19 条判据全 PASS**，`.scratch/s36-drill-final.txt`）：

```
OVER_CAP_SCOPE_IS_PER_PROCESS: PASS — 两台同时各打同一只建不出来的键 3 次（限额 2）：
  22420→放放挡 / 37348→放放挡，合计放行 4（应为 2×限额=4）
OVER_CAP_PAIR_REFUSES_TO_BUILD: PASS — 同时满额那两台之后：D 这只键没建起来=true、前缀里仍只有
  2 只桶键（上界 2）、两台各自的退回原因 {"over-cap":3} / {"over-cap":3}
PAIR_WITH_ROOM_SHARES_ONE_WINDOW: PASS — 只把名额换成 10 ⇒ 键建出来了=true（应为 true）、
  退回 +0/+0（应为 +0/+0）、合计放行 2（应为限额本身=2）
```

这三行里最好读的是第一行与第三行的对照：**同一对进程、同一只键、同样的打法**，紧上界时合计 4，
宽上界时合计 2。两台的先后会改写它们各自的序列（这一遍 `放放挡 / 放放挡`，C2 那遍 `放放挡 / 挡挡挡`），
但合计不动——所以判据读合计而不是读序列。

臂表。C2 改驱动，C3 只改演练自己那一组的参数；一次只留一个，收尾 `grep -rn "MUT " apps/web/src scripts e2e` = **0**，
恢复后 `git diff -- apps/web/src/server/security/rateLimitRedis.ts` 为空。

## 仪器仍欠（不是功能仍欠，写清楚免得下次当成新的发现）

- **单次命令抖过 250ms 照样让测量期间退回。** `settle()` 钉的是"这一趟往返不退回"，
  启动之后的一次慢命令仍然会把一格打成红（这次首跑的红是
  `alpha 在测量期间退回了…: expected 1 to be +0`，slowlog 同时刻记着 10–48ms 的普通命令）。
  复跑 46/46 绿。**没有为此放宽 250ms 那个超时**——它是生产每请求排队预算的一部分。
  ADR-0077 那句"说法诚实"在这里同样适用：改的是"仪器不把一次运气当判据"，不是"偶发红已根治"。
- **演练这一族没有反证臂**说"如果孩子进程连的是别人的 Redis 会怎样"——线路是硬编码的 56379，
  而 `NO_FALLBACK_ON_REDIS_PHASE` 与新增的退回增量两格合起来已经把"没在往返"读得出来。

## 没牙的格子，点名

- **`DEFAULT_MAX_BUCKET_KEYS = 50_000` 这个具体数**：没有门。测试与演练全用小值（2 与 10），
  没有任何一条跑到那个数量级，所以把它改成 500 或 5 000 全都照样绿。
  挑它的算法（一格 ≈ 键字符串 + 至多 `limit` 个时间戳 + 一条索引成员 ≈ 与进程内同一档）
  写在源码注释里，是推理不是读数。
- **`INDEX_TTL_MS = 90 分钟`**：⑤ 只钉 `0 < pttl <= INDEX_TTL_MS`，也就是"有上界"，
  不钉"为什么是 90 分钟"。改成 10 分钟照样绿（虽然那会让一小时那档的名册在一分钟后重数）。
- **`FALLBACK_LOG_INTERVAL_MS = 60_000` 的具体值**：⑦ 钉的是"5 笔只喊一行"，
  把一分钟改成一小时或改成 10 秒都不红。它防的是磁盘写，不是精确节奏。
- **满额时"两台同时各放 `limit` 次"没有专门用例**：演练的 `OVER_CAP_STILL_GATES` 是一台进程连打三次，
  跨两台的同时满额形状只由断线那一组的 `FALLBACK_SCOPE_IS_PER_PROCESS` 覆盖（同一条降级路径，
  不同的触发原因）。要补就在演练里加一组两进程同时撞满额。
  —— **这一格已还**（2026-11-05，第三十六片，见下面「第三十六片补的那一组」）：`④″` 用两个真进程
  同时撞同一只建不出来的键，判据读的是**两台合计**；旧那格对"上界做成每台各一份"仍然盲（臂 C2 里它照旧绿），
  现在由 `OVER_CAP_SCOPE_IS_PER_PROCESS` 顶上。

## 仍欠

1. **"这台实例现在用的是哪个驱动"没有界面位**（ADR-0076 仍欠 2 / ADR-0077 仍欠 1，原样没还）。
   这一片把上界数字加进了**启动那一行日志**（两条都写"桶上界 50000 只"），但那是日志不是界面。
   —— **这一格已还**（ADR-0082，2026-11-05）：`describe()` 把 `bucketCeiling` / `bucketsTracked` /
   `keyPrefix` / `wire` 交给 `GET /api/admin/rate-limit`，`/admin/rate-limit` 每 4 秒问一次。
   本文件那句"拒的是键的数目，不是请求"第一次有了界面落点：`over-cap` 与 `command-failed`
   在两本按原因的账里分开写（"桶键名额用完（不是 Redis 坏了）"vs"命令失败（Redis 没答上）"）。
   限度也照实写进页面：Redis 那份的 `bucketsTracked` 是**这台最近一次判定带回的数**，
   权威是那台 Redis 的 `ZCARD`（臂 R9 钉的就是"把它当成权威键数"这个错）。
2. **`realtime/redisBus.ts` 里同一形状的 `connectionReady` 还是"一次 error 判死"**（ADR-0077 仍欠 4）。
3. **一台 Redis 该住多少个子系统**：这一片钉住了"闸自己写多少键"，没钉"别人写多少"。
   正解是分片或把闸挪到边缘层（选项 5）。
4. **满额形状的跨进程见证**（上一节点名的那条）。—— **已还**（2026-11-05，第三十六片）：见下面
   「第三十六片补的那一组」，判据 `OVER_CAP_SCOPE_IS_PER_PROCESS` / `OVER_CAP_PAIR_REFUSES_TO_BUILD`
   与它的对照 `PAIR_WITH_ROOM_SHARES_ONE_WINDOW`。
   仍欠的是**取向那半没变**：合计 2×限额是这笔代价的读数，不是可以调小的旋钮；要让它不翻倍，
   正解仍是分片或把闸挪到边缘层（仍欠 3），不是把上界改成每台各一份。
5. **`maxmemory` 本身**：今天这台是 `0` + `noeviction`。上界把"我的键"钉住了，
   但如果运维将来给它设了 `maxmemory` + `allkeys-*`，我的窗口会被逐出，
   而那时"闸的记忆丢了"这件事的读数在 Redis 的 `evicted_keys` 里，不在这个进程里。
   `docs/ENVIRONMENT.md` 现在写了这条策略读数，没有写"改成 lru 时要连带做什么"。
