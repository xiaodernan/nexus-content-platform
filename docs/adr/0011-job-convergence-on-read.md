# 0011 — 异步作业的终态由"有人来问"驱动，web 不起后台 worker

日期：2026-09-26 ｜ 关联：§162 作业队列、§163 实时通道、§164 通知、ADR-0010

## 背景

`POST /api/ai/jobs` 把一次生成交给 ai-service 的队列之后，剩下一个必须回答的问题：
**谁来发现它结束了？** web 的 `agent_tasks` 行停在 `running`，通知要等终态才发，
Studio 与 `/tasks/<项目>` 上那句"在跑"也要有人停掉它。

三个选项：

1. **web 进程内起一个轮询器**（每 N 秒把所有 `running` 且有 `provider_job_id` 的行问一遍）。
   看起来最"自动"，但它要回答一串没有好答案的问题：多实例时谁负责哪一行（要租约）、
   进程重启期间漏掉的怎么办（要补偿扫描）、开发机上 `next dev` 热重载会不会留下僵尸定时器、
   以及最贵的一条——它会让人以为"web 知道作业什么时候结束"，而真值其实在另一侧。
2. **靠浏览器**。客户端每 2 秒打一次状态接口，页面开着它就会收敛。
   代价是关掉标签页之后没人管了：那次作业在平台的账本里永远是 `running`，
   而 §164 那条"生成完成"的通知永远不会发出——用户最该收到通知的时候恰恰是他不在场的时候。
3. **读取即收敛**（选这个）：任何一次 `GET /api/ai/jobs/<jobId>` 都现场问一次 ai-service，
   把观察到的终态写进行、发通知。web 不猜、不缓存、不养后台进程。

## 决定

采用 **3**：状态的权威在 ai-service，web 是镜像，镜像在**被读的那一刻**更新。
配套两条纪律：

- **游标写在库里**（`activity_cursor`），不写在进程内存里。两个标签页同时轮询同一个作业时
  只有一个 CAS 得中，另一个不会把同一批活动再推一遍；实例之间也因此不会重复推。
- **通知的幂等靠 `generation:<taskId>` 这个 dedupe 键**，不靠"我记得发过"。
  重复观察最多是多问一次数据库，不会多写一条通知。

## 后果

- 得到：没有新的后台进程、没有租约、没有热重载僵尸；多实例天然安全（谁读到谁收敛）；
  每次读到的都是现场状态，ADR-0010 那条"实时只当加速器、权威状态一律读库"在这里成立。
- 付出，并且这条要写在界面上而不是藏在代码里：**没人问就不收敛**。
  今天会问的只有 `GET /api/ai/jobs/<jobId>` 这一条路，而它没有界面在调（提交入口还没做）——
  所以此刻真实的图景是：**一次异步提交之后如果没人来问，那行就一直停在"在跑"，通知也不会发**。
  `/tasks/<项目>` 也不会替它收敛：打开任务页时逐行去问一遍 ai-service 是 N 次外部请求，
  最坏情况 N × 8 秒，把一页列表变成一次抽奖——所以那条路要走就得先解决"问不动怎么办"（并发上限 + 只问在跑的 + 拿不到就标"未知"）。
  另一条更对路的是**服务端可寻址的作业事件源**（ai-service 完成后回调 web，或 §163 的总线换成 Redis pub/sub 后由消费者组读取），
  那已经不是"再加一个轮询器"能解决的，记在这里作为下一步的形状。
- 因此 `/tasks/<项目>` 上"每一行对应一次请求"这句话仍然真，但行的**状态列**在异步作业上是"最后观察到的状态"，
  不是"现在的状态"。界面与文档都不许把它读成后者。
