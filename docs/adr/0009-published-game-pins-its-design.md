# 0009 公开可玩的作品钉住"发布那一版"的游戏设计

- 状态：已接受（2026-09-25）
- 相关：§50 Game Studio、§56/§57 Publish 与分享、§16 设计模型是唯一真值、§159 不许假数据

## 背景

`/game/<项目>` 已经能把 §54 那份游戏设计文档跑成一关，但它按归属判定，只有作者能进。
要让别人玩到，就得回答"公网上的那一份是谁"：

`games` 表里的工作稿是**一直在改的**——作者今天把敌人血量从 10 调成 999，
如果公开地址读的是这一行，那么昨天分享出去的链接今天就会变玩法。
而 §57 对设计文档已经定了规矩：发布锁定快照，公开页读的是那一版。

## 选项

1. **把游戏文档塞进 `snapshots.document`**（和页面节点同一份 jsonb）。
   否：快照的契约就是"设计文档"（`parseDocument` 那一套），塞进去等于让一份 jsonb 有两种解释，
   读快照的每条路径（历史、Compare、分支、恢复）都要跟着加分支判断。
2. **公开路由直接读 `games` 工作稿**。
   否：违反 §57 的锁定语义，而且"我分享出去的关卡怎么变了"是使用者最先撞到的问题。
3. **发布时把当时那份游戏文档复制进 `published_projects.game_document`（jsonb，可空）**。
   选它。

## 决定

`published_projects` 增加可空列 `game_document`，在 `publishProject` 写 publication 行的同一处，
把当时 `games.document` 原样钉进去；没有游戏行的项目这列是 null。
公开可玩路由 `/play/<handle>/<slug>` 只读这一列，并且沿用 §9c 资产那套双条件判定：
**必须有 public 且未被人工拒绝的发布行**，路径才认。

## 后果

- 公开的那一份不随工作稿变化，和快照同构：作者改完要重新发布才会换。
- 存的是**原样的 jsonb**，不做"只在能解析时才钉"的筛选：解析失败时公开页显示"这一版的游戏读不出来"
  并给出原因，而不是悄悄变成"这个游戏没有内容"。静默丢弃比明说坏了更糟。
- 老发布行没有这一列的值（null），因此公开页不出现"可玩"入口——**不回填**：
  回填等于替历史项目宣布"当时发布的就是现在这份工作稿"，而那件事没人知道。
- 换版本 / 取消发布 / 被拒绝都自动生效，因为读的就是这一行；不需要额外的失效逻辑。
- 代价是多存一份文档 jsonb（与快照同量级）。这是刻意的冗余：它是"发布出去的那一版"的一部分，
  不是第二份工作真值——工作真值仍然只有 `games.document` 一处（§16）。
