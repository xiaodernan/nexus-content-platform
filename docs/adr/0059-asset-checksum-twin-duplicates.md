# ADR-0059：同项目重复上传的 checksum twin——并发下会多一行，记下来不修

## 背景

`uploadImageAsset`（`server/domain/assets.ts`）有一处"同项目内重复上传复用同一份字节"：
先按 `(project_id, checksum)` 查 twin，命中就复用那一行（`reused: true`），
未命中才写新行、新 storageKey。这是**读—改—写**的前半截，而 `assets` 表
**没有 `(project_id, checksum)` 的唯一索引**（`files_project_path_key` 是另一列，
且 `files` 表今天没有插入方）。

于是两个并发上传同一份字节（双击上传、两个标签页同时贴图）时：
两边 select 都看不见对方 → 都走到 insert → 两行相同 checksum、两份字节。
后果只有两个，都不致命：存储配额多算一份、资产清单里出现两张肉眼一样的图。
**不会 500、不会损毁数据**——所以它不在 #170-#175 那条"并发双点 500"的线上。

## 选项

1. **加部分唯一索引 `(project_id, checksum)` + `onConflictDoNothing` 回头读**（#172 同族修法）：
   能把双行消灭，但顺带把另一件事也堵死——**用户合理地上传两张一模一样的图**。
   同一个 logo 放进两个上下文、先上传一张后面想把它归属到另一个角色
   （`character_id` 在 twin 命中时**刻意不改写**：字节相同就是同一张图，
   归属仍是第一次写入它的那个角色，这个行为有测试钉着）。
   加索引后这些诉求全部变成"拿回旧行"，而"同项目同字节是否必须只有一行"
   是产品语义，不是实现细节。
2. **把 twin 查询收进项目写锁**（ADR-0016）：能消窗口，但为"省一份字节"给每次上传
   加一道跨请求串行化，代价与收益不般配（上传本来就不是高频路径，重复上传更是偶然）。
3. **记下来不修**：并发双传同字节是多一行 + 多算配额，用户看得见（清单里两张图）、
   删掉一张即可，没有隐藏损坏。

## 决定

**选 3**。竞态与后果写进本 ADR 与 ROADMAP，不假装它不存在。
真正的修法等产品对"同项目同字节允许多少行"表态：
- 若答案永远是 1，按选项 1 修，并同时回答"归属不同角色"该怎么办
  （大概率要把归属从行级挪到引用级，那是另一个决定）；
- 若允许多行，今天的形态就是对的，本 ADR 归档为"已评估、非缺陷"。

在拿到那个决定之前，新代码**不许**给 `assets` 加 `(project_id, checksum)` 唯一索引。

## 后果

- 并发双传同一字节：两行、两份字节、配额多算一份；串行双传维持今天的复用语义。
- `reused: true/false` 的回执不变，调用方（上传 UI、§38 生成链路）照旧能说出
  "这一张是新建还是复用"。
- 与 ADR-0058（举报升级案的并发重复）同属"已记录、等产品表态"一族；
  两处都不是数据损坏，都不允许用库约束悄悄改业务语义。
