# ADR-0077：进程内限流表的规模——清扫、上界与记账（外加顺手改的三处仪器）

状态：已采纳（2026-11-02）
关联：ADR-0076（Redis 滑窗驱动，它的后果 7 点名了"进程内版本的漏"，本文件是去还那一格）、
ADR-0060（身份之前的按 IP 兜底闸）、ADR-0070/0071（转发链取哪一段）、ADR-0072（回收端点那 6 次/10 分钟）、
`docs/SECURITY.md`「认证与授权」限流那条、`docs/adr/0075-*`（并行会话的搜索建议片，编号让给她了）

## 背景

`apps/web/src/server/security/rateLimitMemory.ts` 的 `buckets` 是一张 `Map<string, number[]>`。
改之前它只在**同一个键再次被命中**时把自己刷新一次，于是别的键里那些早就过期的时间戳永远留着，
键名字符串也永远留着。这张表的规模因此是"这台进程活期间出现过的 distinct 桶"——单调涨、不收口。

不是理论上的涨。桶键的形状是 `路由|身份|IP`，而 §137 的 guest 身份由中间件用客户端可见的 cookie
**现签**：没有会话就签一个随机的，`requireUser()` 拿不到会话行就就地建一个 guest 用户。
所以"来一个新访客"＝"多一只桶"，不需要登录、不需要凭据、不花一分钱。
`rateLimit.ts` 里 `ipWriteGate` 那段注释记过同一件事的另一面（当年它是"按身份限流空转"的原因）：
**一道闸自己成了一道免成本写入口**，而它要挡的对象恰好就是这类入口。

同一时间 Redis 那一版（ADR-0076）从一开始就收了口——`PEXPIRE` 让长时间没人打的键自己消失，
而且它的页眉把这一格直说了："进程内驱动反而没有这一格，这是进程内版本的漏"。

## 选项

1. **部署上限制"只有一台 web"**——不是技术方案，是把债写进运维文档；而且 ADR-0076 的退回路径
   （Redis 坏了退进程内）用的正是这张表，退回期间它照样在被压。
2. **每只桶挂一个 `setTimeout`**：到期自己删。50 000 只桶就是 50 000 个活动定时器，
   Node 的定时器堆本身变成新的规模问题，而且"进程重启就什么都没记"这件事一条都不解决。
3. **惰性清扫**（命中时只把**自己这一只**桶滤空）：`hits` 数组是清了，键名字符串与桶对象还留着——
   而 guest 洪水里绝大多数键一辈子只被命中一次，惰性那一条对它们一次都不跑。收不掉要收的东西。
4. **周期全表清扫 + 桶数上界 + 三本账**（本条）。
5. **"反正生产会设 `NEXUS_REDIS_URL`"**：那台 Redis 挂了之后仍然要退回这张表；
   默认单进程部署（dev、vitest、e2e、小规模生产）用的也是这张表。

## 决定

选 4，三条：

**一、清扫按每只桶自己的窗口。** 桶的形状从 `number[]` 变成 `{ hits: number[]; windowMs: number }`。
判据是 `now − 最新一条命中 > windowMs`（最新那条到期，整只桶才算空——窗口是滑动的），
而不是"这张表里最大的那个窗口"或"最小的那个"：这张表同时住着 `6 次/10 分钟` 与 `600 次/10 分钟`，
按最大判会让短窗口的桶赖着不走（那正是要收的东西），按最小判会删掉还在窗口里的长窗口桶（那是白送额度）。
两个方向都是错的，臂 B5 就是后一个方向，它红得很快。

**二、上界按 LRU 收。** `maxBuckets` 默认 50_000（一格 ≈ 键字符串 + 至多 `limit` 个时间戳 + 一个小对象，
按 300 字节估约 15MB）。`Map` 的插入序在这里当 LRU 用：命中时**先 `delete` 再 `set`**，
最近被碰的永远在尾部，于是淘汰头部 O(淘汰数)——而不是每次命中排一遍全表。
这一条必须成立，否则"防内存耗尽"这件事自己会变成一次放大攻击。

**三、三本账分开。** `nexus_rate_limit_buckets_pruned_total{reason}` 分 `expired` / `cap` / `reset`，
另加 `nexus_rate_limit_buckets_created_total`（**不带标签**：桶键里装着邮箱与 IP，而这一格要的读数
只是总量；指标侧还有 `MAX_SERIES_PER_METRIC = 64` 那道折叠）。
恒等式 `created − pruned === bucketCount` 是这一片唯一能核对"我们真的知道自己攒了多少桶"的东西，
而 observability 只有 counter 与 histogram，没有 gauge，所以桶数的权威读数另开一个
`bucketCount` getter 给测试与诊断，两边都核。

## 后果

**1）淘汰一只还在窗口里的桶，是往更松的方向错。** 这与 ADR-0076 后果 2 那句
"两边的差只会让配额更早用完——限流闸宁可往更严的方向错"方向相反，所以要说清它换来什么：
一个被持续滥用的身份，它的桶一直在被碰，因此一直在 LRU 尾部——**正在挨挡的那几格不会被淘汰**。
先走的是很久没人碰的桶，而那类桶多半本来就该由第一条收掉。真正被这一条牺牲的是
"洪水把上界内的格子全占满"那种形状：那里要么白送一些身份一次窗口，要么这台进程先倒。
选了前者，并把 `cap` 那个读数留在原地。

**2）`cap` 只数"还在窗口里的桶被挤掉"这一种牺牲。** 顶到上界那一步顺手看一眼头部桶自己的窗口：
整窗已过期的那只是**放过名额**，记进 `expired`、不算牺牲、也不喊。
这一条不是排版：全表清扫每 256 次命中才跑一趟，而这张表同时住着 60 秒与 10 分钟两档窗口——
一张顶满的表如果新来的都是短窗口，只等全表那一趟就会让长窗口的桶替它们挨刀。
把放过的额度记进 `cap`，那个读数在正常流量下也会涨，而它唯一的用处就是说"这台进程被 distinct 身份压着"。

**3）"到上界"那行日志最多一分钟一条。** 顶到上界之后**每一次命中**都会淘汰一只，
日志若跟着逐笔走，那就是每请求一次磁盘写——一道挡免成本写入口的闸自己开了一条成本更低的入口。
逐笔的数在 counter 里，日志只是给没在看指标的人的提醒。`expired` / `reset` 不喊：常态不是事件。

**4）记账必须带 `reset`。** `reset()` 不记的话那句恒等式每次清桶都差一截，
而差的那一截正是"数不清自己攒了多少桶"。臂 B4 钉的就是这一格。

**5）单只桶的内存由 `limit` 封顶。** 只有被放行的命中会写时间戳，所以一只桶至多 `limit` 个时间戳；
两条合起来才是这台进程的上界 ≈ `maxBuckets × (键长 + limit×8)`。**而 `maxBuckets` 之内仍然先到先得**——
这一格的正解不在这里，是 `NEXUS_REDIS_URL`（窗口不在任何一台的内存里）与边缘层。
本文件做的是"闸不能比自己挡的东西先倒下"，不是"闸有了容量规划"。

**6）`maxBuckets` 是构造参数，不是环境变量。** 需要调这个数的人都在多实例部署，
那种部署的正解是设 `NEXUS_REDIS_URL`，不是把本机记账的天花板再抬高一格。

**7）`RedisRateLimiter` 退回时用的就是这一版**，所以上面七条同时是那条路径的七条：
退回期间每台各数各的（ADR-0076 后果 1）之外，它正对着的也是这张现在会自己收口的表。

## 顺手改的三处仪器（都属于上一片，红的是测量而不是驱动）

**一、`retryAfterMs` 的 50ms 容差本来就是个错仪器。** ADR-0076 的"验证"那条写着两边相差 ≤50ms，
量到的其实是"Redis 那一趟驱动自己走了多久"：倒计时 = 最早那条到期的时刻 − `now`，
而两个驱动各读各的时钟（进程内用主机 `Date.now()`，Redis 用服务端 `TIME`）。
2026-10-31 复跑连红在 55 / 62 / 64ms，另一次 217ms，同一条用例里 `allowed / count` 一格没差。
判据换成与漂移无关的三句：方向不许反（一边"不用等"一边"还得等"就是漏放或漏挡）、
说"还得等"的不许超过整个窗口、两边差不超过一个窗口 + 1 秒（真分歧一次差出秒级，噪声是几十毫秒级）。
两条驱动同时跑（`Promise.all`）而不是先后跑——先先后后那版把调度间隙直接混进了差值里。

**二、`connectionReady` 一次 `error` 就判死。** 原来 `once('error') → resolve(false)`，
于是"这台连接其实好好的、只是抖了一下"也能读成 false：ioredis 自己会重连，一次抖动之后往往就是 ready。
现在改成**有界的等待**（`CONNECT_READY_BUDGET_MS = 3_000`）：`ready` 事件→true，`end`→false，
到点还没 ready→false，中间出过 error 不算结论。error 事件由构造函数里那条常驻监听器接住
（没有监听者的 `error` 在 Node 里是 uncaught exception），这里因此不再挂 `once('error')`。
预算为什么是 3 秒而不是"Redis 应该多快"：本机探针（`.scratch/s33-ready-probe.txt`）逐个新建 12 份
limiter，空载就绪用时 12 / 14 / 16 / 17 / 23 / 25 / 33 / 35 / 39 / 48 / 48 / 129 毫秒，
八个一次 `new` 出来全部就绪；而同一台机器在并行会话压着跑的时候，一次 `ready` 在 1 秒预算里落过 false。
`hit` 从来不等它，所以这一格变慢只影响测试与演练。

**三、`reset() 只清自己的前缀` 那条原来没等第二份连接。** 上一片补成了"等 `ready` + 钉
`fallbackCount === 0`"，这一片再升级成 `settle()`：往一只丢弃用的键上打一次，
看 `fallbackCount` 有没有涨，没涨才算"这条线路此刻真的在往返"（涨了等 250ms 再来，最多 20 次）。
理由是 `commandTimeout: 250ms` 与 `enableOfflineQueue: false` 这对参数意味着
**连接 ready 了照样可能退回**——命令排在别人的 `EVAL` 后面超了 250ms 就走进程内那一份，
而后面的断言是在跟一份空窗口比。2026-11-02 两次六连跑共红三次，红在三个互不相干的位置
（`alpha.ready` 落 false、`beta.ready` 落 false、`theirs.fallbackCount` 是 1），
而那三趟整体用时 21.33 / 29.99 / 32.91 秒，健康的趟是 10–16 秒：这台机器上跑着十几个容器，
另一条会话的 dev server 正压着同一台单线程 Redis。
判据同时从"绝对 0 次退回"改成"相对 `settle` 基线 0 次"——启动期那几笔退回是 ADR-0076 后果 3
里明码标价过的有界退化，**测量期间不许退回**才是这些用例真正要钉的那句话。
**没有为此放宽 250ms 那个超时**：它是生产每请求排队预算的一部分。

一句实话：`settle` 版连跑六趟 6/6 绿（用时 12.48–14.04 秒）是在健康负载下取的，
那三次红没有制造负载就没法复现。所以这一条的说法是"仪器不再把一次运气当判据"，
不是"偶发红已根治"。

## 验证

常驻门在 `apps/web/test/rateLimit.test.ts` 的 `进程内限流桶的规模（清扫、上界与记账）` 一组（8 条），
加 `apps/web/test/observability-instrumented.test.ts` 的记账凭证 2 条。

- **记账恒等式**：`created` 6 / `pruned` 5+1 / `bucketCount` 三段都核，`reset()` 之后仍然成立。
- **清扫按每只桶自己的窗口**：60 秒那档整窗过期的被收走，10 分钟那档"一个字没少"（`blocked.count === 2`）。
- **洪水顶到上界就不再涨**：50 条 distinct 身份 → `bucketCount` 8、`cap` 增量 42；
  活下来的那几只照常按自己的窗口数到顶（第 20 次仍被挡）。
- **正在挨挡的那一格不被淘汰**：上界 4、洪水 30 轮，**每一轮**都还得是挡
  （这一句是 B6 那轮补的，原来只核最后一次，见下面的臂表）。
- **放过过期名额不算牺牲**：顶到上界时头部那只若整窗过期，走 `expired`、`cap` 不动、日志不喊。
- **日志按分钟收敛**：30 条 distinct → `cap` 增量 26 而 `warn` 只有 1 行；再过一分钟仍在洪水里 → 第 2 行。
- **代价说清楚**：被挤出去的那一格下一次命中重新变空（`allowed: true`）——这一条不是缺陷披露，
  是后果 1 的读数。
- **默认上界存在而且不是无穷**：不设 `maxBuckets` 打 1000 条不淘汰（`cap` 增量 0）。
- 三文件合跑 **39 条全绿**；集成文件 `settle` 版连跑 6 趟全绿；
  两进程演练 `npm run ratelimit:two-process` 12 条判据全 PASS，其中 `CHILDREN_USE_REDIS_DRIVER`
  的读数是"redis 段 6 个进程：驱动 RedisRateLimiter，ready true"，
  `NO_FALLBACK_ON_REDIS_PHASE` 是 `0/0/0/0/0/0`，`REDIS_DOWN_STILL_GATES` 是
  `ready=false、5 次退回、判定 放放放挡挡`（这一条证明预算改动没把"连不上"读成"连得上"）。
  **这句"12 条判据"写错了，2026-11-03 更正**：那一版演练是 **12 个进程、11 条判据**
  （`docs/ROADMAP.md` 第三十二/三十三片那两节写的 11 条是对的）。
  数错的原因是抄读数时把进程数当成了判据数——正是本文件在 B6 那一格说的同一种错：
  **说法与事实对不上，绿了也不作数**。今天这一族是 18 个进程、16 条判据（ADR-0081）。

臂表（每条都是改一处源码、跑、立刻改回来；**一次只留一个臂**，`grep -c "MUT "` 归零才算收尾）：

| 臂 | 改了什么 | 结果（逐字读数） |
| --- | --- | --- |
| B1 | 全表清扫那一趟整个不跑 | 2 红：`expected 6 to be 1`（`记账对得上`，rateLimit.test.ts:115）、`expected 3 to be 2`（`过期窗口被收走…`，:138） |
| B2 | 上界那条不生效（不再按 `maxBuckets` 收口） | 3 红：`expected 50 to be 8`（:152）、`expected 31 to be 4`（:171）、`expected 3 to be 2`（:184） |
| B3 | 淘汰方向反了（从最近被碰过的那一头收） | 2 红：`expected true to be false`（:158，打了 20 次的那只被自己挤掉 ⇒ 又放行一次）、`expected false to be true`（:187，该被挤掉的 `first` 反而留在表里继续挨挡） |
| B4 | `reset()` 清全表不记账 | 1 红：`expected { created: 6, pruned: 5 } to deeply equal { created: 6, pruned: 6 }`（:121） |
| B5 | 清扫用固定 60s 而不是每只桶自己的 `windowMs` | 1 红：`expected 1 to be 2`（:138，还在 10 分钟窗口里的那只被当成过期删了） |
| B6 | 命中时不"先删再写"（`Map` 插入序不再当 LRU 用） | **第一跑 15 条全绿 ⇒ 惰性臂**。把 `正在挨挡…` 从"循环结束后核一次"改成"每一轮都还得是挡"之后重跑 → 1 红：`第 3 轮把正在挨挡的那一格挤掉了: expected true to be false`（轮号与手算一致：上界 4，第 4 只 bystander 进来时头部正是它） |
| B7 | 上界兜底那一步不看每只桶自己的窗口（整窗过期的也算 `cap`、也喊） | 1 红：`没有一只活桶被挤掉，cap 那本账不该动: expected 2 to be 1` |
| B8 | 淘汰日志不设节奏（每请求一行） | 1 红：`26 次淘汰只该喊一行: expected 26 to be 1` |

两条关于臂本身的教训，都来自这一片：

1. **"红得和上一臂一样"就是没恢复的信号。** B3 第一次跑出来的三条红与 B2 一模一样，
   因为 B2 的改动没先恢复——那一跑什么也没证明。恢复上界条件、确认只剩一个 `MUT ` 标记后重跑，
   才拿到 B3 自己的两条红。
2. **一条断言"最后再核一次"挡不住中途的错。** B6 那轮是这一片唯一抓到惰性臂的跑：
   正在挨挡的那一格的桶在中途被挤掉过一次，但因为挤掉之后又被重新创建并挪到尾部，
   最终状态看起来完全正确。判据必须写在发生的那一步上，不然它只是事后核对现场。

没跑的臂，点名：

- **`SWEEP_EVERY_HITS = 256` 这个具体节奏**：没有断言钉它。改成 1 或改成 10 000 都不会红
  （测试用自己的小 `sweepEveryHits`）。它是成本推理，不是读数。
- **`DEFAULT_MAX_BUCKETS = 50_000` 这个具体数**：`上界默认值存在而且不是无穷` 那条只证
  "不设参数也有一张收口的表"，不证这个数本身。挑它的算法（300 字节/格 ≈ 15MB）写在源码注释里，
  没有门。
- **`RedisRateLimiter` 里退回用的那份进程内窗口**：代码上吃的正是这三条（同一个类），
  但**今天不可测**——`fallback` 是私有字段，没有桶数出口。"Redis 长宕 + distinct 身份洪水"
  那条路径的规模行为没有门。

## 仍欠

1. **`stats()` 界面位**（"这台实例现在用的是哪个驱动、退回了多少次"）仍欠，ADR-0076 仍欠 2 原样没还。
   今天的答案只有启动那一行日志与两个 counter。
   —— **这一格已还**（ADR-0082，2026-11-05）：两份驱动各自实现 `describe()`，`/admin/rate-limit` 每 4 秒读一次
   单例那份现场。本文件那条"进程内那三个不适用"在这里有了第二层钉子：界面上它们必须长成
   `—（这个驱动没有键空间）` 这一族句子，而不是 0（e2e 那一轮专门量这个，臂 R11 有牙）。
   而"每台各数各的"这句代价现在写在页面上（`NEXUS_REDIS_URL 未设——限额那句话现在是"每台各数各的"`），
   不再只在代码注释与本文件里。
2. **Redis 侧的键基数没有上界保护**（ADR-0076 仍欠 1）：这一片把进程内那半边收了口，
   那一半边靠 TTL 收尾，活跃 (路由,身份,IP) 组合的数仍由真实流量决定。
   —— **这一格已还**（ADR-0081，2026-11-03）：名册 + 到上界不新建桶键（交给本机窗口判）。
   取向与本文件第 3 条**相反**并且是故意的：那里淘汰是因为没有别处可以挪窗口，
   这里有一个地方可以挪，所以不必白送任何人的既有额度。
3. **退回侧的上界不可测**（上一条"没跑的臂"已经点名，重复列在这里是因为它是功能缺口不是测试缺口）。
4. **`realtime/redisBus.ts` 里同一形状的 `connectionReady` 还是"一次 error 判死"**。
   这一片没改它——那份的 `ready` 有没有同类偶发红，没有读数，也没有门。
   —— **这一格已还**（ADR-0083，2026-11-05，§SEC 第三十七片），**但还的不是"判死"那三个字**：
   `ready` 的语义按决定**没改**（它回答"构造那一次建起来了没有"，落定后不再变，这是它注释里写明的取向）。
   查下来真正坏的是**读数**——`stats()` 以前只有那份闩，于是 Redis 比这台进程晚起来的那台，
   界面上永远写着"没接上——这台实例收不到别机的事件"，而连接层早已自动重连并真的订上线（跨实例投递是真通的）。
   今天新增的是**活的 `wire`**（现读两条连接的 `status`），界面分成两行而不是并成一句；
   "有没有同类偶发红"这一问也有了答案与门：有，而它现在读得出来（`dispose` 与"晚起来"两条见证给的是**反方向**的
   不一致，任何从另一格推导这一格的实现同时红一片）。另外先 grep 过：生产路径无人 `await bus.ready`，
   所以把它改成活的不会修好任何东西——这一句是"为什么不改闩"的决定性理由。
