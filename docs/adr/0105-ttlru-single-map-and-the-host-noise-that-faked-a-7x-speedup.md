# ADR-0105：TtlLru 合成一张 Map——以及一次差点被当成 7× 提速的宿主噪声

- 状态：accepted
- 日期：2026-11-12
- 版本片：v672
- 关联：ADR 0104（v671，摊还复杂度门 + 把双 Map 成本量出来却留白未改）、§46

## 背景：ADR 0104 量出一个"双 Map 税"，并把它诚实地留成了下一片

v671 给 `TtlLru` / `MemoryRateLimiter` 建了确定性复杂度门，量到 `TtlLru` 命中固定 **6 次** Map
操作、写入固定 **3 次**，容量 8 与 8192 完全相等。ADR 0104 同时记下一处"量了没改"的硬件契合留白：
`TtlLru` 把 `{value, expiresAt}` 拆进 `store: Map<K,V>` 与 `expiry: Map<K,number>` 两张表，于是

- 命中付 6 次哈希操作（两表各 `get` / `delete` / `set`），键**哈希两遍、存两份**；
- LRU 序要在两张表之间各自维护（命中时两边都 delete+set）；
- 更隐蔽的是 `get` 里 `this.expiry.get(key)` 后紧跟 `expiresAt!` 非空断言——它靠的是"两张表始终
  同键"这个**代码里没有任何结构保证**的不变量。任何一条路径若只删了一张表，命中就会把 undefined
  的过期时刻读成"永不过期"，缓存静默地不再过期。

合成一张 `Map<K, TtlEntry<V>>`（`TtlEntry` 已导出、形状现成）可把命中 6→3、写入 3→2，键只哈希/
存一份，LRU 序天然同源，并**从结构上消掉那个不变量**。ADR 0104 没有顺手改它，理由是"生产热路径
存储改动要有端到端回归余量"。v671 交付的契约门 4/4 + 语义门 8/8 + 39/39 回归，正是那份额外余量。

## 决定

1. **`TtlLru` 改为单 Map**：唯一一张 `store: Map<K, TtlEntry<V>>`，值条目 `{value, expiresAt}`
   绑在一起。逐条语义保持不变：命中 delete+set 刷到 LRU 尾部；读到过期删自身、返回 undefined、
   **不**刷新 LRU 序；写入不主动清扫；上界淘汰头部一条；`ttl=0` 仍表示永不过期（`Infinity`）；
   `stats` 各计数、`liveSize`（读不删）、`clear` 全部不变。公开 API（含已导出的 `TtlEntry`）一字未改，
   唯一生产调用方 `discoverRedis.ts` 的 `MemoryDiscoverCache` 只用 `new/set/get/clear/liveSize`，零回归。
2. **`set` 同键显式 `delete` 再 `set`**：`Map.set` 同键不会改变插入序位置，而旧版"先 delete 再 set"
   把覆盖当"最近碰过"刷到尾部。为保持这条 LRU 语义与命中一致，保留显式 delete（这次不是历史惯性，
   是注释里写清的语义选择）。
3. **把结构决策固化成门**（`ds-complexity-contract.test.ts` 新增 2 条）：
   - **单 Map 形状门**：在**未到上界**（留足 maxEntries 余量，隔离掉踢除那一次额外 delete）时，
     命中恰 **3** 次、写入恰 **2** 次哈希操作。改回双 Map 会回到 6/3 而红。
   - **源码静态门**：`ttlLru.ts` 只有一处 `new Map<`、用 `Map<K, TtlEntry<V>>`、无独立 `expiry` 表。
   这两条比 v671 的"常数上界"更紧，专门守住 ADR 0104 留下的结构收益与那个被消掉的不变量。
4. **变异臂加 M4**（`docs/evidence/ds/complexity-arms.mjs`）：内联双 Map 退化实现，实测命中 6 次，
   单 Map 门（要 3）判红，3/3 red as expected（M1 / M3 / M4）。

## 实测：一次被自己推翻的"7× 提速"

### 第一版证据（已弃用，如实记录推翻过程）

先用 v671 的 `scripts/ds-benchmark.mts` 跑改前 / 改后各一次（跨进程，`--json` 存档），差是：

| TtlLru 行 | 改前 ops/s | 改后 ops/s | 差 |
|---|---|---|---|
| hit cap=8 | 303101 | 2409900 | **+695%（≈8×）** |
| hit cap=8192 | 251852 | 1732909 | +588% |
| flood 256 | 410305 | 1124531 | +174% |

**这个数不可信，我没有把它写进收益结论。** 三处自证它不成立：
1. 哈希操作只**减半**（6→3），固定开销（计时、分支、GC）不变，物理上撑不起 8× 吞吐；
2. 改前 p99 **49us** 而改后 **1.4us**，量级差 35×——这是宿主争抢 / GC 特征，不是存储形状能改的；
3. 同一份改后代码连跑 3 次，ops/s 在 **1.69M / 2.57M / 2.88M** 之间跳（±40%），说明这台共享
   宿主（并行 lane、容器、GC）的墙钟**根本不稳定**，两次跨进程运行之间没有可比性。
   更早 v671 首轮同一行还是 483k ops/s——303k / 483k / 2.4M 的跨度全是噪声。

### 裁决证据：同进程交替 A/B（可信）

新增 `docs/evidence/ds/single-map-ab.mjs`：把**双 Map 旧实现**与**单 Map 新实现**逐字并排内联进
**同一进程**，**交替**跑 9 轮（每轮反转先后以抵消单向 JIT 热身偏置），判据取每轮分块 p50 的**中位数**，
不取被长尾污染的 ops/s。结果：

| 操作 | cap | 双 Map（旧） | 单 Map（新） | 比值 |
|---|---|---|---|---|
| hit | 8 | 0.286 us/op | 0.205 us/op | **1.39×** |
| hit | 8192 | 0.367 us/op | 0.252 us/op | **1.46×** |
| set | 8 | 0.397 us/op | 0.303 us/op | **1.31×** |
| set | 8192 | 14.473 us/op | 13.527 us/op | 1.07×（GC 长尾污染，不作数） |

**可信结论**：命中约 **1.4×**、小表写入约 **1.3×**——与"哈希操作减半但仍有固定开销"的物理预期一致。
写入 cap=8192 那档 14us/op 明显被淘汰路径的分配 / GC 长尾抬高，比值 1.07× 不解释为收益，如实标注。

**这一节的真正产物不是那个 1.4×，而是一条方法纪律**：在这台共享宿主上，跨进程的 before/after
墙钟对照会被噪声完全淹没（甚至伪造出 7×），**只有同进程交替 A/B + p50 中位数**能裁决一个常数因子
级的结构改动。原 `ds-benchmark.mts` 仍保留其用途——归档单次读数、看**相邻规模的比例**（用于抓
O(n) 塌缩那种数量级差异），不用于裁决 1.x× 的优化；这个分工写进 PERFORMANCE.md。

## 其余实测与回归

- **操作计数**：单 Map 后命中 **3**（旧 6）、写入 **2**（旧 3），容量 8 与 8192 仍完全相等；
  契约门 6/6 绿（含新单 Map 形状门 + 静态门）。
- **零回归**：`ttl-lru.test.ts` 8/8 语义门；全套 7 文件 **71/71**（契约 6 + 语义 8 + discover 三套 30
  + rateLimit / readout）。stderr 里的 cap-warn 与坏帧日志是既有门故意触发的，符合预期。
- **变异臂** 3/3 red as expected（见上）。
- 窄 tsc（ttlLru + discoverRedis + 两门 + 导入图）**exit 0**；eslint 改动文件 / 证据脚本各自
  足堆 **exit 0**（全项目 tsc/eslint 在本机 ~0.3GB 空闲仍 SIGTERM，资源不是红）。
- before / after 两次跨进程 JSON 存档在 `docs/evidence/ds/before-single-map-v672.json` /
  `after-single-map-v672.json`——**存档是为了让人看见噪声有多大**，收益裁决用上面的 A/B。

## 仍欠（如实记）

1. A/B 是**单宿主 9 轮**，没有固定 CI 机型上的多会话均值；1.4× 是这台 win32 / node 22 上的读数，
   不是跨机器 SLA。要跨机器可比需固定 runner + 多轮。
2. A/B 探针里双 Map 版 `set` 未逐字复刻旧版"同键覆盖刷 LRU 尾"的那一次额外 delete（两版 set 逻辑
   对称，比值仍反映存储形状差异）；**命中路径是逐字对应的**，因此命中的 1.4× 最可信，写入的 1.3×
   当作方向性证据。
3. `ttl=0`（Infinity）与负数 TTL 的边界沿用旧版行为，没有被本片的门新增覆盖（既有语义门测了 0）；
   负数 TTL 会得到过去时刻 → 立即过期，是既有的、未改的边界。
4. `TtlEntry<V>` 现在既是对外导出类型、又是内部存储值的形状；若将来需要给条目加字段（如命中计数），
   会同时改变对外导出的形状——那时宜另立内部类型，别让存储结构与公开契约长期共用一个 interface。
