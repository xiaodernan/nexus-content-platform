# 0006 — 设计目录的字符预算：条目可以裁，数不能裁

状态：已采纳（2026-09-24，任务 #31，§66-71 第一切片）

## 背景

§66 要求 Agent 每次都拿到同一批上下文（选中、页面、视口、设计系统、项目文件、资产、用户请求），
§68 禁止把整份文档/整个 repo 塞进模型，§70 要求有 Design Index。
看起来有了目录就同时满足这三条——**实测否掉了这个假设**：

| 形状 | 整份文档 | 目录（不套预算） | 目录/文档 |
|---|---|---|---|
| 起手页（8 节点） | 9,882 字符 | 7,047 | **71.3%** |
| 1,000 节点 | 765,284 | 59,238 | 7.7% |
| 10,000 节点 | 7,859,962 | **714,298** | 9.1% |

两个结论：目录在大项目上是 71 万字符，"索引过"根本不等于"塞得进上下文"；
而在小项目上目录几乎就是文档本身，因为 34 个 token 与全部跨引用边是按**项目**列的，不按节点数摊薄。
所以 §68 要落地，缺的不是索引而是**预算**——以及预算用完之后怎么交代。

麻烦的地方仍然是诚实（§159），不是裁剪本身：一份被裁过的目录如果长得和没裁的一样，
读的人就会把"没列出来"当成"项目里没有"。

## 选项

1. **只发摘要**（totals + 每页前 N 条）：小，但读者不知道少了什么，也没法核对。排除。
2. **按节点数截断**（每页保留前 N 个节点）：截出来的目录会切掉结构中间层，
   于是"这一页有没有某个框"变成不可判定——目录最值钱的就是结构可见性。排除。
3. **字符预算 + 固定优先级的裁剪顺序**：超预算就按顺序丢东西，
   每丢一类写一条 `trimmed` 说明，`totals` 永远来自**未裁**的那一份。

预算该由谁定，是同一个问题的两半：

- A. 写死在客户端：面板显示一个数，实际请求发另一个数——两处会漂。
- B. 服务端装配时算，`sizes.{fullDocumentChars, indexChars, budgetChars}` 随报文一起出去，
  面板只是把这三个数显示出来、并且允许人改一下重算（`?indexChars=`）。

## 决定

选 **3 + B**，`DEFAULT_INDEX_CHAR_BUDGET = 20_000`。

- 裁剪顺序（`fitIndexToBudget`，固定且写进注释）：
  ① 去掉节点的 `textPreview` → ② 按 token / asset / instance / interaction 顺序丢跨引用边 →
  ③ 结构框只留浅层 → ④ 截 `interactions` 列表。
  **`pages` 永不裁**：目录里连"有哪些页"都说不全，剩下的数字就没有归属了。
- `totals` 不重算：宁可少列条目，不少报数。面板因此可以同时显示"节点 8（可达 8）"与"边被丢了 24 条"。
- 压不到预算内就明说压不到：起手页压到 3,000 时目录是 5,473 字符，
  最后一条 `trimmed` 写的是「即便只剩骨架仍是 5433 字符：预算 3000 比这份项目的最小目录还小」。
  这一句是刻意的——它比"悄悄给一个 ≤ 预算的数"贵，但后者是假话。
- 20,000 这个数是**起点常数，不是从某家 provider 的 context window 推出来的**。
  取它的理由是可核对的分界：100 节点的项目（10,926 字符）整份目录原样出去，
  1,000 节点起必须裁。面板上预算可改、改完服务端重算，所以它不是只能信的数。
- 装配只读、不写库；§71 七个分支里没落地的写 `not-indexed` 加一句为什么，不拿空白冒充"已索引"。

## 后果

正面：
- §68 从一句口号变成面板上「目录 7,047 / 整份 9,882 字符（71.3%）」这样可核对、可手动改的读数。
- 面板与将来的 Agent 请求从同一份装配出发（`buildProjectContext` 一处），不会出现"面板显示的和发出去的不一样"。
- 裁剪是纯函数、有单测：同一份文档同一预算 → 字节相同的目录（决定了 AI 请求的缓存与前缀稳定性）。

代价与已付的账：
- **20,000 迟早要重算**：接真 provider 时预算应由 provider 层给（各家窗口 − 其余部分要留的余量），
  而不是由面板的默认值给。届时 `maxIndexChars` 的调用点从路由换成 provider 适配层，契约不用改。
- **骨架下限由 token 表与边表决定**（这份项目约 5.4K 字符）。要再小就得连 token 目录也裁，
  而那正好砍掉 lint/健康度依赖的"哪些 token 被用、哪些只被引用没声明"视图——目前不做，
  因为那半张表就是 §70 目录的主要价值。小项目占比高（71.3%）因此是**如实读数**，不是 bug。
- **`CommandBar` 仍在发整份文档**：这一片只把"该发什么"算出来并显示出来。
  替换请求体是下一片，且必须与确定性 mock 一起改——mock 现在靠 `context.document` 认结构性配方，
  只发目录就会让那些配方静默失败，那是行为变更，不是顺手能改的细节。
- 过程记录（值得留在文档里，因为集成测试没拦住它）：路由第一版从 `ctx.searchParams` 读预算，
  而 Next 16 的 route handler **不提供**这个字段，于是 `?indexChars=300` 被静默忽略、
  服务端按默认预算返回 200。直接调 `buildProjectContext` 传 options 的集成测试测不到这一层，
  只有走 HTTP 的 smoke 测出"预算改了但目录没变"。
  修法是 `new URL(req.url).searchParams`，与 `memories` / `retrieve` 两条既有路由一致。
