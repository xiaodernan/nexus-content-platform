# 0028 — 跨实例实时扇出走 Redis pub/sub，单线路复合物理总线

日期：2026-10-05 ｜ 关联：§163 实时通道、§164 通知、ADR-0010（SSE 而非 WS）、ADR-0025 第六件（注销后不再向他推任何东西）

## 背景

`realtime/bus.ts` 从第一天就把总线做成了接口（`publish` / `subscribe` / `closeChannel` /
`subscriberCount`），生产者只认门面，所以接第二驱动不该动任何调用方——§163 那格因此一直标 `[~]`，
欠的是**跨实例**与**补发**两件事，不再是生产者。

今天只有进程内驱动（`MemoryRealtimeBus`）。它的两个洞都是部署规模带来的：

1. **多实例收不到别机的事件**。用户 A 挂在实例 1 的 SSE 上，实例 2 上的 AI 作业给他发通知，
   事件落在实例 2 的空总线里，A 永远看不见。数据库写成功了，界面不亮——按 §163 的口径这不算坏
   （权威在库里，刷新就有），但"实时"两个字就是假的。
2. **ADR-0025 第六件只在一个进程里成立**。注销账号时 `closeChannel` 摘掉的是**本进程**那份订阅；
   另外三台实例上那个人的 SSE 还在收事件。0025 的实现记录里已经把这格写成了显式约束：
   "换成 Redis 驱动做多实例扇出时这一格必须照样做得到，否则第六件只在一个进程里成立。"

要定的事：线路怎么组织（一频道还是多频道）、要不要顺带做补发、驱动怎么被选中、
以及"业务不能被 Redis 拖住"这条纪律在连接参数上怎么落。

## 选项

1. **单条 Redis 频道 + 复合物理总线**（选这个）。所有帧都发到
   `nexus:realtime:v1` 一个线路上，每帧自带目标逻辑频道；本机那一半边仍旧交给
   `MemoryRealtimeBus` 实例，Redis 只补跨进程的那一半。
2. **每个逻辑频道一条 Redis 频道**（否决）。看起来更"原生"，代价是三处变差：
   - 订阅关系得跟着 Studio 的连接动态 `SUBSCRIBE`/`UNSUBSCRIBE`，一条 SSE 一次来回，
     而项目频道数量随用户开的项目数长；
   - `closeChannel` 要在这个进程里知道"哪些 Redis 频道订过"，还得 `PUNSUBSCRIBE` 清干净，
     状态从一张 Map 变成两处要对账；
   - 坏帧的来源更难归属（频道名本身就是信息）。
   单线路把这些都收在一个 `on('message')` 里，逻辑频道的分发留在本来就为此而生的那张 Map。
3. **Redis Streams + 消费者组做补发**（否决，本片不做）。补发要的是"断线的连接回来能补齐
   错过的刻度"，那需要每用户/每项目的流、裁剪策略与消费位点——是另一格（§163 欠的第二件）。
   现在用 Stream 假装做扇出，等于为还不要的语义先背上流管理。**这一片明确不补发**：
   帧丢了就丢了，权威状态在库里，界面的兜底是刷新与 SSE 首帧的重读。
4. **加一层 WS 广播（或让 Nginx 做 sticky + 内部广播）**（否决）。传输层 ADR-0010 已经裁决过
   SSE；跨实例这件事不需要新传输，需要的是把事件送到"别的进程里那些已经开着的 SSE"。
5. **默认就打开 Redis**（否决）。本机开发、vitest、e2e 都只有一个 web 进程，
   在那里 Redis 不是被测功能而是多余依赖，而且 16GB 内存本机空闲仅 ~2.5GB（见 `docs/ENVIRONMENT.md`），
   多一条常驻连接与另一套失败模式不值得。改成 **`NEXUS_REDIS_URL` 非空才装**，
   并且建单例那一刻把装的是哪个驱动打进日志——opt-in 的开关必须有可观测的装载点，
   否则"设了但没生效"与"生效了但没人说"分不清。

## 决定

- **线路**：一条 Redis 频道 `nexus:realtime:v1`，版本段写在名字里（换帧格式时旧实例的帧会因
  契约校验失败被记下来，而不是被误读）。
- **报文**：`packages/schemas` 里新增 `RealtimeWireFrameSchema`（`kind:'event'` 带 `channel`/`event`，
  `kind:'close'` 带 `channel`，两者都带 `origin`）。接收侧**必须先 `safeParse` 再落到本机订阅者**：
  线路上的字节和浏览器发来的一样是不可信输入，"是我们自己发的"不是免检理由。
  它是第二份定义、只走 web↔web，因此**不进 `CONTRACT_EXPORTS`**（与 `AgentRosterSchema` 同一个理由：
  塞进去会让导出的 ai-request 契约里多出根本不属于 provider 的东西）。
- **两条连接不是一条**：Redis 的订阅连接进了 subscriber 模式就不能再发普通命令，而 `publish`
  与 `closeChannel` 正是要发命令的那一侧。
- **两侧的连接参数不对称**（这一条是打真 Redis 跑出来的，见后果第 5 点）：
  发布侧 `enableOfflineQueue:false` + `maxRetriesPerRequest:1`（**业务不等线路**，断开就当场失败、
  只记账）；订阅侧 `enableOfflineQueue:true` + `maxRetriesPerRequest:null`（这里等的不是某个请求，
  是这条总线自己的初始化，Redis 十分钟后才起来也应该订上）。重连策略用 ioredis 默认值，
  已登记订阅的自动重建交给连接层。
- **`publish` 永不抛**（从 `bus.ts` 抄过来的纪律）：本机那一半边先送到，不依赖 Redis；
  线路失败只让 `wireErrorCount` 与一行 stderr 动一下。没有这个数，一次断线只会变成一行日志，
  跑测试的人看不见"到底丢了几帧"。
- **`closeChannel` 跨进程**：本机立刻关，另外往线路发一帧 `close`，别的实例各自关自己那份。
  这一帧不重试、不补发：关不上就关掉，那个人的下一次请求会因为没会话而失败——
  0025 说的是"不再向他推"，不是"保证某一帧一定送到"。
- **`subscriberCount` 只数本进程**。pub/sub 查不到远端有谁在订，所以这个数的用途是
  "这台机器上有没有人在听"，不是全平台人数；界面与诊断不要拿它做多实例健康判断。
- **`origin` 去重**：每台总线一个身份（`pid:启动时刻:序号`），自己发的那一帧回环到自己时跳过。
  前提是**进程级单例**（`getRealtimeBus` 挂在 `globalThis` 上，dev 下每条路由可能各自拿到一份模块图）；
  如果哪天有人绕过单例自己 new 一份，同进程就会出现两个 origin，去重仍然成立但连接会翻倍。
- **`ready`**：`Promise<boolean>`，回答"这台总线的跨实例那一半边接上线了没有"（订阅在服务器
  登记成功 **且** 发布连接真的 ready，不是"命令发出去了"）。永不 reject，落定一次不再变。
  发布侧连不上时立刻答 `false`，不去等那条按设计会一直排队的订阅——否则 Redis 宕机时
  `ready` 永不落定，await 它的人只能等到超时。
- **`dispose()` 只在具体类上**，接口不加：生产者的生命周期不归总线门面管。用 `disconnect()`
  不用 `quit()`——本机主动收摊不需要跟对面道别，而 `quit()` 在从未连上的连接上会吊住收尾。

## 后果

1. 多实例部署现在是真的：设 `NEXUS_REDIS_URL` 即扇出，生产者、SSE 路由、通知链一行没改
   （这正是当初把总线做成接口的回报）。
2. 事件仍**不补发**，所以 §163 那一格剩下的欠账只剩这一件，性质从"缺功能"变成"明确的语义选择"：
   断线期间跨实例的事件收不到，界靠刷新与 SSE 首帧重读兜住。要补发得另立 ADR 选 Stream。
3. web 多了一个运行时依赖 `ioredis ^6.0.0`（声明在 `apps/web/package.json`）。默认驱动不连它——
   但 `bus.ts` 静态 import 了 `redisBus.ts`，所以每个用到总线的服务端路由都会**加载** ioredis 模块
   （不建连接）。这些路由全在服务端，不进浏览器包，客户端不受影响。
4. `wireErrorCount` 与 `ready` 是新驱动上的可观测点；进程内驱动没有这两个东西（它没有线路）。
   诊断入口将来要说"哪个驱动 + 掉了几帧"，形状已经有了。
5. **测试把实现改对了一次**（值得留在记录里，因为它证明的是"为什么这条必须打真 Redis"）：
   第一版给两条连接用了同一份 `enableOfflineQueue:false` 参数，`SUBSCRIBE` 是在连接建立之前
   发出的，队列一关它就当场失败——于是这台总线永远订不上线路，跨实例那半边静默地一条都不送。
   四条投递用例在真 Redis 上全红；而本机那一半边始终是对的，所以任何单元测试都发现不了它。
   第二版又踩了一次：断言之前的"发一帧直到收到"式 warm-up，自己漏出去的帧在断言开始后才到达，
   把"收到 1 条"变成"收到 2 条"。`ready` 就是为了让这类等待不再靠猜时间的做法。
6. 线路故障变成一种**看得见但不致命**的状态：日志、计数、`ready=false` 三个出口都有，
   业务请求不会被 Redis 拖住，也不会悄悄丢帧而无人知道。
7. Redis 成了"看没看到"的依赖，不是"对不对"的依赖：它是加速器，权威状态永远在库里（§16/ADR-0010 那条）。
   因此 Redis 挂掉时多实例部署退化成"各自只看得见本机事件"，这正是 0028 之前的行为，
   不会把已经写进库的东西弄坏。

## 验证（落点与实测）

- `apps/web/test/realtime.redis.integration.test.ts`（真 Redis，两条独立总线 + 一条绕过总线
  直接往线路上发字节的原生连接）：
  1. 别机的订阅者收到，**自己这台只收到一次**——`seenAlpha` 停在 1 就是 origin 去重的见证；
     去掉那一刀这里会是 2，Studio 上同一个进度条动两次。
  2. `closeChannel` 跨实例：关门在**另一台**上直接可见（`beta.subscriberCount(gone) === 0`），
     不是"没收到"那种反证；关门这条频道先有一条真的送到过，之后那条才没到；别的频道照旧收得到。
  3. 线路上的帧先过契约：合法帧落到本机订阅者（对照），两种坏法（非 JSON 的字节、
     `event` 少必填字段的帧）只让 `wireErrorCount += 2`，本机订阅者一条都没多收。
  4. 自己的 `origin` 不处理：带自己身份的帧与带别人身份的帧连着发，到的那一条是别人的。
  5. 端点连不上：`publish` / `closeChannel` 都不抛，本机订阅者照样立刻拿到，
     `wireErrorCount > 0`，且 `ready` 落定为 `false`（不是吊死）。
  6. 驱动选择：未设 / 全空格 → `MemoryRealtimeBus`；非空 URL → `RedisRealtimeBus`，且单例同一份。
- 本机跑法（Redis 由 `infra/docker-compose.yml` 的 `nexus-redis` 提供，端口 56379）：
  `npx vitest run apps/web/test/realtime.redis.integration.test.ts`。实测 6 例全绿（tests 972ms）。
- **两个真实操作系统进程**的那一寸由 `npm run realtime:two-process` 补上（`scripts/realtime-two-process.mts`）：
  上面那两条总线共享一个进程、一个 globalThis、同一份模块图，所以它们证明的是线路与帧，
  证明不了生产路径上那台单例会在两个进程里各自选到 Redis 驱动。这条脚本 spawn 一个长命监听进程、
  再用四次独立 spawn 发事件与关门（实测 5 个进程、4 次往返、八条判据全 PASS），
  关门生效拿的是监听进程自己报出的订阅人数 1→0，"关门后没收到"另配一条"别的频道收到了"作对照。
- **变异探针**：7 条臂逐条改掉这一片的一句纪律（回环摘除、关门广播、坏帧校验、本机半边先送、
  `publish` 不抛、驱动选择的那次读空、订阅侧的重连参数），预测哪些用例该红就跑一遍——
  7/7 与预测一致，还原后控制跑仍绿。第一条臂（去掉 origin 那一刀）在单实例里是看不见的，
  它红的正是 `seenAlpha` 停在 1 那一句。

## 欠账

- **补发**（§163 那格剩下的唯一一件）：断线期间的跨实例事件收不到，界靠刷新与 SSE 首帧重读兜住。
- **真跨机部署**没验过：今天的两进程见证走的是同一台机器的同一条 Redis。跨机多出来的那一寸
  不是"能不能送到"（线路名与帧格式都一样）而是延迟、防火墙与多机房路由，那些不在这一片的判据里。
- **没有裁决入口**：`wireErrorCount` 与 `ready` 现在只在 stderr 与测试里，界面上看不到"这台实例掉了几帧"。
