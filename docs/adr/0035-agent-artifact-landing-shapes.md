# ADR-0035：Agent 产物的两种落地形状——审批门补丁，与显式「接受」整份文档

- 状态：已采纳（§52 第一片：Game Agent 的 RPG 原型草稿）
- 日期：2026-10-11
- 关联：§52、§112、§74、§149、§150、§16、§159、ADR-0020（编排只读）、ADR-0012（审批 holds 住审阅过的那一版）、ADR-0033（自动保存发 patch 不发整份）

## 背景

§52 的原话是「Game Agent 生成游戏草稿」。ADR-0020 落下的第一片是**四步只读**编排，
它的卖点恰恰是"这一轮什么都不改"。现在往同一份配方里加一步会产出东西的步骤，
就必须回答两个此前没人回答过的问题：

1. **产物住在哪儿**——如果只在步骤结论里写一句"我给你设计了 8 个实体的 RPG"，
   那不叫产物，叫描述（§159 禁止的就是这种"计划里有、东西不存在"）。
2. **谁有权把它变成项目里的真值**——`games` 表里那一份是用户正在 Game Studio 编辑的东西。

平台里已经有一份"AI 的东西怎么落地"的先例：§74 的审批门。它的形状是
**补丁挂在任务行上等审批，批准时执行的就是那一份补丁**（ADR-0012）。
问题是补丁这个形状只适合设计模型那种"节点/属性逐个改"的对象；
§54 的游戏文档从建库起就是**整份 JSON 存取**（一项目一份，引用完整性只有拿到整份才验得出来）。
把一份新写的草稿包装成"补丁"，是为了复用门而伪造语义。

## 选项

1. **接进 §74 的审批门**。一致，但审批门执行的是一条 patch 事务，而这里根本没有 patch；
   硬做要在 `approvals` 旁边开一种"批准 = 整份换掉"的第二语义，那道门以后就说不清
   自己审的是哪一种东西。
2. **执行器直接写库**（跑完那一步就把草稿存进 `games`）。
   一次就破两条线：ADR-0020 的"只读"承诺变成假话，以及 §149 的"一次 AI 操作 = 一个可撤销事务"——
   这一步没有撤销凭证，也没有人点过头。最实际的伤害是：编排会在用户没要求的时候
   盖掉他正在编辑的那份设计。
3. **本决定**：**产物留在任务行里，落地由用户点那一下显式的「接受」发生，且只许创建、不许覆盖。**

## 决定

- **草稿存在任务行**：`agent_tasks.result.steps[].draft`，形状直接用 `GameDocumentSchema`
  （`StepReportSchema.draft` 是 optional）。于是刷新之后还在、别的实例也读得到，
  接受入口才有东西可接——组件状态不算"存在"。
- **落地入口只收 `{ taskId }`**：`POST /api/projects/<id>/agent/draft`。
  那份游戏文档由服务端从任务行**读出来**，不从请求体收。
  为什么：收整份文档的入口就是"谁都能把任意一份设计贴进项目"的入口，
  而这一片唯一的主张是"接受的是这一步真跑出来的那一份"。与 §68「服务端派生、不信客户端给的摘要」同一条线。
- **create-only**：项目里已有游戏文档时**拒绝**（409 `accept_refused`）。
  接受是"多给一份东西"，不是"顶掉你正在编辑的那份"——冲掉用户作品只要发生一次，
  之后界面上所有「接受」按钮都没人敢点。
- **拒绝的判断排在 stale 写检测之前**（`saveGame` 里 `createOnly` 那条在 `updatedAt` 比较上方）。
  草稿的时间戳天然是它跑出来的那一刻，拿它去比一份被用户改过的设计，
  只会得到"这次写入是旧版本所以被拒"这种误导的原因——真正的原因是**这里已经有东西了**。
- **拒绝要说什么**：点名已有那一份（它的项目内名字），并给出真出路
  （"要换掉请先在 Game Studio 里删掉或改那一份"）。只说"已存在"是把决定推回给用户猜。
- **接受之后没有第二套语义**：进了项目就是普通的 Game Studio 文档，撤销走 §150 那套 Command。
  这一格因此不记 §149 的事务，回执那句话也照实这么写，不假装"撤销这次生成"。
- **四种问法各有自己的答案**：CSRF 前不碰库 / `not_found`（别人的任务、不存在的任务、
  挂在别的项目上的任务给同一个 404——那一行存着提示词摘要与草稿，"存在但不给你"本身就是信息）/
  `draft_missing`(409) / `accept_refused`(409) / `rate_limited`(429)。
- **两类结局都进审计**：放行时 `targetType: 'game'`、`targetId` 是那份文档的 id、`allowed: true`；
  拒绝时 `targetType: 'agent_task'`、`allowed: false` + `detail.reason`。

## 怎么被钉住的

- 纯层 19 条（`agent-game-draft.test.ts`）：配方不等于理解、同一份输入两次逐字段相同、
  id 只从 seed 派生、草稿真能跑、经验跨得过等级门。
- 集成 7 条（`agent-draft-accept.integration.test.ts`）：上面那四种问法逐条对号、
  只认 `taskId`、不覆盖且**库里那列 JSONB 字节相同**、放行审计按本次那份文档的 id 查得到一条。
- `games.integration.test.ts` 的 createOnly 五道里有**两条对照**：
  ① 同一份草稿不带 `createOnly` 就写得进去（证明拒绝来自这道门而不是文档本身不合契约）；
  ② 项目里那份是 2020 年存的、草稿是刚刚跑的（证明挡着覆盖的**只有**这道门——
  另一种排布下"更旧的写"守卫会顺手替它挡下，那条臂就只红在措辞上，见下面的"洞"）。
- 编排 5 步全绿 + 草稿落在任务行 + `countGames === 0`（"跑完还是只读"这条承诺是可测的）。
- e2e `@smoke`：跑 → **reload** 后接受入口还在 → 点接受写库 → 游戏面板读得到同一份 →
  再点被拒且库不变（截图 `agent-accept.png` / `agent-accept-refused.png`）。
  步数断言从服务端计划里读，不写死数字（配方加一步会让写死的断言假绿）。
- 七条变异臂的读数写在 `docs/TESTING.md` 这一天的记录里。其中一条**先跑出一个洞**：
  只摘掉 `createOnly` 时，两处 fixture 里"用户那份"的时间戳都比草稿新，于是"更旧的写"
  那道守卫顺手也挡住了覆盖——门没了却什么都没发生，红的全是措辞断言。
  这说明"拒绝"这条主张在当时的用例里根本没有独证（sole witness）。
  补上"旧设计 + 新草稿"那一格之后（域层与路由层各一条），摘门才红出**真覆盖**：
  库里那份被盖掉、路由回了 200。这条决定真正防的是那种情形，测试从此防的是同一件事。

## 后果

- 好的一面：ADR-0020 那句"只读"没有因为加了一步产出物而变成谎话——它可以被 `countGames === 0`
  一句话证明；§52 那一步有真产物；用户点头之后产物才落地，落地之后可撤销；
  已有设计永不被静默覆盖。
- 代价：一份草稿只能接受一次。接受过之后项目里就有了游戏文档，再点同一份草稿必然 409。
  今天不做"另存为第二份"，因为 §54 的存储形状是一项目一份（要做的是那个前提，不是这里的入口）。
- 未决：§52 说的 Game Design → Combat → Level → … → Code 那条链仍然没有——
  这一步只到"编出一份可玩的 RPG 原型草稿并让它有地方去"，不改设计模型的其他部分，也不生成代码。
- 顺带修掉的错账：268bd8d 的 commit message 写的是「ADR-0034」，而 0034 是另一件事
  （世界地形圆台，2026-10-10 另一片）。代码注释与 ROADMAP 现在指向本文（0035）；
  commit message 改不了（已进历史），所以把这条错账记在这里而不是假装它不存在。
