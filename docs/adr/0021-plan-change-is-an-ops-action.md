# ADR-0021：改档位是一个运营动作，不是购买流程；它允许改自己

日期：2026-09-30 · 状态：已采纳 · 关联：§133、§134、§159、§80、§84、ADR-0014、ADR-0019

## 背景

ADR-0014 定下"档位只有一条轴（`users.plan`）真正咬合，额度与上限都由它派生"，并在后果里留了一句：
**"改档位没有界面：`UPDATE users SET plan` 是服务端代码里的事。"**

§133/§134 要求的是消费透明与订阅档位，`PLAN_LIMITS` / `PLAN_MONTHLY_GRANTS` 也已经按五档写好了。
缺的不是规则，是**一个能改档位的入口**——没有它，`pro` 那一档的上限在代码里存在、
在产品上却只对"运维记得去改库"的那几个账号存在。

同时这个入口天生危险：它发的是**额度**，而额度直接换钱（扣点、存储上限）。
所以这一片要先把"它是谁在什么情况下用的"说清楚，再谈按钮长什么样。

## 选项

1. **不做入口**，继续让运维改库。ADR-0014 的原状，成本为零，但档位在产品上等于不可达。
2. **做成购买流程**：界面上"升级到 Pro"、标价、接支付。
3. **做成运营兜底入口**：只有 `admin` 能改，界面上写清"这是运营动作、不是购买"，
   允许 admin 改自己的档位，每次尝试（成功 / 被拒 / 同档位重复提交）都进审计。
4. 与"改角色"合成一个端点，用带判别式的报文区分两件事。

## 决定

选 **3**。四条配套约束：

- **与改角色分成两个端点**（否掉选项 4）。两件事要分开的是两样东西：审计动作名
  （`user.role.change` / `user.plan.change`）与限流桶的键。共用一个键会出现
  "改了三次档位就被挡在角色操作之外"这种解释不清的现象——而解释不清的限流比没有限流更糟。
- **允许 admin 改自己的档位**，这与"不能改自己的角色"**刻意相反**。理由不是"反正拦不住"——
  admin 本来就有全部权力——而是两件事的性质不同：
  **改角色是授予权限**（自己提权 = 拿到这个会话的人就能变成审核员，所以那条路必须堵死），
  **改档位是发放额度**。拒绝自己改，会让"本机只有一个账号"的开发环境根本用不了这个入口，
  而它挡不住任何真实的滥用（能直接改库的人不需要走这个入口）。
- **先判权限，再判报文**。顺序反过来的话，一次越权尝试如果随手带了个错档位，
  审计里会记成 `unknown_plan` 而不是 `not_admin`——把"有人越权"读成"有人拼错了参数"。
- **没有支付**（§159）。界面上不许出现"升级"这类词，也不许标价：账面上今天没有任何一分钱流进来，
  写一个价格就是把不存在的东西说成存在。这一格是运营兜底，购买流程是另一件事（§134 的未做部分）。

## 后果

- 好处：档位从"只能改库"变成一个有判定、有审计、有界面的动作；`pro` 那一档的上限第一次可达。
  审计里同时记下这一档当时的**额度与存储上限**，事后读审计的人不必再去翻那一天的代码。
- 好处（安全侧）：被拒的尝试、以及**同档位重复提交**都落一行。后者读起来是个独立信号——
  前端会挡住"选了同一档"这条路，所以走到服务端的同档位请求要么是脚本，要么是页面 bug。
- 代价：它**不是**购买流程，所以今天"用户想自己升级"这件事在产品上仍然不存在。
  这一格刻意只服务运营，不假装成自助订阅；把两者混起来会同时骗用户和骗账。
- 代价：`plan` 的取值校验在两层（域层给得出人话的拒法，库里 `users.plan` 的 CHECK 是最后一道墙）。
  两层都要留着——只有库那层，用户看到的是 500。
