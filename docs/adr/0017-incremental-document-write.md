# ADR-0017：文档写入改成增量，但语义仍是「整份文档替换」

状态：采纳（2026-09-28）
关联：任务 #62（§147 的写放大）、`docs/adr/0016-project-writes-serialized-by-xact-lock.md`、
`apps/web/src/server/domain/projects.ts`、`apps/web/test/document-incremental-save.integration.test.ts`

## 背景

ADR-0016 用事务级 advisory lock 解决了「同一项目的并发保存互相踩」，但同一件事的另一半还挂着：
**一次保存要把整份文档重写一遍**。`writeDocument` 的做法是「删掉本项目全部 pages / design_nodes /
design_tokens / components，再按文档逐行插回去」，于是改一个字的代价和改一千个节点一样：
10,000 节点档在 `docs/PERFORMANCE.md` 口径 `prod-adr0015` 里是 583–763ms（属性写入那一行），
今天在同一台机器上量 4000 节点，HEAD 版本是 782.3ms（5 遍中位）。

Studio 是自动保存的，所以这不是「慢一点」，而是每次编辑都付一次全量写。

## 选项

- **A. 客户端发补丁**（§150 的 Command 已经在客户端存在，客户端知道改了哪几个节点）。
  语义上最省，但 PUT 的报文契约、`packages/schemas`、AI/Agent 两条写入路径都要跟着改——那是单独一片。
- **B. 服务端读回当前行、算出差异、只写变化的行**（本 ADR 采纳）。API 契约不动。
- **C. 只增改、不删**（接手这一片时工作区里那版就是这样，并且把并发用例的断言改成了「合并语义」）。
  它看着更像合并，实际会让删除静默失效：删掉一个节点再保存，读回来它还在——设计模型与库从此漂移（§16）。否。
- **D. 继续整删重插**。10,000 档的属性写入超标 12–15 倍，而且写放大随文档大小线性涨。否。

## 决定

`writeDocument` 保持唯一入口（`createProject` / `saveDocument` 都走它），语义不变，实现改成增量：

1. **语义不变**：客户端每次发的都是完整文档，文档里没有的节点就是被删掉的——缺失即删；
   最后完成的那个事务整体胜出（锁还在原来的位置，ADR-0016 的结论不受影响）。
2. **节点差异交给 Postgres 比**：jsonb 的相等本身就是键序无关的，于是把要写的那几行打包成一个 jsonb 参数，
   用 `jsonb_array_elements` + join 差出「内容或所在页变了」的那几个 id；JS 只把 `id + page_id` 读回来判增删。
   为什么不把全部行读回 JS 逐字段比：4000 节点实测「读回 957.6ms + 比对 468.3ms」，
   而「只读 id 10–12ms + 库里差集 161.5–264.8ms」（整张读数表在 `docs/PERFORMANCE.md`）。
3. **删除按主键**：`delete ... where page_id = ? and id in (...)`。单独按 id 删用不上 `(page_id, id)` 主键，
   会全表扫描——本机测试库积到十万行时，并发用例从 1.9s 涨到 12.3s。
4. **令牌 / 页面 / 组件**行数少（几十行），保持原来的 JS 侧比对（`diffByKey` + `stableKey`）。

## 后果

- 4000 节点、改一个节点后保存：**196.8–225.5ms（两遍中位）vs 782.3ms（HEAD）**；
  无改动保存 198.1–202.5ms vs 797.0ms。写 1 行而不是 4000 行，写放大那一半到此关掉。
- **没有达标的**：`docs/TESTING.md` 那条「属性写入 <50ms」仍然红。剩下的代价不是「写多少行」，
  而是「每次保存都要把整份文档过一遍」：客户端发全量（3.5MB @4000 节点）→ 服务端序列化成 jsonb 参数
  → 库解析比对（约 180ms）；另外 `saveDocument` 之后的 §49 语料同步仍是全量重切（146.5ms @4000）。
  要再往下走只有选项 A（发补丁）。10000 档这一版今天没量到（HEAD 是 1434ms），下次补。
- 新增两条被钉住的边界，各有用例：
  - 删掉的节点必须真的从库里消失（「只增改不删」会让删除静默失效）；
  - 同一份文档里「删掉一页 + 把该页的节点搬到别的页」必须先把被删页面的行排除出「库里已有」的集合，
    否则那个节点既不插也不改地消失（旧行被级联删掉，换页的 UPDATE 又匹配不到新页）。
- 代价与限度：一次保存的**读**变便宜了，但**比较**仍要过一遍文档，节点越多那个 jsonb 参数越大；
  多实例部署不受影响（差异是在库里算的，写仍然由 advisory lock 串行）。
