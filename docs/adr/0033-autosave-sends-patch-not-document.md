# ADR-0033：自动保存发补丁，不发整份文档（#62②）

- 状态：已接受（2026-10-09）
- 关联：ADR-0016（写入串行化）、ADR-0017（增量保存的写放大那一半）、§150（Command 客户端栈）、§68（AI 上下文按库装配）、ADR-0011（读时收敛同口径）

## 背景

Studio 的自动保存（`store.save()`，1.8s 防抖）一直是整份 PUT：`PUT /api/projects/<id>`
发的是**整份 DesignDocument**（4000 节点 ≈ 3.37MB，10000 节点 ≈ 8.42MB），服务端
`parseDocument` 做全文档形状门，再走 `saveDocument` 的增量写入。ADR-0017 把**写放大**
关掉了（2026-09-28 量：改一个节点 782.3 → 196.8ms @4000；2026-10-09 补测 @10000：
1433.9 → 477.6ms），但**报文**这一格没动：每次保存仍然把整份文档序列化、上传、
再解析一遍。`docs/TESTING.md` 的「属性写入 → 画布更新 <50ms」这一门因此一直红
（@10000 生产构建量过 583–763ms）。

§150 的 Command 栈在客户端早已存在，且 `execute` 当下就产出可序列化的
`HistoryEntry { applied, inverse }` —— 也就是说"只发增量"的报文**本来就有**，
差的是一条服务端应用路径。

## 决定的取舍

**新增 `PATCH /api/projects/[id]/design`，客户端自动保存优先发 Command 补丁列表（ops），
全量 PUT 退居兜底。** 具体：

1. **报文是补丁列表而不是单个补丁**：`{ patches: DesignPatch[] }` 按时间序
   （一条命令一个补丁）。撤销发逆补丁（`entry.inverse`），与手工编辑、AI 事务
   共用同一个待发队列——服务端看到的动词词汇完全一致。
2. **服务端在锁内读-改-写**：`patchProjectDocument` = `lockProjectWrites` →
   `loadDocument(tx)` → 逐条 `applyPatch` → `parseDocument` 规模/形状门 →
   `writeProjectDocument`。与 §188 公开 API 的补丁（`apiPatchDesign`）同一形状，
   但那一条的落库因审批门可以拒；这一条是作者自己的编辑器，没有审批门。
3. **整批同生共死**：任何一条 op 打空（`skipped`）→ 整批一条不写，409 `ops_skipped`；
   打完补丁的文档过不了门 → 400 `document_rejected`。两种都**没有半截写**（§159），
   客户端拿到就换全量 PUT 再试一次（见"后果"）。
4. **合并语义 vs 替换语义的分工**：补丁只增改，库里没被 op 提到的行一个字不动；
   全量 PUT 的"缺失即删"原样保留（`document-incremental-save.integration.test.ts`
   最后一节把两者的对照钉在案）。删一个节点仍然走 `remove` op（或撤销），
   不靠"少发一个节点"。
5. **`forceFullSave` 显式逃生门**：`setMode` / `setPage` / `jumpTo` / 快照恢复这类
   "补丁词汇表表达不了的整份文档改动"显式要求下一次保存整份 PUT，不猜。
6. **语料同步与全量同一条纪律**：`syncDesignKnowledge` 在事务外、按打完补丁的整份
   文档重切（ADR-0017 同口径；放事务里写会与被回滚的文档漂移）。

## 记录下来的数（2026-10-09，同一台机器）

服务端进程内（`scripts/perf-save.mts`，每项 5 次中位/最小）：

| 场景 | 全量 PUT | 补丁路径 |
|---|---|---|
| 4000 节点，改一个节点 | 190.7 / 182.0ms | **356.2 / 342.0ms** |
| 10000 节点，改一个节点 | 450.5 / 439.6ms | **799.6 / 713.1ms** |

**补丁路径服务端更慢**，慢在 `loadDocument`（锁内读回整份文档才能打 ops）
加上 `parseDocument` 的全量门——这是明账：客户端省下的（3.4/8.4MB 的主线程
`JSON.stringify`、同样字节的上行网路）全部记在浏览器与网路一侧，服务端多付
一次读。1.8s 防抖的自动保存本来就不在乎这一次往返。

浏览器端（`scripts/perf-browser.mts`，口径 `dev-patch-20261009`，每项 3 次去掉第一遍）：

| 属性写入 → 画布更新 | 起手 8 | 1000 | 4000 | 10000 |
|---|---|---|---|---|
| 2026-09-29 dev-repro | 37.7ms | 117.8ms | — | — |
| 2026-10-09（本 ADR 落地后） | 21.2ms | **42.8ms** | 73.2ms | 181.9ms |

100 / 1000 / 10000 三档里 **1000 档进了 <50ms 的门**；10000 档比生产构建那次
（prod-adr0015 583–763ms）好 3–4 倍，但 dev 口径下仍红。**不做因果归因**：
两次读数之间隔着多片改动（选中响应的 memo 修正在本片之前），本 ADR 只声明
"补丁路径落地 + 这一档现在达标"，不声明"达标全部由补丁路径带来"。

## 后果

- 好的一面：自动保存的上行字节与主线程序列化从"整份文档"变成"攒下的 ops"；
  卸掉保存途中的长任务（浏览器探针的读段里长任务 0）；`writes` 网络顺序里
  落库的动词从 PUT 变成 PATCH（@smoke AI command bar 那条测试的顺序断言随之改成"落库"）。
- 代价：服务端每次多一次 `loadDocument`（见上表）；客户端 `save()` 的复杂度
  （待发队列、editSeq、409 兜底）从"发一份"变成"发一批、失败要放回队头"。
- 409/400 兜底换全量 PUT 是**刻意的不对称**：补丁被门挡下时，全量发的是同一个人的
  同一份内存状态，是换一条路而不是把用户卡在 error 上；但它同时意味着
  "补丁永远可达"这件事没有测试兜底——兜底路本身有 e2e@smoke 的 AI 落库顺序压着。
- 未决：服务端仍会把整份文档读回内存打 ops。真要再下一个数量级，只有
  "按 touchedNodeIds 定向读写行"的新写入者（不再 COW 整份文档），那是独立一片。
