# 0012 — 批准交回的是被扣下的那一版，不是重新生成的一版

日期：2026-09-26 ｜ 关联：§74 人工审批、§149 一次 AI 操作 = 一个可撤销事务、§150 Command、§162 异步作业、ADR-0011

## 背景

§74 要求"删除、对外发布、消耗 credits、生产部署"这类动作在落地之前经过人工。
AI 那条路上一共三个地方可以放这道门，位置不同，能保证的东西差别很大：

1. **让请求方自报**（`approvalPolicy` 由前端填）。这条路已经存在，且是 §68 那条"上下文不由请求方定义"的同一类问题：
   直接打 `/api/ai/run` 的人把数组留空，门就不存在了。今天它的值由服务端覆盖成 `WEB_APPROVAL_POLICY`，
   请求方那一份只用来证明"覆盖确实发生了"（集成用例第 1 条断言的就是装配之后的线上报文）。
2. **让 provider 自己报**。真实 provider 会在结果里附 `approvals`，但它报的是**它记得的那些**——
   规则版 mock 与任何一次截断/改写都可能给出一条 `remove` 而不附任何说明。
   所以 web 侧还有一遍**逐 op 扫描**（`remove / removePage / removeToken / removeAsset`），两边取并集。
   provider 失忆不能变成"删除直接进画布"。
3. **在写入前拦**（选这个）。补丁进不了工作区，界面上那句"画布还没有被改动"才是可验证的，而不是安慰话。

拦下之后有一个必须现在回答的问题：**批准的那一刻，交回编辑区的是哪一份补丁？**

- **重新跑一次**：界面上简单（批准 = 再点一次执行），但它把"批准"变成了"批准一个我还没看过的结果"。
  第二次生成的补丁和第一次被扣下的那份可以完全不同——用户看过的是"删掉 Hero"，落地的是"删掉 Hero 外加改了标题"。
  这条直接违背 §74 的语义，也让人无法用 diff 复核。
- **交回当初扣下的那一份**（选这个）：等待态存的就是那一份完整结果，批准只是让它离开等待态。

## 决定

- `holdForApproval(taskId, record)` 是全库唯一给 `agent_tasks.requires_approval / status='awaiting_approval'` 置值的写入方，
  并且**只在任务还是 `running` 时才置**：终态行被覆盖的话，账本上会多出一条"先成功了、后又等审批"的回溯记录。
- 挂起时不写 `finishedAt`：等待不是终态。写了它，任务列表会把"还等人决定"算进已跑完的用时。
- 读侧（`GET /api/ai/tasks/<id>/approval`、`GET /api/ai/pending-approvals`）**不含被扣下的补丁正文**，
  只说"有几处要决定、分别是什么动作、理由是什么"。审批入口的找回不靠把补丁发给浏览器。
- `decideApproval` 用 `WHERE status='awaiting_approval'` 的 CAS 做一次性裁决：第二次决定返回 `not_pending`（409），
  批准那次返回的 `held` 与挂起时那份逐字节相同。
- 批准之后补丁**仍走 `applyResult` 那条 Command 事务**（§149/§150），与一次普通生成同形：一次 Ctrl+Z 回到 AI 动手之前。

## 后果

- 得到：批准的内容=看到的内容；刷新之后现场还在（卡片从账本找回，不是 React 状态里的一次性记忆）；
  别人和别的项目一条都读不到；批准与放弃各留一行审计（含被拒的那次，`allowed:false`）。
- 付出，而且这条如实写在界面上而不是藏在代码里：**期间文档如果被别人改过，交回的那一份可能落不了地**。
  服务端不预演"这笔 op 现在还能不能应用"——预演要再读一次权威文档，而它给不出比"应用时会不会成"更强的保证。
  落不了地时报的是"补丁未能改动模型：AI 返回的 op 与当前文档不匹配"，那是真失败，不是审批没生效。
- 这条"与一次普通生成同形"的要求顺带暴露了一个更早的缺陷（这次才撞到，因为它与 §149 无关也一直在）：
  `invertPatch` 对 `remove` 求逆时，函数末尾那次全局 `ops.reverse()` 会把"先根后子"的子树还原顺序翻成"子在前、根在后"，
  撤销时子节点因为父级还没回来被逐条 skip——**节点悄悄少一半而没有任何一处报错**（画布 8 → 1 → 2）。
  还原时跟着克隆塞回整份 `children` 还会与逐条 `insert` 叠成双份（节点数对得上，画布每个子节点画两遍）。
  两处都由 `packages/design-model/test/patch-commands.test.ts` 钉住：断言落在"子节点本身回来了、且只回来一次"，
  而不是 `hero.children.length`——那份数组跟着克隆节点整体回来，一个子节点都没重新 insert 也照样是 2，
  这正是这个缺陷原先绿着的原因。
- 挂起时改的是**说法**，不是事实。provider 的活动流与计划步骤按"补丁已经应用"写（`1 个 op 已落地`、步骤 `done`），
  而交回浏览器的那一份什么都没应用——同一屏上就成了"画布还没有被改动"配"已落地"这种自相矛盾。
  `gateResponse` 只动 `delivered`：那一句换成"已挂起 N 个 op，批准之前不会落地"，`done` 的步骤标成 `skipped`；
  **`held` 那一份一个字都不改**，因为批准的凭据正是"用户看过的就是这一版"。
- 跨语言的那半（ai-service 侧的 `DESTRUCTIVE_OPS`）不靠注释保持一致：
  `apps/ai-service/tests/test_run.py::test_destructive_op_set_matches_the_web_gate` 直接读 web 侧那份源码比集合。

## 补记（同日）：异步那一路接的是同一道门，不是第二道门

§162 的异步作业刚有 web 侧消费者时，结果交回浏览器那一步是**原样给**：provider 返回的整份
`AiResponse` 落进 `agent_tasks.result`，`GET /api/ai/jobs/<id>` 谁问就照抄谁。于是"绕过 §74"
不需要构造请求，只需要在界面上多选一个"异步"。这一条不是补个 `if` 就算完，有三个决定要落字：

- **门放在 `settle()` 里**，也就是全库唯一写终态的那一个地方，不放在查询接口里。
  ADR-0011 说异步的终态"由有人来问才收敛"，那么"这份结果能不能算成功"也只能在那一刻判；
  放在查询侧会变成同一行账被问一次过门一次，问两次过门两次。
- **`HeldRecord` 要多存一份 `delivered`**（同步那一路不需要，它本来就当场把这份发出去了）。
  异步没有"当场"：挂起之后用户可能刷新、可能换实例、可能几小时后才来裁决，
  每一次都要看到他当初批准的那一字不差的版本。而 `delivered` 里的理由是 `nodeNamer(document)` 现算的，
  文档在这期间会变——重算出来的名字和挂起那一刻不同，"我批准的就是这一版"这句话就空了。
  所以存进去（`held` 与 `delivered` 两份都在），**不重算**。
- **挂起时不发通知**，与同步侧同一条理由：`Generation complete` 替一次还没人决定的事签字就是假事件（§164）。
- **观察报文改用自己的 zod 契约**（`AiJobObservationSchema`，路由 `safeParse` 之后才发）。
  之前这个对象是手搓的、没有契约，而"门给的到底是哪一份"正是这次新增的字段（`response` / `approvals` / `notes`）；
  没有契约的话，下一次有人把整份 `held` 顺手加进出参，是静默泄漏而不是红一条测试。

代价要如实说：既然门在 `settle()`，而 `settle()` 由观察触发，那么**没人来问就没有挂起行**。
今天的队列是进程内内存队列（`backend=memory`），刷新即失联——这条链路还没有 TTL 清理，
也没有真 worker 的端到端验证（本机 DEMO MODE 到不了一步真 provider 的异步提交）。
但这与"泄漏"是两回事：没被问过 = 没把结果交回过任何浏览器。

**2026-10-27 核对后改口径**：上面的两笔代价都已变化——① 队列不再只有内存后端，
配 `NEXUS_REDIS_URL` 就是 Redis（跨实例、重启不丢；连不上启动失败，不悄悄退回内存）；
② 等待中的挂起行**已有 TTL**（`APPROVAL_TTL_MS` = 24 小时，`convergeExpiredApproval`
在读的时候收敛成 `cancelled` 并发通知，见 ADR-0022）。仍欠的是真 provider 下真 worker 的端到端。
