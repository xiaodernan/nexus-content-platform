# ADR-0054：游戏侧的 completion 是"多少人通关过"，与页面的滚动完成度**分开存**

- 状态：**已接受并落地**
- 日期：2026-10-22
- 相关：§168（Analytics）· §50（公开可玩）· §51（八种型）· §159（不拿假数据充数）· ADR-0043（爬虫与真人另计）

## 背景

ROADMAP 的 §168 那条欠账里写着：

> **游戏侧 completion 事件仍欠**（这一件不在这一片里）

§168 第一、二、三片把**页面的访客现场**采到了（滚动比例、可见时长、爬虫与真人另计），
但那些数说的全是"**这一页滚到哪儿**"。一个玩到结局的人，在那一套里留下的是
"完成度 100%"——于是创作者看得见"有人滚到了底"，却看不见"有人把它玩通了"。

§53 的可玩投影早就有了（八种型都能玩、对话型有两个结局），所以**游戏知道通关的那一刻**，
只是那一刻没有落点。缺的不是一个玩法，是**一个事件与它的落点**。

## 三个决定

### 一、自己一张表 `game_completions`，不挂在 `publication_visits` 上

`publication_visits.completion_pct` 是**滚动比例**，"通关"是**一个事件**⇒ 两者不是同一个口径。
挂在一起的后果很具体：那一列会同时装着"滚到 80%"与"玩通了"，读它的人得先猜作者指哪一个。

⇒ 于是新表只存事件：`publication_id / visitor_key / user_id / suspected_bot / completed_at`，
**没有"完成度"那一栏**——它存不下滚动比例，混不进去。

### 二、粒度是"**多少人通关过**"，不是"通关了几次"

唯一索引 `unique (publication_id, visitor_key)` ⇒ 同一个访客在一个发布版本上只记一次。

理由是"多少人玩通了"才是创作者能据以行动的那个数（有多少人玩得下去），
而"通关了几次"会把重玩的人算成好几个人（一个人刷五遍 = 五次通关 ⇒ 看着像五个人）。
⇒ 所以界面上的措辞、导出的列名、API 的返回值都跟着这个粒度走：
`recorded: false` 明确告诉调用方"这一次没有新增"，而不是悄悄加一。

### 三、通关只由**公开可玩页**上报，作者自己的工作稿不报

回调是函数，不能从服务端组件穿过边界传到客户端组件 ⇒ 上报那一层落在客户端
（`apps/web/src/play/PublicPlay.tsx` 渲染播放器并提供回调）。
作者自己的工作稿页（`/game/<项目>`）**不传那个回调** ⇒ 自己试玩不会被记成"有人通关了"。

同一把匿名 key（`@/lib/visitor-key`，从 `VisitMeter` 里抽出来共用）⇒
"谁通关了"与"谁看过这一页"指的是同一个人，能对得上。

## 后果

- **多了一张表与一次迁移**（`0034_game_completions.sql`）：换来的是两个口径不再混。
- **爬虫照收但另计**（沿用 `classifyVisit`）：可疑的行照样入库（"被爬过"要留得下痕迹），
  但不算进真人那一格；空 UA 也算疑似（浏览器一定带 UA）。
- **上限是 30 次/小时/IP+key**（比访客现场的 240 严）：通关是低频事件。
- **互动作品（非游戏）的 completion 仍然没有** ⇒ 这一条欠账没有因为今天这一格而清空，
  ROADMAP 上如实留着。
- **还没做浏览器那一寸**：e2e 里"玩一次 ⇒ 创作者那边多一个数"这一条要另作一片
  （要先在真浏览器里发布一个带游戏设计的版本）。
