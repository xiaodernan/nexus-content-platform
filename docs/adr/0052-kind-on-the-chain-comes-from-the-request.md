# ADR-0052：链上那一型由**请求显式给出**（不从目标文本猜，也不写死 RPG）

- 状态：**已判决（并已落地）**
- 日期：2026-10-22
- 关联：§51、§52、§53、§16、§159、§110、ADR-0042、ADR-0046、ADR-0049

## 背景

ROADMAP 那条欠条（2026-10-22 核过原文，行 922）：

> **仍欠**：链上这一格只跑 RPG 那条管线——2D 那五种类型与对话管线在链上还没有各自的一格
> （要接得先让链上的草稿带上 kind，而不是像今天这样默认 RPG）。

2026-10-21 那一格把**下游**修好了：链上的试玩格按草稿标的 `kind` 派管线
（`playtestByKind`）。但**上游**还只会造 RPG：

- `apps/web/src/lib/agent-game-draft.ts` 把 `kind` **写死**成 `'rpg-prototype'`；
- `gameStep` 硬编 `compileRpg` + `playtestRpg`，摘要写死"RPG 原型草稿"、notes 写死"经验来源…"。

⇒ **链从头到尾都还是 RPG** ⇒ 欠条只付了一半。

另外还有一处**两份真值**（§16）：2026-10-21 新增的 `playtestByKind` **自己**写了一遍
"kind → pipeline"的判断，而 `compileForKind`（`packages/game-model/src/story.ts`）是仓库里
明写的**唯一分派点**（"两个试玩入口都必须走这里：各写一遍判断，迟早变成一个页面说没接、
另一个页面硬跑 2D 关卡"）⇒ 那一格一并收回来。

## 选项

| 选项 | 判决 | 理由 |
|---|---|---|
| (a) 从**目标文本**里"理解"出类型 | 否 | §159 禁止把规则说成理解。"做一个解谜游戏"到底算不算解谜？⇒ 那是猜；猜错时用户看到的是一份**他没要的设计**，而结论里还写着"配方给的" |
| (b) 配方里**写死**（永远是 RPG） | 否 | 别的型永远编不出来 ⇒ 那条能力不存在（"有代码"不等于"做完了"，§159） |
| (c) **请求显式带** `gameKind` | **是** | 作者/外部 Agent 明说要哪一型；不认识或链上没有配方 ⇒ **诚实拒收**，不替人挑一个"最像的" |

## 决定

**(c)**，并且三件事跟着它一起定下来：

1. **型记在计划里**（`AgentPlan.gameKind`）⇒ 任务行读得出"这份作业当时编的是哪一型"，
   刷新后复看不用猜（§16：设计模型是唯一真值）。
2. **一张配方表，每型一段变体**（不是两张表）：topdown 那五型共用同一份实体与数值，
   只把**"经验/等级门"那几句换掉**——不是补一句"其实不参与判定"，
   因为那句会与前一句（"条件凑齐但没到级就不结算"）**自相矛盾**。
   数值同理：`xpReward` / `requiredLevel` 只有 RPG 管线读（`compileGame` 只读任务上的 `timeLimit`），
   留在别的型的草稿里就是"设计里写着要 2 级"而这一型根本不看等级。
3. **派发只留一处**：`playtestByKind` → `compileForKind` ⇒ 链上任何一处都不再自己判断型。

**对话那两种（`interactive-story` / `visual-novel`）在链上编不出来** ⇒ **诚实拒收**
（400 + 一句"链上还没有配方"）：链上那份配方给的是战场与战斗，而对话要的是**对话实体**
（正文与选择）⇒ 做一份空草稿糊过去就是 §159 禁止的假交付。

## 后果

- **今天那份 RPG 草稿逐字节不变**：改配方说明与数值之前先拍了快照（`gameDraft` 的 JSON），
  改完逐字节对过 ⇒ 一样；纯层用例另外钉住关键句（等级门那句、经验那句、`xpReward` 那个数）。
  **RPG 那一条链的结论（摘要 / counts / notes）也逐字保留**（红线：今天的行为一个字都不许变）。
- **API 多了 `gameKind`**（可选，缺省 = RPG 原型）：`POST /api/projects/<id>/agent` 的请求体。
  外部 Agent 用得上；**界面上的选择器还没有**（另作一片，要 e2e 截图那一套）。
- 链上现在能编的类型：**RPG 原型 + topdown 那五型**（2D / 2.5D / 3D / 探索 / 解谜）。
  这五型共用同一份关卡计划，只是画法不同 ⇒ 规则一份、画法五份（仓库既有立场）。
- 对话那两种在链上**编不出来**（明确拒收，不是空草稿）；试玩格对它们也**明说还没接**
  （报告形状不同：没有"走法"可言，算的是可达性与停点）。
- 这一格把"**今天的口径**"与"**将来的口径**"分开了：链上编出来的**是草稿**，
  接受进项目之后它就是项目里的一份普通游戏文档 ⇒ 作者随时可以在 Game Studio 里改型
  （§51 的型是文档的一部分，跟快照走）。

## 补记（同日）：**改一半比不改更坏**

这一格落地后我回头把链上九步**逐格**核了一遍 ⇒ 发现还有两步在拿 RPG 的判据读非 RPG 的设计：

- **战斗格**（`combat.ts` 的 `evaluate`）：`compileRpg` + `playtestRpg` ⇒ 战斗目标
  （通关 / 战斗时长 / 赢家要付代价 / 站着不动不能赢 / 一直躲不该倒下）的读数全来自 RPG 管线；
- **布局格**（`level.ts` 的 `evaluate`）：同样硬编 ⇒ 布局目标与"战斗目标达标几条"也是 RPG 的读数。

⇒ ⇒ **同一个作业里，上游（编草稿、试玩）读的是自己那条管线，下游（战斗、布局）读的是 RPG 那条**
⇒ ⇒ **两个口径** ⇒ 用户看到的数字互相打架 ⇒ **这比"整条链都是 RPG"更难查**
（后者至少自洽，前者会让"战斗目标达标"与"试玩报告"对不上）。

⇒ **教训**：把"按型派"这件事做完的判据不是"下游那几格改了"，而是
**链上每一格都从那份草稿的 `kind` 出发** ⇒ ⇒ 核法只有一条：**逐格问"这一格的读数来自哪条管线"**
（这一格报了 pipeline 字段以后，界面上就能自己说 ⇒ 不用人记）。

⇒ ⇒ 这一条也补进 ROADMAP（2026-10-22 那段"战斗格与布局格也按型派"）。
