# ADR-0264：判据自身的形状也是判据——一次 33 分钟的全量门禁停机

- 日期：2026-11-14
- 状态：已采纳
- 影响：`apps/web/test/not-found-visual-style.test.ts`（修复）、`apps/web/test/gate-hygiene.test.ts`（新增）、`verify:fe-gates` 的可执行性

## 背景

`npm run verify:fe-gates` 是 96 套前端视觉判据的统一入口。它一直是绿的，直到某次它跑了 **33 分钟没有输出一行**，被杀掉时仍未结束。

排查结论不是"某套判据太慢"，而是**其中一套判据进入死循环，而且是在模块顶层（collect 阶段）**：

```ts
for (let m = /\.nf-/g.exec(globals) as RegExpExecArray | null;
     m;
     m = /\.nf-/g.exec(globals)) {
  const comments = [...globals.matchAll(/\/\*[\s\S]*?\*\//g)];
  if (!comments.some(/* 这个匹配不在注释里 */)) return m.index!;
}
```

`for` 的初始化和更新段**各写了一遍正则字面量**。JS 每次求值一个正则字面量都产生**新对象**，`lastIndex` 因此每轮回到 0，`exec` 永远返回**同一个**首个匹配。只要首个 `.nf-` 落在注释里，`return` 永不执行，循环就永远转下去——还每轮把 36 万字节的全文注释 `matchAll` 一遍。

## 为什么它绿了很久

**因为首个 `.nf-` 恰好不在注释里。** 那是数据巧合，不是正确性。

`globals.css` 里 `.nf-` 出现 30 次，第一个在字节 3979（一行提到 `.nf-title` 的注释），第一个不在注释里的是 59125。并轨把 `BrandTitle` 那段注释（提到 `.nf-title`）带进来之后，3979 落到了首位——事故条件凑齐了。

于是：**没有任何一条判据变红**。所有测试文件本身"通过"，只是永远跑不完。

这类故障对「测试全绿」这套语言**完全不可见**：它不产生失败，它取消产生失败的可能。

## 代价比"慢"大得多

死循环在字母序 `n` 处挂死，意味着 `o` 到 `z` 开头的判据**从来没被执行过**。

修复后第一次真跑全量，立刻暴露 2 条早就红了的判据：

- `publish-panel-visual-style.test.ts`：提交 `33212785`（并轨收官尾巴）给 `PublishPanel` 加了预检结果四行（`data-publish-preflight-outcome` / `data-publish-ai-ready` 落地），那是真实的新行为，SHA 恒等门该破——但没人来签字，因为这一套排在 `p` 之后，永远轮不到。
- 同文件另一条：那四行当时被写成 `.pp-note12*`（公开试玩页的族）却用在 `.pb-` 组件里，门面族判据当然红。

**死循环的代价不只是 33 分钟，是遮蔽。** 一条永远跑不完的判据，等价于把它之后的所有判据全部删除——而且不留任何痕迹。

## 决定

### 1. 修法不是"把正则提到循环外"

那只是让这一次跑通，形状仍然危险。换掉问题的形状：

- 注释区间**只算一次**（`[...globals.matchAll(/\/\*[\s\S]*?\*\//g)]`）；
- 用 `indexOf('.nf-', at + 1)` 正扫每个位置，**结构上不可能**自我重置；
- 用二分判定某个位置是否落在注释内。

代价 O(n + k·log m)，与文件大小线性、与出现次数对数。原写法是 O(∞)（在事故条件下）。

二分那一步有个坑值得记：**不能**写成「`at < start` 就往左、`at >= end` 就往右」——落在两个区间之间时会越界走丢。正确写法是找**最后一个 `start <= at`** 的区间，再判 `at < end`。

### 2. 新增「判据卫生门」：`gate-hygiene.test.ts`

守的不是某个页面的样式，而是**判据代码自身的形状**：凡是依赖 `lastIndex` 的 `g`/`y` 正则，只许有一个实例。

这个形状之所以危险，恰恰因为它写起来**更短**：

```ts
for (let m = /x/g.exec(s); m; m = /x/g.exec(s)) {}   // 短一行，且在首个匹配不在注释里时完全正确
```

它只在数据变化时爆炸，而数据会变。

### 3. 检测器必须有自检

一条"扫描所有判据找违规"的判据，如果扫描器本身写错，它会永远绿——**和没有一样**。所以这份门里四条是自检：

- 已知坏样本（含折行形态）必须被判违规；
- 单例正则 + `while` 的**好**写法不许误报；
- sticky（`/y`）同族同样违规（它也吃 `lastIndex`）；
- 样本量兜底：至少看住 90 套（glob 写错导致空跑时，`toEqual([])` 会假绿）。

### 4. 注释既不喂绿，也不喂红

第一条真跑就红了，红得有价值：**扫描器把修复注释里引用的旧代码当成了违规**。

本项目有一条反复出现的纪律「注释不得喂绿任何一道门」。它的镜像同样成立：**注释也不得喂红任何一道门**。修复的注释里必须引用那段旧代码才说得清事故原貌；如果扫描器把引用当违规，下一个想记录教训的人就只能不写。

所以扫描前剥注释，并单独加一条判据钉住这个双向性：剥之前原文**含**这段（教训要能读），剥之后必须干净（它没跑到代码里）。

## 结果

```
修复前：verify:fe-gates  33 分钟 → 被杀，零输出（实际会永久挂死）
修复后：verify:fe-gates  375 秒 / 96 套 / 1005 条，1003 通过
       其中 collect 47.81s、tests 12.46s —— 96 套的"执行"只要 12 秒，
       剩下全是每套都要读 globals.css + tokens.css 的采集成本
```

判据：`gate-hygiene.test.ts` 8 条；`not-found-visual-style.test.ts` 14 条（不变，但 collect 从 ∞ 变成 4.84s）；补签 `publish-panel-visual-style.test.ts` 的 SHA。

## 补充（同日第二片）：把误伤的串行解掉

上面「结果」里那 375 秒有个不舒服的比例：`tests` 只占 12.46s，剩下全是 collect + prepare。
原因是根 `vitest.config.ts` 里那一行 `fileParallelism: false`——它的注释写得很清楚：

    // Real-DB suites share one Postgres; 5s kills them when they queue. Sequential is cheaper than red.

那条约束是**对的**，但它保护的是「共用同一个 Postgres 的集成测试」。96 套视觉判据
一个都不碰库（只 `readFileSync` 读 CSS/源码做正则），跟着串行属于**误伤**。

**做法是派生一份配置，不是改根配置。** 改根配置＝为了视觉判据去动 DB 测试的正确性；
派生一份＝让两种测试各按自己的约束跑。这是本 ADR 同一条思路的延续：
**约束要落在它真正保护的东西上。**

`vitest.fe.config.ts`：只 include `apps/web/test/**/*-visual-style.test.ts`，
`fileParallelism: true`，`pool: 'forks'`。

选 forks 不选 threads 的理由：Windows 上 worker_threads 起停更慢，而 `readFileSync`
是**同步阻塞**调用——在线程池里会拖住同进程的其他测试；fork 各自独立进程，阻塞只影响自己。
`maxForks` 上限取 8 而不是 CPU 数：不是为省 CPU，是为省内存——每个 fork 各自持有一份
36 万字节 CSS + 若干源码字符串，16 个 fork 的峰值 RSS 会到 GB 级。

`fe-gates.mjs` 仍然**显式传 96 个文件**：如果那份配置的 `include` 哪天写错，
这里会因为"传了 96 个却 filter 出 0 个"而红，而不是安静地跑 0 套、报绿。

```
修复死循环后（串行）  243s 端到端 / vitest 161.66s（tests 8.66s）
并行配置后            65s 端到端 / vitest  36.24s
────────────────────────────────────────────────
相对最初 33 分钟零输出，约 30×
```

## 仍欠

1. **仍没有超时兜底**。`testTimeout` / `hookTimeout` 都管不到**模块顶层**——
   这次就是死在那里。真正的兜底是外部看门狗（`timeout` 命令或 CI 的 job 超时），
   这一片没做。现在的并行配置把 96 套压到 36 秒，客观上让"跑到一半卡住"更容易被发现，
   但那不是兜底，是运气变好了。
2. **只扫了 visual-style**。同族形状理论上可能出现在任何测试或源码里；这次扫描范围
   选了 96 套判据，因为那是唯一跑全量的一批。
3. **collect 才是真正的大头**（并行下累加 100s）。每套判据都在模块顶层把 `globals.css`
   与 `tokens.css` 各读一遍——36 万字节 × 96。真要再进一步，得把"读一次 + 共享解析结果"
   做成 fixture（`globalSetup` 或 `setupFiles` 注入），但那样每套判据就不能独立运行了，
   是设计取舍不是纯优化。**没做，也不打算在短期做**——65 秒已经不影响任何人的工作节奏。
