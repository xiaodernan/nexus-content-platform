# ADR-0015：文档规模的门按"整份文档"挡，不按"单页"挡

状态：采纳（2026-09-27）
关联：§146（性能规模档）、§147（大项目）、`docs/PERFORMANCE.md`、任务 #63

## 背景

`apps/web/src/server/validation.ts` 里 `parseDocument` 是 `PUT /api/projects/[id]` 的门。
它原本有一条 `MAX_NODES_PER_PAGE = 4000`：任何一页超过 4000 个节点就整份文档拒绝。
这个数字没有 ADR、没有注释说明为什么是 4000、也没有任何用例引用它。

2026-09-27 用 `scripts/perf-browser.mts` 在真浏览器 + 真生产构建上压 §146 的最高档时，
这一档根本 PUT 不进去：

```text
规模档 10000：造文档失败 —— 写入失败：HTTP 400
{"error":"validation_failed","issues":["页面 Home 节点数超过上限 4000"]}
```

当时的绕法是摊成 3 页（10002 节点 / 3 页），确实量到了数字，但那不是 §146 写的那一档。

## 两个事实让这条门站不住

1. **它没有约束它想约束的资源**。`DocumentEnvelope` 允许 64 页，所以 4000 × 64 = 25.6 万节点的文档
   过得去这条门，而一页 5000 个节点过不去。真正会撑爆的是"整份文档先进内存再被克隆"，
   跟节点摊在几页上没有关系。
2. **它和仓库自己已有的证据矛盾**。模型层基准早就把 10000 节点写进过一页
   （`docs/PERFORMANCE.md`：`createProject` 含 10k 节点一个事务 2512ms），
   集成测试也有一条"一个页面 8,000 个节点仍然存得下来也读得回来"一直是绿的。
   那条绿走的是 `saveDocument`、**绕过了这道门**，所以它从来没测过用户实际会撞上的 400。
   （这条是本 ADR 主要想记的教训：**规模类的用例必须走用户走的那道门**。）

## 选项

- **A. 保留单页上限，只把数字放大**（比如 12000）。挡的还是错的东西，
  只是恰好放过 §146 这一档；下一页数一多又会以别的形式挡。
- **B. 改成按整份文档的节点总数挡**（本 ADR 采纳）。挡的是真资源，
  而且 §146 要的形状（一页 10000）能过去。
- **C. 不设上限**。今天的实测里 10002 节点的首帧已经 1.6 秒、JS 堆峰值 148MB，
  再往上就是拿整个浏览器赌用户的机器，不能没有门。

## 决定

门改成整份文档的节点总数上限：

```ts
export const MAX_NODES_PER_DOCUMENT = 20_000;
```

数值取自实测与需求两头：
- §146 的最高档 10000 **必须**过得去（这是需求，不是性能目标）；
- 一页 10000 个节点实测（门改后重测，`docs/PERFORMANCE.md` 2026-09-27 口径 `prod-adr0015` 那一节）：
  首帧 1761.3 / 1809.9ms、属性写入到画布 583.3 / 763.3ms、JS 堆峰值 145 / 161MB（两遍各取中位数）；
- 取顶档的两倍留一倍余量给真实项目（页面各自的根、组件实例这些也要占节点数）。
  再往上（30k+）要等 `applyPatch` 的结构共享与增量保存做完，那时改这个数必须同时留一条新的实测。

单页不再单独设限。`pages ≤ 64`、`tokens ≤ 2000`、`components ≤ 512` 这些形状限制不动。

## 后果

- §146 的三档（100 / 1000 / 10000）在真实 HTTP 路径上都能存能读；
  压测脚本相应改回"全部塞进一页"，摊页那条路删掉了 —— 门改了以后，
  再用摊页的数当 §146 顶档就是谎报。
- 新增的钉法（`apps/web/test/projects.integration.test.ts` 的「§146 顶档走真实那道门」）：
  ① 一页 10000 个节点必须过 `parseDocument` 并且 `saveDocument`/`loadDocument` 对得上条数；
  ② `MAX + 1` 个节点被拒，且拒绝理由里带数字（挡住的是这条规则，不是别处先坏）；
  ③ `MAX_NODES_PER_DOCUMENT ≥ 20000` 单独钉住 —— 反向实验发现②是 `MAX + 1` 构造的，
  常量改多大它都绿，所以"这个数字本身不许被悄悄调小"得由③来说；
  ④ **①②③全都只用一页，所以没有一条测到"求和"这一维**：把 `reduce` 换成"只看 `pages[0]`"
  或"各页的最大值"，前三条照样绿——那等于门悄悄退回单页语义，而退回单页正是本 ADR 要修的东西。
  第四条因此造三页、每页都不够上限、总数超上限，要求被拒；同一条里带反向对照
  （同样三页、总数在上限之内必须放过），证明拒的是"和"而不是"多页"本身。
- 变异探针（改的是 `validation.ts`，跑完还原；未变异对照全绿）：
  `reduce → 只数 pages[0]` 1 条红（④）；`reduce → 各页最大值` 1 条红（④）；
  `if (nodeCount > MAX)` 整个短路 2 条红（②④）。④是三颗变异里唯一能看见"求和没了"的那条。
- 变红的东西：任何依赖"单页 4000 就会被拒"的旧行为（本仓库里没有：全仓 grep 过，
  除了历史文档叙述之外没有引用点）。
- 遗留：这道门挡的是"能不能存"，挡不住"存了会不会卡"。
  文档里写死的性能门（属性写入 <50ms、选中响应 <16ms）在 4000/10000 档是红的，
  那属于 §147 的活，不由这个常量负责，也别把它当成本 ADR 已经解决。
