# ADR-0104：把"摊还 O(1)"从注释变成有牙的门——数据结构热点路径的可测复杂度

- 状态：accepted
- 日期：2026-11-12
- 版本片：v671
- 关联：ADR 0028（realtime Redis 连接纪律）、ADR 0076/0077（MemoryRateLimiter 桶上界与摊还清扫）、§46（TtlLru）
- 编号注记：本 ADR 起初写作 0103，提交前并行 lane 的 `facf76c` 先占用了 0103（边缘 Server-Timing），
  故本片让位、改为 0104 并同步更新了全部交叉引用。共享树里两条 lane 可能在同一会话里认领同一个
  下一个编号——提交前重查 `ls docs/adr/ | grep 01xx`。

## 背景：两张最热的数据结构，成本承诺写满页眉，却没有一道门钉过成本

`TtlLru`（anon 发现页 / 会话 / 一众进程内 TTL 缓存）与 `MemoryRateLimiter`（全站限流的进程内驱动，
也是 Redis 驱动退回时的那一份）是全站最热的两张进程内数据结构。两份源码的页眉把性能论证写得极详尽：

- `TtlLru`：「命中就 `delete` 再 `set` 刷到尾部，淘汰从头部 O(1) 走，热路径不会因此线性扫描」。
- `MemoryRateLimiter`：「淘汰按插入序当场收，`Map` 当 LRU，每淘汰一只只走一格，不是每次命中排一次
  全表——**上界被洪水顶住时每次请求只多淘汰一只，否则'防内存耗尽'自己会变成一次放大攻击**」；
  全表清扫「摊到 256 次一笔」。

这些是**复杂度承诺**，不是功能承诺。而既有的门——`ttl-lru.test.ts` 8 条、`rateLimit.test.ts` 的规模组
（清扫 / 上界 / LRU 选择 / 记账 / 日志收敛 / 反证臂）——**全在问"答案对不对、删了谁、记了几笔"**，
**没有一条问"每次花多少、成本会不会随规模塌"**。于是存在一类真实退化：有人把 `TtlLru.get` 里顺手
加一次 `liveSize()` 式全表扫描、或把 `evictToCap` 改成每次排全表——语义门全绿、线上却从 O(1) 塌成
O(n)，而限流那一条尤其危险：它本是用来挡免成本写入口的闸，退化后自己成了放大攻击。

缺的不是"再测一次时间"，而是**一条确定性、不 flaky、能区分 O(1) 与 O(n) 的复杂度门**。

## 决定：两种证据分工——墙钟只归档，操作计数才做门

1. **基准 harness `scripts/ds-benchmark.mts`**（墙钟，只归档、不断言阈值）：量两张结构的吞吐 /
   p50 / p99，输出可贴进 `docs/PERFORMANCE.md`，`--json` 走机器可读。三件**对照**而非单点：
   ① `TtlLru` 命中成本 vs 容量（8 / 8192）；② `TtlLru` 上界洪水（40 万 set 挤 256 上界）；
   ③ `MemoryRateLimiter` 上界洪水（6 万 distinct 桶，两档 maxBuckets 64 / 4096）。
   沿用 `scripts/perf-baseline.mts` 的纪律：共享宿主上写死毫秒阈值只会 flaky，flaky 的终点通常是
   把断言删掉——那不如一开始就把数字记进文档，由人眼与**相邻规模的比例**去读。
2. **复杂度契约门 `apps/web/test/ds-complexity-contract.test.ts`**（操作计数，确定性、做门）：
   临时包住 `Map.prototype.get/set/delete/Symbol.iterator` 计数（`vi.spyOn` 自动还原，先存原方法引用
   再 spy、由 spy 转发给原引用，避免递归套娃），在**同步被测区间**前后清零，于是计数里只有被测结构
   自己的操作。`MemoryRateLimiter.hit` 虽是 `async`，函数体内无 `await`，整段在返回那个已 resolve 的
   Promise 之前同步跑完，故紧跟调用读到的计数就是这一笔 hit 的全部成本。判据钉三条**形状**：
   - `TtlLru` 命中：容量 8 与 8192 的每命中操作数**相等**且有常数上界；
   - `TtlLru` 踢除：顶到上界前后每 set 操作数相等（踢除 O(1)，不是每次扫全表）；
   - `MemoryRateLimiter`：上界洪水逐笔操作数**零方差**、两档 maxBuckets（8/4096）单笔淘汰成本**相等**。
   **判据刻意不硬编码"命中=6 次"**：那会把将来"双 Map→单 Map"（命中 6→3）的正当优化判红。
   钉的是"与容量无关 + 常数上界 + 洪水逐笔相等"——同时有牙又不惩罚正当改动（ADR 0094 X4 同源纪律）。
3. **变异臂 `docs/evidence/ds/complexity-arms.mjs`**（`node` 直跑，纯 Node ESM，非类型规则集）：
   内联退化实现，证明门有牙。两条臂 RED as expected；第三条**没红成**的臂与其缘由如实记录（见下）。

## 实测读数（measured, not assumed）

**确定性操作计数**（门本身，零墙钟）：`TtlLru` 命中恒 **6** 次 Map 操作、写入恒 **3** 次，
容量 8 与 8192 **完全相等**；踢除前后每 set 成本不变；`MemoryRateLimiter` 顶到上界后逐笔恒
**13** 次、**480 笔零方差**，两档上界（8 / 4096）单笔淘汰成本相等。

**墙钟对照**（node v22.22.2 / win32 x64，`scale=1`，共享宿主，只归档不裁决；全文在
`docs/PERFORMANCE.md`）：
- `TtlLru` 命中容量 8→8192（1024×）：ops/s 483k→214k、p50 0.42→0.56us——同量级，无 O(n) 退化。
- `TtlLru` 上界洪水 40 万 set / 256 上界：ops/s 356k、p50 0.74us——线性，非平方塌缩。
- `MemoryRateLimiter` 洪水 6 万 distinct：maxBuckets 64→4096（64×）ops/s 18k→11k、p50 49→79us，
  只慢约 39%，不是 64×——摊还 O(1) 淘汰。
- p99（28–237us）是 GC 与宿主争抢的长尾，重跑会漂，不解释成代码行为。

**读数方法修正（记下，免得重踩）**：基准首版逐操作 `performance.now()` 计时，量出 `ns/op=6875`
却 `p50=0.4us` 的自相矛盾假数——单次计时调用本身几十~几百 ns，与 TtlLru 命中同量级，20 万次计时
把读数整个吃掉了。改成**分批计时**（每 512 次操作量一段总时长，延迟分布用每块的每操作均值），
计时调用从 40 万降到几百，读数才自洽。这一修正正是契约门必须走操作计数而非墙钟的理由。

**变异臂（2/2 RED as expected）**：① `TtlLru` 命中混入 O(n) 逐元素扫描 ⇒ cap8=11 vs cap8192=8195，
门1 红；② 淘汰成本随 max 涨 ⇒ max8=12 vs max4096=4100，门4 红。

**零回归**：`ds-complexity-contract.test.ts` 4/4 + 既有 `ttl-lru` / `rateLimit` /
`rate-limit-readout` **39/39**。窄 tsc（web 测试 + tools 脚本各自只含改动文件与导入图）**exit 0**；
三个新文件 eslint 逐个足堆（`--max-old-space-size=2000`）**各 exit 0**（全项目 tsc/eslint 在本机
~0.3GB 空闲仍 SIGTERM，资源不是红）。

## 一条没红成的臂，和它为何是门的边界而非漏洞

曾设计第三条臂"固定上界（max=8）下每次淘汰扫一遍全表"，预期门3（逐笔零方差）会红——**实测判绿**。
查清后确认**门是对的**：上界固定时 `bucketCount` 恒等于 8，"每次扫固定的 8 只"就是 O(1)（只是常数
更大），逐笔成本自然零方差；真正该拦的复杂度退化是"成本随一个**会长**的维度涨"，而固定上界下没有
这种维度，能红的退化是"随 max 涨"（臂 ②，门4 抓住了）。这条没红成的臂与缘由如实写进证据脚本注释、
PERFORMANCE.md 与本 ADR——**不伪造一条"有牙"的臂自欺**，也顺带划清门3 的判据边界：它证的是
"固定上界下每笔成本不随时间/流量漂移"，不是"每笔成本最小"。

## 硬件契合 / 数据结构留白（量出来了，没顺手改）

`TtlLru` 把 `{value, expiresAt}` 拆进 `store` / `expiry` **两张 Map**：命中付 6 次哈希操作、键存两份、
LRU 序在两张表间各自维护；`get` 里 `this.expiry.get(key)` 后紧跟 `expiresAt!` 非空断言，靠的正是
"两表始终同键"这个**没被结构表达出来**的不变量。合并成一张 `Map<K, {value, expiresAt}>` 可把命中
6→3、写入 3→2，键只哈希/存一份（更好的缓存局部性），并从结构上消掉那个不变量——这是实打实的
硬件契合收益（少一半哈希探测、少一份键内存、LRU 序天然同步）。

**但本片只把成本量出来并记在这里，不改生产热路径数据结构**：`TtlLru` 被 anon 发现页等最热只读路径
依赖，在没有端到端回归余量的共享宿主上顺手换存储形状，风险大于本片范围。列为下一片候选（连同
"改前先补两驱别名隔离门"那条 ADR 0095 仍欠），不假装已经拿了收益。

> **v672 / ADR 0105 兑现注记（2026-11-12）**：留白已还——`TtlLru` 已改为单
> `Map<K, TtlEntry<V>>`，命中 6→3、写入 3→2，键只哈希/存一份，LRU 序同源，`expiresAt!` 那个隐式
> 不变量从结构上消掉。本片刻意"钉形状不钉字面 6"的判据正是让它保持绿（ADR 0094 X4 纪律兑现）。
> 收益裁决用**同进程交替 A/B + p50 中位数**（命中 1.39× / 1.46×、小表 set 1.31×）；跨进程
> before/after 的 +695%（≈8×）被三处自证推翻，**未**当作收益。新增单 Map 形状门 + 静态门 +
> M4 变异臂钉住结构收益。详见 `docs/adr/0105-...` 与 `docs/PERFORMANCE.md` v672 章。

## 仍欠（如实记）

1. 墙钟读数是**单宿主单次** `scale=1`，没有多会话均值、没有 CI 固定机型上归档——数字只配当对照与
   回归基线，不配当跨机器 SLA。要跨机器可比需固定 runner 与多轮取均值。
2. 契约门数的是 `Map` 操作次数这个**代理量**，不是 CPU 指令/缓存未命中。它可靠地抓住"混进 O(n) 扫描"
   这类结构退化，但抓不住常数因子级的实现退化（如一次命中多两次哈希——那正是"双 Map 税"能再省
   的地方，也正因如此判据不钉具体 6 次）。
3. `MemoryRateLimiter` 单桶 `filter` 是 O(limit)（limit 由调用方给、本就封顶），本片的门覆盖的是
   **桶数维度**的摊还成本，没有把 `limit` 维度做成门；O(limit) 是设计内的，记为界不是事故。
4. ~~双 Map→单 Map 的收益只有**结构推理 + 操作计数**（6→3），没有实测前后墙钟对照——那要等真正动手
   改的那一片，届时用同一支 harness 做 before/after（见上"留白"）。~~
   **v672 / ADR 0105 已补**：前后墙钟做过并存档，但在本机共享宿主上被噪声淹没（跨进程对照伪造出
   +695%），最终以**同进程交替 A/B + p50 中位数**裁决（命中 1.39× / 1.46×、小表 set 1.31×）。
   这反而把本 ADR 缺的那条方法论补上了：常数因子级改动不能靠跨进程墙钟对照，只能靠同进程 A/B。
