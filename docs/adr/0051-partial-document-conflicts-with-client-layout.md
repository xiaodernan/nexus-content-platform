# ADR-0051：「首屏只带视口内内容」这条路走不通（与"客户端算布局"冲突）⇒ 改走流式首屏

- 状态：**已判决（那一路否掉，改做流式）**
- 日期：2026-10-21
- 关联：§147、§16、§68、ADR-0048（首屏那一刀）、`docs/PERFORMANCE.md`「2026-10-21」那几节

## 背景

§147 的首屏那一格今天查清了三段账（安静机器、同一构建）：

| 段 | 耗时 |
|---|---|
| 服务端 `loadDocument`（读 + 组装，已绕过 drizzle 逐行映射） | **434ms** |
| **RSC 序列化 + 传输** | **700-900ms** |
| **浏览器（解析 + 水合 + 首屏求解 + 首次绘制）** | **800-950ms** |

⇒ **两段大头都随文档大小走** ⇒ 解法是"**首屏别带整份文档**"。
而"带多少"这件事有现成判据：画布是**虚拟化**的（`visiblePaintOrder` 的判据是**纯几何**的：
视口 + 256px 外扩与包围盒相交）⇒ 10000 档那一页**只渲染 54 个 DOM 节点**（视口内可见 54 个、裁掉 9946 个）。

于是上一格（ADR-0048 的后续）把"**部分文档**"这条路的价值量出来了
（`scripts/partial-document-size.mts`，10000 档真文档）：

| 载荷 | 大小 |
|---|---|
| 今天的整份文档 | **9.37 MB** |
| 瘦 layout（数组编码的几何）+ 视口内 54 个节点的完整 node | **938 KB（10.2× 小）** |

而且 `packages/design-model/src/partial.ts` 已经把这个**投影**做出来了（纯函数 + 5 条红线单测）。

## 为什么这条路走不通（硬理由，不是"难做"）

**客户端自己算布局。** `apps/web/src/studio/store.ts:403/413` 调的是
`resolveLayoutIncremental` / `resolveLayout` —— 布局在**浏览器里**算，不在服务端算
（预览页与公开页那两处 `resolveLayout` 也在服务端/组件内自己算）。

⇒ **要算全图的几何，客户端必须持有全量节点** ⇒
**"首屏只给视口内那几十个节点" ⇒ 客户端算不出全图布局 ⇒ 画布画不出全图** ✗

而**编辑路径把这个前提钉死了**：改一个节点 ⇒ 它的兄弟位置要跟着变 ⇒ 布局要重算 ⇒
**重算要全量文档** ⇒ 首屏没给全量的文档，**用户一编辑就得多拉 9.37MB** ✗
（那就把首屏省下的时间又赔回去了，还赔上一次往返）。

⇒ **⇒ 这一格与"编辑即时"不相容**（不是工程量的问题，是前提冲突）⇒ **不做**。

## 那剩下的路：流式首屏

**内容照样全给，只是分批到**：

- 首屏先到：骨架 + **视口内那一块**（第一块）⇒ 用户很快看到画布上有东西 ✓
- 后面陆续补齐 ⇒ 用户开始编辑时内容多半已到齐 ✓
- **不动任何现有前提**（客户端仍然算布局、仍然持有全量文档）✓

**要核对的**（下一格）：
1. Next 的 RSC 是不是流式的（`<Suspense>` + 异步组件 ⇒ 是，但要确认这条路上怎么用）；
2. 文档能不能**分块**（把 document 拆成"视口内 + 其余"两段，两个异步组件）；
3. **第一块能早多少**（同一构建、开/关两轮实测：首屏"第一个节点画出"提前多少）。

---

## 核对（2026-10-21 晚）：流式可行，但它有一个**前置条件**，而那个前置条件把问题推给了产品

- **技术上可行**：Next 的 RSC 是流式的（`<Suspense>` + 异步 server component）⇒ 文档能分块送。
  团队**用过一次**（`apps/web/src/world3d/WorldWalk.tsx:339`，`fallback={null}`），路由级的 `loading.tsx` **没用过**
  ⇒ 这不是熟路 ⚠️；而且要把 `StudioShell` 的 prop 结构拆开（它是所有 Studio 面板的宿主）⚠️。
- **但流式自己带一个前置条件**：**客户端编辑要全量文档**（布局要重算 ⇒ 见上）
  ⇒ 内容**可能还没到齐** ⇒ 用户一编辑**画布就缺一半** ✗
  ⇒ ⇒ **"文档是否完整"这个状态是流式的前置条件**（编辑前若未齐 ⇒ 要等它 ⇒ 那一次等待就是流式的代价）。
- **⇒ 由此，这一格最终撞上的是一个产品问题**，不是代码问题：
  **"用户打开 Studio，多久开始编辑？"**
  - 若用户**不马上编辑**（先看看/截图/分享）⇒ 首屏**别带**那份 9.37MB（走接口懒加载）就是对的
    ⇒ **ADR-0048 那一刀该做**（它的取舍是"画布内容早 400~850ms vs 容器晚 ~500ms"）；
  - 若用户**马上编辑** ⇒ 首屏**必须**带全量 ⇒ 流式与部分文档都救不了
    ⇒ 只能继续优化"带全量"这件事本身（今天的读已经降到 434ms，剩下的就是序列化与浏览器那一段）。
- **⇒ 这一格该做的不是继续找代码解法，而是把上面这个产品问题问清楚**；
  技术侧同时把**"文档是否完整"**这个状态做出来（它是流式的前置，今天也能独立交付：编辑前确保全量到齐）。

## 后果

- **`packages/design-model/src/partial.ts` 留着，但**它**现在没有接线**
  ⇒ 必须在文档里说清"它是能力，不是已交付的功能"（§159：不拿"有代码"当"做完了"）。
  它将来的用处有两个：① 流式首屏的第一块（视口内那份内容）② 预览/公开页/变体看板
  算"只有视口内"的那一份几何（省 CPU，不改首屏）。
- **首屏那一刀的判决不变**（ADR-0048）：塞文档进 HTML 省的是 HTML 等待，
  首帧一点不早、首次编辑还更慢 ⇒ 默认保持带文档。
- **这一格的方法论又记一笔**：这一串里被否掉的三个方案（塞文档进 HTML / 一页一行 /
  组装挪进 Postgres）与这一条（部分文档），**看起来都最对**；否掉它们的都是
  **"与某个既有前提冲突"**，而不是"实现起来麻烦"。
  ⇒ **找解法之前先把前提列出来**（谁算布局？编辑要什么？），能省掉大量白做的方案。
