# 规模基准（§146 / §147）

`npx tsx scripts/perf-baseline.mts` 造 100 / 1000 / 10000 节点的文档，
对设计模型的每条热点路径取 3 次中位数（先跑一次预热——JIT 没热的第一个数没有参考价值）。

这不是测试：本机 16GB、还跑着一堆容器，把耗时写死成断言只会制造 flaky，而 flaky 的下场通常是断言被删掉。
数字记在这里，回归靠人眼比对。**改热点路径前后各跑一遍**是这一项的纪律。

文档形状：根框 → 容器逐层分叉到第 6 层，叶子是文本与按钮（按钮固定 120×40，
这样"点击目标过小"那条规则真的会被触发，而不是空转）。

**读数纪律**：只有 `execute + undo` 那行落在噪声之外（6.7 倍，见下）。其余路径这一轮代码没动，

真要判回归，同机连跑两遍看是否稳定复现。

## 这一轮实际修掉的两个问题

1. **每次编辑把补丁应用两遍**：`DesignStore.execute` → `runPatches` 先 apply 一次求新文档，
   随后 `buildEntry` 为了求逆和算 diff 又从同一份 `before` 起头 apply 一次。
   现在 `buildEntry` 把过程中的 `cursor` 一并返回，`runPatches` 直接采用——一次编辑一次应用。
2. **`clone()` 用的是 `structuredClone`**：设计文档是纯 JSON（它本来就要过 JSONB 与
   `JSON.stringify`），而 `applyPatch` 每条补丁都整份克隆文档，于是克隆函数就是热点本身。
   换成自写递归拷贝（只对纯对象/数组走快路，`Date`/`Map`/类实例仍回落 `structuredClone`）。
   刻意保留值为 `undefined` 的键与数组空洞——`JSON.parse(JSON.stringify())` 那种"更快的写法"
   会把它们丢掉，undo 之后节点形状就变了（`patch-commands.test.ts` 里有这条回归）。

净效果：一次编辑 + 撤销，100 节点从 4.0ms 降到 0.54ms，10000 节点从 861ms 降到 129ms。

## 2026-09-24：Design Index（§70）的耗时与尺寸（同一脚本新增两列）

`buildDesignIndex` 是每次装配上下文都要走的路径，所以它既进耗时表，也要进**尺寸**表——
§68 那句"别把整个 repo 塞进模型"必须是一个可核对的数字，否则它只是一句口号。

| 节点数 | buildDesignIndex | 目录字符 | 文档字符 | 目录/文档 | 压进 20000 预算后 |
|---|---|---|---|---|---|
| 100 | 0.5 ms | 10,926 | 79,483 | 13.7% | 10,926（没触发裁剪） |
| 1000 | 5.7 ms | 59,238 | 765,284 | 7.7% | 5,343（0.7%） |
| 10000 | 46.5 ms | 714,298 | 7,859,962 | 9.1% | 5,360（0.1%） |

三条读数，其中第二条是对"目录一定小"这个直觉的反驳，所以写下来：

1. **耗时不是问题**：10k 节点 46.5ms，比 `analyzeHealth`（218ms）和一次编辑（129ms）都便宜。
2. **目录本身并不自动小**：不套预算时，10k 节点的目录是 **71 万字符**。"索引过"≠"塞得进上下文"，
   所以 §68 的预算是必需的，而不是装饰。
3. **小文档反而缩得少**：起手页（8 节点）实测 **7,047 / 9,882 字符 = 71.3%**。
   因为目录要把 34 个 token 与全部跨引用边逐条列出来，这部分是**按项目**而非按节点数增长的。
   同一份起手页把预算压到 3,000，`fitIndexToBudget` 会裁到 5,473 字符并如实写出
   「即便只剩骨架仍是 5433 字符：预算 3000 比这份项目的最小目录还小」——
   压不下去时它报告压不下去，而不是假装到了预算内。

预算取 20000 的理由与取舍见 `docs/adr/0006-design-index-char-budget.md`。

## 2026-09-24：持久层第一次进表（真实 Postgres，10k 节点）

上面所有数字都是**内存里的文档**。这次把同一份 10k 节点文档真的写进库、再读回来：

| 路径 | 耗时 | 说明 |
|---|---|---|
| `createProject`（含 10k 节点，一个事务） | 2,512 ms | 切块插入之后才跑得动，见下 |
| `loadDocument` × 4 | 206.6 / 198.0 / 205.8 / 180.8 ms | 稳定在 ~200ms，热身后没有下降趋势 |

两条结论，第一条是个已经修掉的**真 bug**：

1. **10k 节点的项目以前根本存不进库**。`writeNodes` 把整个页面的节点拼成一条 `INSERT`，
   节点行 9 个参数 × Postgres 单语句 65,535 参数上限 ⇒ 一个页面超过约 **7,281 个节点**就
   `MAX_PARAMETERS_EXCEEDED`，保存整体失败。§146 的规模目标写的正是 10,000 节点，
   而模型层基准从没把文档写进过库，所以这条断链一直没人碰到。
   现在按 500 行切块（`INSERT_CHUNK`），事务语义不变。回归测试：
   `apps/web/test/projects.integration.test.ts` 的「一个页面 8,000 个节点仍然存得下来也读得回来」，
   反向实验（去掉切块）确认会红。
2. **§68 的服务端装配原本读两次文档**：`buildProjectContext` 内部 `loadDocument` 一次，
   `assembleAiRequest` 为了拿权威文档又读一次 ⇒ 10k 节点上每次 AI 请求白花约 **200ms**。
   现在 `ContextResult` 把装配时读到的那一份带出去，目录与工具文档出自同一次读取（也就必然互相对得上）。

测量条件照实写：本机 Windows + 本地单实例 Postgres（55433），单轮、无并发，
所以这些是"一次操作值多少毫秒"，不是吞吐容量；并发下的表现还没测，因此不写。

## 2026-09-24：Code Index（§69）的耗时与尺寸（同一脚本新增一列）

`buildCodeIndex` 和 `buildDesignIndex` 住在同一条上下文装配路径上（§67），所以也进同一张表。
这一轮整表重跑，前面几列随之更新（本机噪声 ±30%，只读加法与量级）：

| 节点数 | resolveLayout | validateDocument | lintDesign | analyzeHealth | generateProject | buildDesignIndex | **buildCodeIndex** | execute + undo | diffDocuments | 合计 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 100 | 1.1 | 0.6 | 1.3 | 2.6 | 0.7 | 0.5 | **5.5** | 0.2 | 0.7 | 13 ms |
| 1000 | 5.1 | 2.5 | 5.8 | 15.5 | 3.0 | 3.7 | **13.8** | 5.9 | 5.4 | 61 ms |
| 10000 | 53.7 | 30.4 | 50.9 | 175.9 | 29.9 | 29.4 | **161.0** | 168.3 | 68.2 | 768 ms |

代码目录的尺寸（预算 `DEFAULT_CODE_CHAR_BUDGET = 8000`）：

| 节点数 | 目录字符 | 文件 | 符号 | 内部依赖 | 压进 8000 后 |
|---|---|---|---|---|---|
| 100 | 6,128 | 3 | 54 | 1 | 6,128（没触发裁剪） |
| 1000 | 6,133 | 3 | 54 | 1 | 6,133 |
| 10000 | 6,138 | 3 | 54 | 1 | 6,138 |

三条读数，第二条是这一节存在的理由：

1. **耗时几乎全在 codegen 那一趟**：10k 节点 `generateProject` 单独 118.5ms，`buildCodeIndex` 220.9ms
   ⇒ 真实 AST 解析只加约 100ms。它必然 ≥ codegen 本身，因为它读的就是 codegen 的产物（§16 的投影，
   不是第二套对代码的认知）。
2. **目录尺寸与节点数无关，只与页面数有关**：100 → 10,000 节点，目录从 6,128 变到 6,138 字符（+0.16%），
   文件恒为 3 个（tokens.css + 每页一份 `.tsx` + `index.ts`），符号恒为 54 个。
   这一点必须写下来，否则容易反过来说成"代码目录比设计目录小两个数量级，所以它更好"——
   它小是因为**这份投影本来就不按节点展开**（节点在代码里是锚点注释，不是符号），
   而不是因为索引有什么魔法。设计目录会从 71 万字符炸到需要预算，代码目录本来就不会，两者不是一回事。
3. **因此它进上下文是安全的，但"够不够用"要看页面数**：基准文档只有一页。真实项目几十页时
   目录会按页线性增长，8,000 字符的预算就会开始裁人——`fitCodeIndexToBudget` 的裁剪顺序
   （锚点 → 每页前 60 个符号 → 参数 → 文件数）与"压不下去照样报压不下去"的写法，
   和 §70 那一节是同一套纪律。

另有一条**已知断链**（不是性能，但正好被这张表照出来，所以记在这里）：
codegen 把 code-only 区域发成 JSX 里的字符串字面量（`packages/design-model/src/codegen.ts:544`），
所以这些区域的函数**在导出的 `.tsx` 里不是代码**。目录给它们的位置是 `code-only/<页面>/<节点>.<语言>`——
那是我们自己起的寻址名，导出工程里并没有这份文件；这条已经写进 `CODE_INDEX_OMISSIONS`，
不是靠注释留在源码里。上表的文档形状没有 code-only 节点，所以 3 个文件不含这类区域；
带这类区域的核对走断言，在 `apps/web/test/code-index.test.ts` 与 `test/context.integration.test.ts`（真实 Postgres）。

## §147 还没做的部分（别把上面当成"大项目已优化"）

- ~~**拷贝仍是整份**~~：`applyPatch` 已落地结构共享（写时拷贝 `CopyOnWrite` 类），
  10k 节点 `execute + undo ×10` 从 657.9ms 降至 **168.3ms**（≈ 3.9×），
  同会话前后对照（`scripts/perf-baseline.mts`），详见 `packages/design-model/test/structural-sharing.test.ts`。
- **持久层还有两处已知但不划算的**：`writeDocument` 里 token 与 component 仍是**一行一条 INSERT**
  （几十条时无所谓，几百条就会变成 2.5s 里可见的一段）；`loadDocument` 按页面逐页查节点（N+1），
  页面数上去以后每页一次往返。两者都不影响正确性，等真的被量到再改。
- **画布侧没有虚拟化 / 增量渲染**：`resolveLayout` 每次改动重排整页（10k 节点 ≈ 98ms），
  Studio 现在靠"一次只改一个节点"掩盖它；真正的 §147 要按视口裁剪 + 脏子树重排。
- **没有 worker**：排版与体检都跑在主线程上。
- **健康层每次改动全量重算**（`analyzeHealth` 10k 节点 ≈ 218ms）：只在「健康」页签或 Publish 弹层打开时发生，
  但文档大了要改成防抖或增量（`analyzeHealth` 已接受外部传入 `layouts`，就是为了那一天）。
- 浏览器端指标 — `npm run perf:browser`（`scripts/perf-browser.mts`）。建真项目、在真 Chrome 里量
  首帧（画布出现第一个节点）、pan/zoom 帧距与 >33ms 的帧、属性写入到画布重绘的延迟；
  每档 3 次，去掉第一次预热取中位数。

  **2026-09-24 的一次自我更正，值得记下来**：这张表最初记的"120 / 1000 / 4000 节点"三档数字
  全是无效的。压测脚本造节点时手写了一份字面量，缺 `style.cornerRadius` 与 `layout.padding`；
  那种文档能写进库、也能读出来，但健康度（`lintDesign`）与排版（`resolveLayout`）会在
  `Object.entries(undefined)` / `padding.top` 上抛，React 整棵树挂掉——
  于是画布始终只有起手那 8 个节点，而脚本打印的"节点数"取自**客户端自己加了多少**，
  看起来像 4000 档，量的其实一直是 8 个节点的画布。首帧 326ms、属性写入 33.6ms 那些数就是这么来的。

  现在脚本自己核对两件事：写完后**从服务端读回来**数节点数，以及**画布 DOM 里真渲染了多少**，
  两个数对不上就直接报错终止（"压测没生效：文档里 N 个节点，画布只渲染了 M 个"）。
  造节点也改成克隆一个已存在的合法节点，不再手写字面量。

  修好之后第一次真数据（同一台机器，dev server）：

  | 指标 | 起手 8 节点 | 1000 节点（画布 DOM 确实 1000 个） |
  | --- | --- | --- |
  | 首帧（出现第一个节点） | 345–418ms | 904.9ms（913.1 / 896.6） |
  | pan 平移 p95 帧距 | 12–18ms | 139–176ms |
  | pan 平移 >33ms 的帧 | 0 / ~280 | 40 / ~235 |
  | 图层树行数 | 7 | 999 |

  读法与限定（比数字重要）：
  ① **首帧量的不是"整页画完"**，是壳子挂载 + 首个节点出现，所以它对文档大小不敏感；
  ② **本机 rAF 不锁 vsync**（有头模式也一样 6.1ms），帧距不能当 fps 读；有意义的是
  `>33ms 的帧` 与 p95——1000 节点那档 p95 从十几毫秒跳到 140–176ms、每次平移掉 40 帧，
  这才是 §147 说的"没有虚拟化"的代价，也是接下来做视口裁剪的依据；
  ③ 属性写入延迟跨运行能抖到 2 倍，单次数字不足以支撑"优化前后"的结论，要比就同一天连跑取中位数。
  模型层那边同一份文档 resolveLayout 只要 17ms（1000 节点），所以瓶颈在 DOM/渲染，不在排版计算。

  **§147 视口裁剪落地后的复测（同一天，同一台机器）**：画布只把视口（外扩 256）内的节点放进 DOM，
  1000 与 4000 节点两档的画布 DOM 都稳定在 **18 个**（此前是 1000 / 4000 个），
  画布右上角写明"画布按视口裁剪：显示 18 / 1000"。pan 平移的 p95 从 139–176ms 降到 115–127ms，
  但 **>33ms 的帧数一点没变（40/235）**——所以"掉帧"这件事不是 DOM 节点数量造成的，别这么宣布胜利。

  更该记的是没赢的那部分：**4000 节点那一档首帧没量到**（等 180 秒页面仍没画出第一个节点），
  而同一档的图层树列出了 **3999 行**。也就是说画布裁完了，页面还是打不开——
  下一个瓶颈在图层面板那种"把整份文档渲染成一列 DOM"的地方，以及 4000 节点的载入本身。
  这条已开成任务，没测到之前不会写成"§147 完成"。

## 2026-10-10：§147 两扇门的归因——选中响应的地板在浏览器，不在界面

问题：`docs/TESTING.md` 的「选中响应 <16ms」在 1000 档实测 44ms 上下，五个月没动过。
先归因再优化，这一轮只做归因（`store.ts` 的 `select` 加了 dev 专属的
`nexus:sel:store` / `nexus:sel:commit` 标记，`scripts/perf-browser.mts` 的选中探针拆成
「派发+命中 / 界面提交 / 渲染+绘制」三段，`PERF_PROFILE=1` 多跑一次选中交互的 CPU 采样）。

生产构建同会话两遍（`PERF_LABEL=prod-62b-profile`，1000 档，去掉第一遍）：

| 指标 | 读数 | <50ms 门 | <16ms 门 |
|---|---|---|---|
| 属性写入 → 画布更新 | **21.5ms**（22.4 / 20.7） | **进** | — |
| 选中响应（驱动器全程） | 44.7ms（40.6 / 48.8） | — | 红 |
| 选中响应（页面内，同段） | 58.6ms（55.4 / 61.8） | — | 红 |
| 首帧 | 685.5ms（765.0 / 605.9） | — | — |
| pan 中位帧距 | 6.1ms | ≥55fps 达标 | — |

归因三条，都不是猜的：

① **选中窗口里没有界面自己的 CPU**。CPU 采样（200µs 间隔）：选中交互窗口命中 30 个样本，
   **83% idle、17% program、0 个应用函数命中**；属性写入窗口同理（124 样本，83% idle，
   剩下的是 zod 与 React fiber 的各 1.6%）。也就是说那 44ms 里几乎没有一个毫秒是
   界面代码在算——它在等浏览器把「输入 → React 调度 → 绘制 → 探针看见」走完。
② **驱动器不是成本**。同一次交互在开发口径下分两段量：驱动器全程与页面内同段只差 ~6ms
   （131.5 vs 125.5），Playwright 的 `mouse.click` 派发不解释那 44ms。
③ **派发与命中测试也不解释**。init 脚本里的 pointerdown 捕获标记证明：进入
   `store.select` 之前只过了几毫秒；store 自己的提交（选择 + 快照）在开发口径下是
   `__studioPerf` 里 `整段 1ms` 那一档。

**结论（这一轮的账面）**：选中响应 <16ms 这扇门，按现在这个探针量的是
「输入事件 → 手柄出现在 DOM」，其中 2–3 个合成帧（16.7ms/帧，headless 不锁 vsync 也快不过
调度）就是地板——**门的地板本身高于门的数字**。要证明"界面更快"只能量界面那一段
（新标记已经在了），或者在页内用 `performance.measure` 把 React 的 commit→paint 段单独算。
**下一轮（安静机器上）先补测分段读数，再决定要不要动界面**；本轮机器被两个自会计话占着
（同期 pan 的 >33ms 长帧从 0 涨到 28/342），绝对数都按记账带口径，不做跨会话相减。

10000 档这一轮在生产构建下 **没量到**：`page.goto` 30 秒超时（首屏 SSR 8.4MB 文档 +
机器负载），脚本如实报错退出——不拿 1000 档的数顶替（§159）。

## 2026-10-10：10000 档属性写入的段位归因——是 `resolveLayout`，占整段 80%+

上一节留的「慢在哪一段」这轮量到了。两处地基：① `next.config.ts` 的 `env` 把
`NEXUS_PERF_SEGMENTS=1` 内联成 `NEXT_PUBLIC_NEXUS_PERF_SEGMENTS`（构建期开关，
生产构建不设就是零成本），`studio/store.ts` 的诊断门从 dev-only 改成
「dev 或显式开关」；② 用这个开关的生产构建重跑 10000 档。

口径 `prod-10k-segments`（每项 3 次去第一遍）：

| 段（10000 档属性写入） | 各次 | 中位 |
|---|---|---|
| 输入 → 画布更新（总） | 111.4 / 99 / 84 | **91.5ms** |
| `buildSnapshot` 整段 | 84 / 79 / 70 | 79ms |
| ├ **求解 `resolveLayout`** | 83 / 79 / 70 | **79ms（≈100%）** |
| ├ tokens（derivedCache） | 0 | 0ms |
| └ 资产（derivedCache） | 0 | 0ms |
| 一次按键跑了几次快照 | 2 / 2 / 2 | 2 |

结论（三段都对上账）：**这 91.5ms 里几乎整个都是布局求解**——与模型层基准
（`resolveLayout` 10000 节点 57ms，`design-model` 的 §147 一节）同量级。
derivedCache 的命中是有效的（tokens/资产 0ms），ADR-0027 的 layout 复用也是
（pan 中位帧距 6.1ms，没随求解抖）——**卡住的只有"一次编辑触发的全量重解"**：
第二次快照与第一次同 revision（layoutCache 的键只比 revision），却仍然付了一次
79ms——要么键没覆盖这条路径，要么同 key 的 cache 没落住（这要到 `resolveFor`
里核，不猜）。首帧 1333.5ms 与上一轮（1213.3）同量级，堆 80MB（比上一轮
110MB 低——分段那次跑的时候负载不同）。

**下一格的动作由此确定**：让一次编辑只解算受影响的子树（增量重解），
或先把 layoutCache 的命中做实（第二次快照不该再解）。两者都在
`packages/design-model` 的 `resolveFor`/`resolveLayout` 一侧，纯函数可单测——
**红线照旧是数**：改完同一口径重跑，总延迟应从 91.5ms 掉到一次求解以下。
