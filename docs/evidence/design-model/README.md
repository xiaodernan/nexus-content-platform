# @nexus/design-model — evidence for v231 (the instance-override `text` sibling folded into the per-child patch)

_Numbering note: design-model is the canonical model (ADR 0004) that the Studio slice (M1) and the
three-runtime / agent-runtime lanes all read. Its increments here are the ones whose correctness is a
model decision rather than a feature of a consumer, so they are titled in this corpus directory rather
than buried in a consumer's README._

**v231 — `InstanceNode['overrides']` could not express a text override; the `text` sibling is folded into the per-child patch (ADR 0016 amendment 231, plan item 17).** The old shape reserved a `text` sibling on the overrides map — `overrides.text = { [masterId]: 'words' }` — which (a) forced a cast on every writer and on `readOverrides` itself (the test carried the same cast, with the reason written down), and (b) made a master child literally named `text` unreachable for geometry patches because `readOverrides` skipped that key. The canonical decision: an override IS a patch, so `text` is just another patchable field — `InstanceChildOverride` now carries `text?: string` and `InstanceNode.overrides` is `Record<NexusId, InstanceChildOverride>` with no reserved key and no index-signature trap. The text still applies only when the clone is a text node. Legacy snapshots are a lossless ENCODING (the same data under a different key), so `normalizeInstanceOverrides` folds the sibling on READ instead of orphaning every local document behind a `SCHEMA_VERSION` bump — `persist.ts` refuses unknown versions, so a bump would throw away saved work. The one genuinely ambiguous shape (a child named `text` carrying a text-only patch) folds correctly because the new key IS `text`. Measured: design-model 34/34, tsc 0 (dist rebuilt); Studio 484/484 (31 files), tsc 0 (Studio reads the rebuilt dist); the cast is gone from `instances.test.ts`.

**v243 — `validateDocument`: the internal-consistency check the normalized graph always claimed.** _Ledger note: this increment's ADR entry is deferred — the ledger file held another lane's uncommitted amendment, so appending would stage their work; the record lands when that entry commits. The title below names the version, so it takes effect then._ Every path that brings a document INTO the model from outside (a remix, a snapshot, an AI batch, edited JSON) handed it straight to the store and the renderer; a malformed graph draws something subtly wrong rather than crashing. `validateDocument(doc: unknown)` answers a VERDICT — a LIST of named problems, never a throw — so a caller shows a person what is wrong (the `normalizeHandle` rule, applied to a graph). It pins the model's own conventions, three of which are easy to get wrong: a document's children live on the **root node's `pageIds`** (the first draft checked `doc.pageIds` and the probe caught it — every real document failed); a document's `childIds` is a REQUIRED-but-DEAD field that must stay empty; and **`pageIds` is misnamed — it holds PAGES and component MASTERS** (a master is added under the root, so it lands there beside the pages; consumers filter by `type`, which is why this was never visible — recorded as a bound, not repaired). It names: `root-missing`/`root-not-document`/`root-has-parent`, `document-child-ids-used`, `node-id-key-mismatch`, `node-without-parent`, `parent-missing`, `child-missing`/`child-parent-disagrees`/`duplicate-child`/`self-child`, `active-page-missing`/`active-not-page`, `parent-does-not-list-child`, `cycle` and `unreachable`. Wired into the remix lane (v233): a publication whose graph is inconsistent is now refused BY NAME instead of loading. Measured: design-model 40 → 51 (validate.test.ts 11 cases), tsc 0; Studio 516 → 517, and `docs/evidence/design-model/validate-proof.mjs` 4/4 (§1 accepts what the model produces · §2 refuses 14 malformed shapes by code + unreachable · §3 total + non-mutating · §4 the consumer refuses a graph-inconsistent document).
