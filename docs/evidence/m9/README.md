# M9 evidence — the ops line

M9 is NEXUS Ops: the observability the repository has owed since the ROADMAP's first line ("observability").
The service half of it landed in v271 — the audit trail — and the reading half in v272. What is graded here is
the **contract between the two**: the client's own model and the service's own wire, read from the source
files that define them.

## `audit-contract-proof.mjs` (M9 v273 — ADR 0016 amendment 273)

```
node docs/evidence/m9/audit-contract-proof.mjs
```

It needs **nothing but Node** — no Java, no Maven, no Docker, no database, no running service. That is not a
shortcut; it is the point. The claim being graded is a claim about **two source files**, so the two source
files ARE the fixture:

| § | what it proves |
| --- | --- |
| 1 | the service's wire record has **six fields, in order**, read out of the Java `record` — and the instant is a `long`, so epoch **milliseconds** |
| 2 | the client's model declares the **same six fields, in the same order, all required** |
| 3 | the two fields that are **nullable on the wire are nullable in the client** — `actorId` and `assurance` |
| 4 | the four fields that are **not** nullable on the wire are **not** nullable in the client — the fix widened two fields, not all six |
| 5 | the client's own type **accepts what the service really sends** — an anonymous entry (`actorId: null`, `assurance: null`), a named one, and a verb this build has never heard of — checked by the **TypeScript compiler itself**, over the **shipped** `ops.ts` |
| 6 | an anonymous entry belongs to **no account**: it lands in the reserved `__anonymous__` bucket, never in a real account's |

### Why it is worth a file

v271 built the service's door and shipped a client model beside it that **disagreed** with it on the two
fields that matter most: the service sends `null` for an anonymous action, and the client's `AuditEntry`
declared both non-null. The service refused to fake an actor to fit a type, and the client model's own
docstring had to admit it — "the one place the client's `ops.ts` type is wrong (`actorId` declared
non-null)". A type that is wrong in a comment is still wrong.

The proof reads the field list **out of the source** rather than restating it. A proof that compares a
hand-written list with a hand-written list proves only that two people typed the same thing; this one
parses the Java `record` and asks the TypeScript compiler what the interface means, so a change on either
side has to change the other.

### It has been shown to FAIL

A green proof nobody has seen go red is decoration. Three mutations were run against it, and each is caught
by a **different** section:

| mutation | caught by | the message |
| --- | --- | --- |
| `actorId: AccountId \| null` → `AccountId` | **§3** | `AuditEntry.actorId must accept null — the service sends null for an anonymous action, and a type that refuses null is a type the service has to lie to satisfy` |
| `assurance: Assurance \| null` → `Assurance` | **§3** | the same, for the assurance |
| the `string & Record<never, never>` arm removed from `AuditAction` | **§5** | `Type '"stake"' is not assignable to type 'AuditAction'` — the compiler, not a hand-written imitation of it |

§3 catches the narrowing of the two nullable fields; §5 catches a type that is closed to the verbs a
**separate deployable** may add. Neither would be caught by the other.
## the ARTIFACT PAGE’s own history (M9 v280 — ADR 0016 amendment 280)

**The gap.** v272 put the trail in the Studio’s toolbar: every entry, newest first, for the author to read. But the toolbar answers "what happened to the publications" and the ARTIFACT PAGE answers "what is this" — and a reader who opens a publication had no way to ask "what happened to THIS one?". The trail’s whole value is that it outlives the row it witnessed (v272’s proof: the publication answers 404 and its entries remain), and the place where that matters most is the publication’s own page.
**Two new modules, both in the shape every lane here has.** `history.ts` is PURE: `historyRowsOf(entries, targetId)` filters the trail to ONE publication (exact match on the target, order preserved — the trail’s order is part of what it asserts) and `renderHistoryHtml(rows, carried)` renders the section. `auditServer.ts` is the server-side half: it reads the service’s `GET /audit` and answers with a REASON rather than a thrown error, because an artifact page that says "the history could not be read" is an honest page and one that throws into a route handler is a 500.
**A failed read does NOT take the page down.** The artifact page reads the publication and the trail independently, and a trail that could not be read leaves the artifact intact with no history section at all. An artifact that 500s because the TRAIL was unreachable would make the publication unreachable for a reason that has nothing to do with it — and an EMPTY history is not inserted, because a heading with nothing under it would read as "this publication has no history", which a failed read knows nothing about.
**The count of the WHOLE answer is stated beside the rows.** The trail is capped, so an old publication’s entries can be past the cap — and a reader must be able to tell "this publication has one entry" from "the answer was cut short before this publication’s entries appeared". The section says both numbers, and says the cap when the two disagree.
**The page says what "no history" does not mean.** A publication published before the trail existed has no entries at all, and the empty state says that — "no audit entries name this publication. That is not the same as ‘nothing happened’". A page that implied nothing happened would be making a claim the service never made.
**The styles travel with the section.** The artifact page’s shell belongs to the PREVIEW renderer; the history is a guest in it, and a guest that assumed it could restyle the host would be a guest that could break the drawing. The section carries its own scoped styles.
**Files.** `apps/studio/src/lib/history.ts` + `history.test.ts` (new — the pure filter and the section, 13 cases), `apps/studio/src/lib/auditServer.ts` + `auditServer.test.ts` (new — the server-side reader, 6 cases), `apps/studio/src/app/p/[projectId]/route.ts` (reads the trail server-side and injects the section).
Measured: `apps/studio` **951/951 (51 files)**, `tsc -p apps/studio/tsconfig.json` **exit 0**, doc gate **exit 0**.
**Bounds (§60).** The trail records what **happened**, and a refused verb is not in it. The page shows only the entries that NAME this publication — an entry names one project id, and a row that named none belongs to no publication. The trail is capped, so an old publication’s entries can be past the cap; the page says so rather than presenting a partial history as complete. The service **verifies nothing** (ADR 0018), so the assurance beside an actor is the entry’s own statement of what the claim was worth. The service offers **no truncation**, and the trail grows forever.
## the trail’s FILTERS and its TALLY (M9 v281 — ADR 0016 amendment 281)

**The gap.** The trail panel (v272) showed every entry, newest first, in one list. That is the honest and complete thing to show — but a reader with a question ("what was taken down?", "how many times was this published?") had to read the whole list and count it themselves. A list that cannot be narrowed is a list that makes the reader do the work the system already did.
**The TALLY, counted from the rows the answer carried.** `trailSummaryOf(rows)` counts publishes, take-downs, and — importantly — an `other` bucket for any action this build does not know. A verb this build does not recognise is NEVER folded into a verb it does: if a `follow` ever arrived (it is in the client’s model, not in the service), a summary that said "3 published" when one was a follow would be a lie. The tally is over ALL the rows, not the filtered ones — the filter narrows the LIST, so a reader can always see what the filter is hiding.
**The FILTERS, in the trail’s own language.** `filterTrailRows(rows, action)` matches on the service’s word (`publish` / `unpublish`), NOT on the display verb ("published" / "took down"): the display verb is a rendering choice, and a filter that matched on it would break the day the wording changed. The panel carries three controls — All, Published, Taken down — and a filter that matches nothing says "no entries of that action" rather than falling back to the whole list.
**THREE numbers in the footer, because there are THREE questions.** What is SHOWN (the filter admits), what could be RENDERED (the reading half accepted), and what the SERVICE says it carried. The last two are the v272 drop-check, unchanged: renderable can never exceed the service’s count, and a smaller number is exactly the discrepancy the footer exists to expose. The first differs from the second whenever a filter is on — which is the filter working, not a discrepancy.
**The proof grades the filter, not just the list.** §9.6 in the real-browser harness: the panel states the tally; the take-down filter shows ONLY take-downs and FEWER rows than the whole trail; the publish filter shows ONLY publishes; and ‘All’ puts every row back — because a filter that could not be undone would be a trap.
**Files.** `apps/studio/src/lib/trail.ts` + `trail.test.ts` (the tally and the filter, +6 cases), `apps/studio/src/components/Toolbar.tsx` (the filter controls, the tally line, the three-number footer, and the `data-trail-action` attribute on each row), `tools/harness/studio-publish.mjs` (a new §9.6).
Measured: `apps/studio` **957/957 (51 files)**, `tsc -p apps/studio/tsconfig.json` **exit 0**, doc gate **exit 0**.
**Bounds (§60).** The filters narrow the LIST; they do not re-ask the service. The trail the panel holds is the newest window the service returned, and a filter over a window cannot reach past it. The tally counts what the answer carried, not the whole trail — the service’s own count is stated beside it. The service **verifies nothing** (ADR 0018), so the assurance beside an actor is the entry’s own statement of what the claim was worth.
## the SOCIAL verbs join the AUDIT TRAIL (M9 v289 — ADR 0016 amendment 289)

**The gap.** The trail recorded what happened to the PUBLICATIONS — a publish, a take-down — and the three social actions (like, comment, follow) happened to publications too, without a word in the trail. A reader asking “what did people DO with this publication?” had to read the like bar and the comment thread separately, and neither of them was a record: a panel is a view of NOW, and the trail is a record of WHAT HAPPENED.
**The service writes, and the trail’s OWN rules hold for the social verbs.** (1) **Only a SUCCESSFUL mutation is recorded**: a refused like (no account) and a refused comment (blank body) write nothing, and the cases say so. (2) **A mutation that changed NOTHING is not recorded**: a SECOND like finds the row the first one wrote and changes nothing, so it writes nothing — the trail records what HAPPENED, not what was attempted, and a trail that recorded the second like would be recording an attempt. (3) **The write joins the caller’s transaction** (the default propagation, as in v271), so a rolled-back like leaves no entry claiming a like happened.
**The un-verbs are recorded too, and they are NOT folded into the verbs.** A like that is taken back is something that happened, exactly as a publication that is taken down is: the service writes `unlike` and `uncomment`, and the trail’s words are “took the like back” and “removed the comment”. Merging them into the verbs would lose one of the two facts, and a reader asking “did they take it back?” deserves an answer.
**A FOLLOW is NOT in the trail, and the reason is the trail’s own.** The trail’s target is what the event happened TO, and for a publication that is a project id — the panel links it to `/p/<target>`, and the artifact page’s HISTORY filters by it. A follow’s target is an ACCOUNT, and a target field that meant two things would break both readers. The follow is left out and said so, rather than squeezed in where it would lie.
**The client LEARNS the verbs.** The trail’s display words, its tally buckets (`liked`, `unliked`, `commented`, `uncommented`) and its FILTERS all grow with the service: a like has its own bucket rather than falling into “other”, because a tally that called a like “other” would be hiding the very thing the panel is for. And the tally says only the buckets that are NOT zero — a line that always carried every bucket would grow a dozen “0 took down”s and a reader would learn to skip it.
**Files.** `services/nexus-api/src/main/java/dev/nexus/api/social/LikeService.java` (records `like` and `unlike`), `.../social/CommentService.java` (records `comment` and `uncomment`), `.../social/LikeServiceTest.java` and `.../social/CommentServiceTest.java` (the trail’s rules for the social verbs, +5 cases), `apps/studio/src/lib/trail.ts` + `trail.test.ts` (the words, the buckets, the tally text, +4 cases), `apps/studio/src/components/Toolbar.tsx` (the tally line and the Liked / Commented filters), `tools/harness/studio-publish.mjs` (a new §13).
Measured: `apps/studio` **1019/1019 (55 files)**, `tsc -p apps/studio/tsconfig.json` **exit 0**, the service’s social package **48/48** (17 like + 19 comment + 12 follow), doc gate **exit 0**. The real-browser E2E **102/102** with the new §13 (the trail re-read and carrying the social verbs: the tally names them, the rows carry them, and the Liked filter narrows to them).
**Bounds (§60).** A follow is NOT in the trail (its target is an account, and the trail’s target is a publication). The trail records the SOCIAL verbs but not every verb the product has: a moderation action, a report, or a tip would each need a target and a rule before they could be written down, and the service does not invent rules it has no policy for. The trail is still capped and still append-only, and the service still offers **no truncation**. The assurance beside an actor is the entry’s own statement of what the claim was worth (ADR 0018), and nothing here makes it worth more.
## the TRAIL’s contract proof: the shapes that read the wire, checked against the wire (M9 v291 — ADR 0016 amendment 291)

**The gap, and it is not academic.** The v273 contract proof grades the client’s `ops.ts` against the service’s wire record. It does NOT grade the modules the TRAIL actually reads through — and the trail’s mapping **DROPS a row it cannot validate**: `toTrailRow` returns null for a row missing an id, an action, a target or a finite instant. So if the service RENAMED a wire field, the trail would not crash and would not complain: it would quietly render FEWER rows, and a rename of `assurance` would leave the trail showing rows with no assurance beside them — which reads as a fact rather than as a bug. A promise nobody checks is a comment, and a DROPPED ROW is the quietest kind of promise broken.
**What the proof reads, and why it reads the SOURCE.** The service’s wire record is parsed out of the Java (a hand-written field list would make the proof assert the thing it is supposed to check), and the client’s two shapes are parsed with the **TypeScript compiler’s own parser** — the trail’s input shape in `trail.ts` and the server lane’s declared shape in `auditServer.ts`. Three source files, and the claim being graded is a claim about three source files, so the source files ARE the fixture: no service and no database are needed.
**What it asserts, in order.** §1 the wire record’s six fields, in order, with the instant a `long` (epoch milliseconds) and the two nullable ones Strings. §2 every field the TRAIL reads is a field the service SENDS, AND every field the service sends is read by the trail — the second half is the one that matters: a field that arrives and is never looked at is a field the trail silently drops. §3 the same for the server lane. §4 the two client shapes name the SAME fields, because two client types for one wire shape is one more place for them to drift apart. §5 the reader is shown to FAIL: renaming a wire field in a COPY of the service’s source leaves the trail reading a field the service no longer sends, and the proof says so.
**Files.** `docs/evidence/m9/trail-contract-proof.mjs` (new — the proof), `package.json` (the `verify:trail-contract` script).
Measured: `node docs/evidence/m9/trail-contract-proof.mjs` **exit 0** (all five sections, and the mutation caught), and `npm run verify:trail-contract` runs the same thing.
**Bounds (§60).** The proof checks the FIELD NAMES and the nullability of the two nullable ones — it does not check the VALUES, because a value’s correctness is the service’s business and its own tests. It checks the shapes the trail READS; a module that reached the wire through some other path would need its own check, and the proof says which files it grades so that a new reader knows what it is covering. The proof does not replace the v273 contract proof — the two grade different files, and both are needed: one for the client’s declared model, one for the code that actually reads the answer.
## the SOCIAL verbs’ contract proof, on ONE reader (M9 v293 — ADR 0016 amendment 293)

**The gap.** The v273 proof grades the client’s declared `ops.ts` model; the v291 proof grades the TRAIL’s shapes. The three social verbs had no cover: the like, the comment and the follow each have a client shape that the service’s wire record does not check — and the failure mode is the same quiet one. The social mappings DROP rows they cannot validate (a comment with no body, a follower with no id), so a renamed wire field would not crash anything: the client would quietly show FEWER rows, and a renamed `handle` would leave the follower list showing account ids with no names — which reads as a fact rather than as a bug.
**ONE reader, shared.** The proof’s reading machinery now lives in `docs/evidence/m9/wire-fields.mjs`: a Java `record’s field list parsed from the Java, and a TypeScript interface’s field list parsed with the **TypeScript compiler’s own parser** — because a proof that compares a hand-written list with a hand-written list proves only that two people typed the same thing. Two copies of a reader is two places for a reader to be wrong, and the whole point of these proofs is that a reader is CHECKED: the v291 proof was refactored onto the shared reader, and the new social proof sits beside it.
**What it asserts.** §1 the three verbs’ client shapes and the service’s wire records name the SAME fields — symmetrically: a client that reads a field the service does not send reads nothing, and a field the service sends that the client never reads is a field that arrives and is thrown away. §2 the instant is a `long` of epoch MILLISECONDS on the wire and a number on the client — the same unit on both sides, which is the check that would catch a service sending SECONDS (the v263 incident). §3 the reader is shown to FAIL: renaming the follow’s `handle` leaves the client reading a field the service no longer sends.
**Files.** `docs/evidence/m9/wire-fields.mjs` (new — the shared reader), `docs/evidence/m9/social-contract-proof.mjs` (new — the proof), `docs/evidence/m9/trail-contract-proof.mjs` (refactored onto the shared reader), `package.json` (the `verify:social-contract` script).
Measured: `node docs/evidence/m9/social-contract-proof.mjs` **exit 0** (all three verbs agree, the instants are the same unit, and the mutation is caught), `node docs/evidence/m9/trail-contract-proof.mjs` **exit 0** after the refactor, and `npm run verify:social-contract` runs the same thing.
**Bounds (§60).** The proof checks the FIELD NAMES and the instant’s unit — it does not check the VALUES, because a value’s correctness is the service’s business and its own tests. It grades the shapes the social lanes DECLARE; the loose input shapes the mappings validate (the ones that drop rows) are a second surface, and the mapping’s own dropping is graded by the unit tests rather than by this proof. The proof does not replace the v273 or v291 proofs — the three grade different files, and all three are needed.
## the ECONOMY panel becomes REAL: the tips this account was given (M9/v299 — ADR 0016 amendment 299)

**What changed, and why it took five increments to get here.** v274 added the panel and found that there was nothing behind it: no economy endpoints existed, so the panel said ‘the economy door is not built’. That was honest, and it stayed honest for five increments — until v297 gave the service a tips table and v298 gave the profile its bar. Now the panel shows the REAL numbers: the tips the device’s account was given and the total they came to.
**The total is the SERVICE’s number** (the DATABASE’s sum over the whole history), reported unchanged. A panel that added to the count would be showing a number the service never said — and the count it read (the window) and the total it knows are DIFFERENT numbers when the history is longer than the window, so the panel says both.
**The panel asks WHO IT IS WHEN IT OPENS, not at render time.** The account can be set (or changed) after the toolbar last rendered, and a panel that asked ‘who am I’ when it mounted would answer for an account that no longer exists. This was found by the real-browser proof: the panel said ‘this device has no account’ for a device that had one.
**And it says what has NOT been built.** The SUBSCRIPTIONS still need a PLAN CATALOG — who sets the price and the period — and that is a product decision this build has not made. The panel says so in words instead of showing a fake ‘no subscriptions’ as though the feature were there and empty: a reader who saw ‘no subscriptions’ would conclude that nobody subscribes, which is a different claim from ‘subscriptions are not built’.
**Files.** `apps/studio/src/app/api/tips/route.ts` (the door learns to READ as well as to write), `apps/studio/src/lib/tipLane.ts` (`readMyTips`), `apps/studio/src/components/Toolbar.tsx` (the panel reads the real tips, asks who it is when it opens, and names the subscription gap), `tools/harness/studio-publish.mjs` (the §17 checks for the panel).
Measured: `apps/studio` **1063/1064 (58 files)** — the one failure is a concurrent lane’s in-flight `probe293`; `npx tsc -p apps/studio/tsconfig.json` **exit 0** for this lane’s files, doc gate **exit 0**; the real-browser E2E **135/135** (the panel shows ¥5.00 received and names the subscription gap).
**Bounds (§60).** The panel shows the tips RECEIVED, not the ones GIVEN — the service’s read door answers for a recipient, and a second read for the payer would be a second question the panel has no rule for yet. The total is over the WHOLE history while the count is over the window, so the two can differ and the panel says both. A tip is a RECORD of a gesture and never a payment (ADR 0018). The subscriptions are not built, and the panel says so rather than pretending.

## the trail's target carries its KIND (M9 v384 — ADR 0016 amendment 374)

**The gap.** An audit entry's target is an id, and an id alone does not say what it names. Every verb this build records targets a publication — and the day a follow or a tip is written down, a reader must be able to tell an account from a plan from a work.
**Declared, never guessed.** The parallel lane's first attempt classified the target by SNIFFING THE ID'S PREFIX — a rule that could never fire here (accounts are `acct-…`; plan ids are a creator's own choice of word). The completion makes the kind a DECLARATION: `AuditService` owns a closed set of three (`account`, `plan`, `publication`), refuses an entry that names no kind or a fourth one BY NAME, and every call site now says which kind it acted on. The column and the wire field are never null.
**The client learns it symmetrically.** `ops.ts`'s `AuditEntry` gains a REQUIRED `targetType` (the service always sends it; a client that treated it as optional would declare a shape the wire never has). `trail.ts`'s row carries the kind, DROPS a row that cannot say it (the panel's count discrepancy makes the drop visible), and spells the three the way a person would say them — an unknown kind passes through, the same rule the action keeps.
**And the test the suite cited since v289 exists at last.** `LikeServiceTest`'s javadoc has pointed at `AuditServiceTest` since v289 — a file that did not exist. Eight cases now grade what `AuditService` refuses and stores.
**Files.** `ops/AuditEntry.java`, `ops/AuditService.java`, `ops/AuditController.java`, the five services' call sites, `social/ReportEntry.java` + `ReportRepository.java` + `ReportService.java` (the filed list narrows by kind, the property in the finder's NAME so the derivation binds it), `apps/studio/src/lib/ops.ts` + `auditServer.ts` + `trail.ts` (+tests), both contract proofs (the seven-field shape), `AuditServiceTest.java` (new).
Measured: the service **240/240**, studio affected files **90/90**, `tsc` exit 0, trail-contract proof exit 0, audit-contract proof exit 0, social-contract proof exit 0.
**Bounds (§60).** No verb targets an account or a plan yet — the kinds are on the wire, and the first writer of an account-targeted entry is a future increment. The filed-list kind filter is on the wire with no panel control yet. The service verifies nothing (ADR 0018): the kind is the caller's declaration.


## the trail's filter is the SERVICE's (M9 v385 — ADR 0016 amendment 378)

**The gap.** The trail panel's filter narrowed the rows the browser already held (v281). That is honest about the window it has and silent about everything past the cap: with the trail capped at a hundred and the panel asking for twenty, "the newest 20 that happen to be take-downs" is a different set from "the newest 20 take-downs" — and the desk had already learned this (v326). One question, asked in two places, is a question that can start answering itself two ways.
**The ask moved.** `GET /audit?action=…` narrows IN THE QUERY: `AuditService.list(limit, action)` picks the finder by whether an action was named, and the window it answers with is the newest N of THAT action. The verbs are a CLOSED SET — the nine this build records — and one outside it is REFUSED BY NAME before any window is read, the same way the desk refuses a reason it does not have: answering a question about a verb this service never recorded with an empty window would read as "nothing of that action ever happened".
**What a service-side filter costs, and who pays it.** The browser no longer sees the rows the filter excluded, so the panel's own tally can no longer count what the filter is hiding — the property v281 had given it for free. The service now answers a THIRD number beside the window (`total`: how many the whole trail holds, narrowed or not), and the footer states it: "N shown · the service carried M · the whole trail holds T · the service caps at L". Four numbers, four questions. The desk's tally door (v312) is the same idea for the same reason.
**The browser half got simpler, not just re-wired.** `filterTrailRows` — the client-side filter, with its tests — is RETIRED: one job done in two places is a job the two places can disagree about. The lane's `readTrail(limit, action)` carries the ask, the Studio route forwards it verbatim, and a refusal's NAME travels back through the route's 503 so the panel says why rather than "HTTP 400".
**Files.** `ops/AuditService.java` (the closed set, `requireAction`, `list(limit, action)`, `count`), `ops/AuditEntryRepository.java` (the filtered finder), `ops/AuditController.java` (the parameter, `total`, the 400 that names the set), `apps/studio/src/lib/auditLane.ts` + `app/api/audit/route.ts` (the ask travels, the answer's third number comes back), `components/Toolbar.tsx` (the buttons re-read with the action named; the footer states the whole), `lib/trail.ts` (−`filterTrailRows`), `AuditServiceTest.java` (+6), `auditLane.test.ts` (+3), `tools/harness/studio-publish.mjs` (§9.6 grades that a filtered trail still states the whole).
Measured: the service **246/246 (10 classes)**, `apps/studio` **1282/1282 (67 files)**, `npx tsc -p apps/studio/tsconfig.json` exit 0, audit-contract proof exit 0 with the new §7 (the envelope: entries · count · limit · total, the three numbers REQUIRED in the lane).
**Bounds (§60).** The E2E could not run here — the real-browser harness needs the Java service and Docker, neither of which this machine has; §9.6's new checks are written against the same selectors the rest of the section drives and are graded on the next machine that can. A verb added to the service must join the closed set in the same commit, or the filter will refuse it — the set is the vocabulary, and it grows on purpose or not at all. The filter narrows the window, never the tally's honesty: the tally still counts the rows on the screen and says so ("of these N rows"). And the service still verifies nothing (ADR 0018) — the filter is a question about what was recorded, not a claim about what was true.


## the trail's window can be PAGED (M9 v388 — ADR 0016 amendment 381)

**The gap.** v385 moved the filter into the service and added the whole-trail count, and the panel still asked for the newest twenty and nothing else. The trail is the one table that only GROWS: a reader who wants last month's entries had no way to ask for them, and "the service caps at 20" was the end of the conversation. The filed list had already learned this (v386).
**The page is part of the ask.** `GET /audit?offset=…` in ROWS — the same meaning the filed read's offset has, and the same rows-into-pages translation (v387's lesson applied from the start rather than discovered by the first pager). The lane echoes the window it asked for, so two reads in flight cannot be mistaken for each other's answers; the route forwards the offset with a negative clamped to the first window.
**Two honest endings, because there are two different questions.** With no filter on, the whole-trail count says exactly where the end is, so "Older" is disabled at `offset + carried >= total`. With a filter on, the service never answers the FILTERED set's size — so a window that came back SHORT of the cap IS the end of that action's rows (a service with more would have filled it), and that is what disables "Older" there. A filter change resets the page: the newest twenty of every action and the newest twenty of one action are different sets with different beginnings.
**And the footer says which rows, only when it honestly can.** Unfiltered: "showing 21–40 of 137 · 20 on screen · the service caps at 20". Filtered: "N shown of this action · the service carried M · the whole trail holds T · the service caps at L" — a range would have to be counted against a set nobody counted, so the panel counts what it has and states the whole beside it instead.

## traffic counted where it crosses — a bounded ledger, not a metrics system (M9 v592 — ADR 0016 amendment 546)

**The gap.** The service could say whether it is alive (`/health`), whether it can serve while the database is down (`/health/ready`, `/health/live`), what its JVM holds (`/health/vitals`) and whether deliveries are landing — and nothing about how much traffic it had served, how many answers were 4xx/5xx, or how long they took. Those facts lived only in the proxy. ADR 0037 had named the gap exactly and closed the metrics-system half of the sentence; this slice crosses the count, and no more.

**The door is not the health door.** `GET /health/traffic` answers **200 while the process answers** — with the database STOPPED it answered in **4 ms**, and in **5 ms** after it returned — under `Cache-Control: no-store`, and never borrows a connection. A failing database is not a failing process; a 5xx share is not a 503 the service imposes on itself. `/health` keeps ADR 0030's shape and status; traffic is a third door with a third audience.

**Count where the status is final.** A `OncePerRequestFilter` wraps the whole dispatch and reads the status the response actually carried — framework-produced 404s and thrown exceptions are both counted, and a thrown dispatch records **500** and still propagates. `TrafficMeter.record`/`.snapshot` share one monitor, so both partitions — five status families and five inclusive-top latency buckets — always sum to `requests` on every snapshot; the proof asserts both. Durations are summed in nanoseconds and converted to milliseconds once.

**Bounded memory is the design.** Ten counters regardless of how many distinct paths are asked; exactly 10 ms is `upTo10Ms`, `10 ms + 1 ns` is `upTo50Ms`. No per-path map, no percentile, no history, no reset — and `/health/traffic` counts itself: the answer does not contain the request that asked, and the next one does (measured: requests 5 → 6 after the first read; 6 → 7 with the database down).
