# 撞库场景压力证据 · 登录门时机（2026-11-22 · §STRESS-AUTH）

> 指令第十一条点名「撞库之类的场景」。`scripts/stress-auth-brute-force.mts`
> 对一台在跑的服务连打错误口令，量的是三件事：门**准时**吐 429、429 带
> `retry-after`、门槛**先于**口令比对。

## 读数（13 次错误口令 · 同一个一次性邮箱）

| 项 | 值 |
|---|---|
| 第 1–10 次 | 每 5–35s 一次（那台服务的数据库当时不可达，见下） |
| **第 11 次** | **429** |
| `retry-after` | **595s**（≈ 15 分钟窗口剩余，与 `auth/login` 的 10 次 / 15 分钟一致） |
| 第 12–13 次 | 429（门之后不再放行） |
| 第二个邮箱（同 IP） | 单独计数，**不连坐**（键是 IP+邮箱） |

**结论**：门的时机、退避头、以及"按账号而不是按 IP 一刀切"这三条都成立——
第 11 次准时拦住，`retry-after` 有值，第二个账号照常受理。

## 诚实限度（重要）

- **第 1–10 次回的是 500，不是 401**：被打的那台服务（并行线 `D:\内容创作平台` 的
  `next start`，占着 3100）当时数据库不可达，所以错误口令走到了比对那一步才炸。
  这不影响门的结论（限流计数在比对之前就记了），但**"每次错误口令都是 401"这一条没测到**。
- 机器内存常年 ~1GB：每次登录请求 3–35s，`--n` 只能给到 13。
  吞吐不是本片的主张，**门的时机**才是。
- 未测：成功登录后的会话保持、以及 Redis 后端下的多副本限流一致性（那需要
  `verify:rate-limit` 的两进程既有证据）。

## 复跑

```powershell
npx tsx scripts/stress-auth-brute-force.mts --base http://127.0.0.1:3100 --n 13
# 需要 services/nexus-api 或并行线服务在跑；数据库不可达时前 10 次会报 500（门依然准时）
```

## 第二轮（同日 · 数据库在线 · 修掉脚本自己的 CSRF 缺陷）

上一轮"第 1–10 次是 500"是那台服务的数据库不可达，不是门坏了；这一轮打的是本仓
当前 HEAD 的生产构建、数据库在线，先修了脚本自身的一个真缺陷：

- **缺陷**：注册请求只带了 session/csrf **cookie**，没有带 `x-csrf-token` 头
  （`request(..., cookie)` 漏了第 5 个参数，旁边还留着 `void token;`），
  所以注册恒被 `csrfOk` 拒绝，输出只有 "register FAILED" 看不清原因。
  修法：把 `token` 传进注册与第二个账号的请求，并让失败时打印状态码与正文片段。
- 修复后读数（`--n 14`，一次性邮箱 `brute-*@example.test`）：

| 项 | 值 |
|---|---|
| 注册 | **200** |
| 第 1–10 次错误口令 | 每次 **401** `invalid_credentials` |
| **第 11 次** | **429**，`retry-after=900s` |
| 第 12–14 次 | 429（门之后不再放行） |
| 第二个邮箱（同 IP） | 注册 200、登录 **401**（不连坐；键是 IP+邮箱） |
| 延迟 | p50 88ms · max 92ms |

**结论**：门的时机（第 11 次）、退避头（900s）、口径（先于口令比对、按 IP+邮箱分桶）
三条全部实测成立。剩余未测仍是 Redis 后端下多副本限流的一致性（归 `verify:rate-limit`）。
