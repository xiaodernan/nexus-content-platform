# 压力测试 · web SSR 并发 burst（2026-11-22 · §STRESS-WEB）

> 指令第十一条：模拟海量用户、高并发、瞬间大数据量冲击，看会不会崩、能不能容纳。
> 本片是**第一份**可复跑的 web 侧证据；Java / Redis / 既有 sweep 的证据见文末。

## 测的是哪台机器（先说清，否则数字没有意义）

- 目标：`http://127.0.0.1:3100` 上**正在运行**的那个进程。
  实测它是 `D:\内容创作平台\apps\web` 的 `next start`（并行线的检出，非本仓检出）——
  本仓自己的 3100 起不来（端口被占），**没有**为了测试杀并行线的服务。
- 客户端：`scripts/stress-web-burst.mts`（keep-alive，steady maxSockets=64，burst 128）。
- 路线：`/` · `/guide` · `/bible` · `/about-nexus`（都不碰业务库）。
- 负载：每条路由先 3 次预热，再 120 并发；最后 `/` 240 并发瞬间撞车。
- 客户端超时 30s；超过即计 `rejected`（超时/ECONNRESET），**不计入错误状态码**。

## 读数（单机单次，§59：数字是事实不是承诺）

| 波次 | 应答 | HTTP 状态码 | p50 | p95 | max | rps |
|---|---|---|---|---|---|---|
| steady `/` | 120/120 | 200 ×120 | 26.4s | 34.4s | 35.0s | 3 |
| steady `/guide` | 119/120 | 200 ×119 | 25.5s | 48.9s | 49.5s | 2 |
| steady `/bible` | 3/120 | 200 ×3 | 25.7s | 28.9s | 28.9s | 0 |
| steady `/about-nexus` | 82/120 | 200 ×82 | 40.5s | 50.0s | 50.2s | 2 |
| burst `/`（240） | 236/240 | 200 ×236 | 51.4s | 78.1s | 79.4s | 3 |

**5xx：0。错状态码：0。** 所有拿到应答的请求都是 200。
未拿到应答的 160 个连接全部是**客户端 30s 超时**（少数 ECONNRESET），
即：这台机器在 120 并发 SSR 下**答得过来，但答得慢**——不是答错，也不是崩。

## 结论（诚实版）

1. **正确性没有塌**：全程 0 个 5xx、0 个错码，服务进程存活，压测后 `/` 仍可正常访问。
2. **容量确实到顶了**：本机空闲内存约 2.5GB（仓库自己的记录），同时跑着并行线 web、
   ai-service、Docker、Postgres、Redis；120 并发 SSR 要 25–50s 才答完，
   `/bible`（语料最重的路由）只有 3/120 在 30s 内答上。
3. **这是机器上限，不是产品崩溃**：把它读成"高并发下系统不可用"是错的，
   读成"高并发下系统很快"也是错的。真实读法是：**这台开发机供养不起 120 并发 SSR**，
   部署侧需要多副本 + 网关分流（仓库已有 `nexus-gateway` 与 `verify:loadbalance`）。
4. **下一步**（本片不做）：① 同一脚本打生产构建的**本仓**检出（需先腾出 3100）；
   ② 打不碰 SSR 的 API 路线（`/api/*`）看纯后端容量；③ 撞库场景（错误口令连打）
   走 `verify:auth` / rate-limit 既有证据，不新造。

### 一次真实的非确定性崩溃（如实记录，不掩盖）

同一构建的**冷进程**上，第一次跑 `--n 100` 时：
steady 四条路由各 100 请求全部 200 → 最后 burst `/` 200 并发**只答了 20 个**，
进程在 1.2s 内消失，退出码 `0xC0000409`（STATUS_STACK_BUFFER_OVERRUN / fail-fast），
其余 180 个连接 `ECONNRESET`。客户端与服务端日志**都没有 JS 堆栈**，Windows 无崩溃转储。

随后阶梯复现（同一构建、每档前重采样内存）：

- 40 / 80 / 120 并发：全部 200，内存 144→356MB，进程存活；
- 160 并发（每请求一个新访客 cookie）：50 个 200 后进程再次 `0xC0000409`；
- 之后同一进程负载**再未复现**：160 / 200 / 240 并发（含 240 个唯一访客）全部 200，
  内存峰值 500MB，进程存活；最终 `--n 100` 标准脚本 200/200 通过。

结论只写测到的：这是**非确定性 native fail-fast**，不是可稳定复现的容量墙；
RSS 峰值 500MB 远低于可用内存，提交内存也有 8.8GB 空闲，所以不能归因于简单 OOM。
未测到的：V8/native 栈损坏的具体模块（无 dump）。下一步若要钉死，需要在一台安静主机上
开 `--report-on-fatalerror` / WER LocalDumps 复跑；产品侧的缓解仍是多副本 + 网关分流
（`nexus-gateway` 与 `verify:loadbalance` 已存在），而不是让单进程硬扛全部首发流量。
