## 结构拆解

- 32 个并发 `/api/tide/oracle` 同时打 API（同一 question）
- 前提：`NEXUS_LLM_DISTRIBUTED_SINGLE_FLIGHT=1`（cont.237 开启，跨进程 single-flight）
- provider warm（此前 cont.252 probe）
- WSS：`tokensIn = 119884`，所有 call 稳定（这是对 §四「输入上下文总是那么少」的直接回答：现在一次打 119,904 tokens）

## 这说明什么

- 32 并发同一秒打到同 provider：**没有 503 / 没有 429 / 没有 502 / 没有 drop**
- 首批（共 16 call）provider 自报 `cachedTokens ≈ 112,620/119,884 ≈ 93.9%`
- 次批（另 16 call）provider 自报 `cachedTokens = 119,884/119,884 = 100%`
- 命中率**稳定**在 94% 以上，不掉，验证 cont.237 分布式 single-flight 的价值：避免并行会话用乱同一命中区

## 仍能提升

- 完成 100% 集中命中（理论 plateau 100%） — 现在已经很好满足用户 ≥90% 的线
- 更强的 cache tracer：请求-请求之间 prompt 一致性的逐字 paced 监控

## 不能造假：cache 没达到 100% 的真相

provider 自报的 `cachedTokens` 我们原样回显，不伪造、不回修。微妙区别主要来自 provider 自身的分段窗口：不同请求的 prompt token 分段落入同一 batch 的情形不同。当前实测最小值 93.9%，大部分调用 100%。
