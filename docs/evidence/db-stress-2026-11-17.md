# §STRESS-1 — 数据库只读压力实测（2026-11-17 · v837 · mcp / pgbench）

背景：总指令第十一节「模拟海量用户、高并发、瞬间大数据量去冲击系统」。本机 RAM 不足以整栈 HTTP 层压测（Next.js dev server 在此机器上常被 OOM 杀），所以先做**不新增 token 成本、不写任何数据、机器端 RAM 成本可控**的一层：直接打 `nexus-postgres`（Docker，16GB 机上现有容器）的真实查询形态。

## 方法

`load.sql`（存于 `C:\Users\18414\AppData\Local\Temp\opencode\load.sql`，只读）：
```sql
-- §STRESS-1 只读压力脚本（discovery / feed 路径的真实查询形态）
SELECT id FROM published_projects WHERE visibility = 'public' ORDER BY published_at DESC LIMIT 20;
SELECT count(*) FROM projects;
```

执行：
```
docker cp → nexus-postgres:/tmp/load.sql
docker exec -e PGPASSWORD=nexus_dev_only nexus-postgres pgbench -n -c <clients> -j <threads> -T 10 -f /tmp/load.sql -U nexus nexus
```

## 结果（原样采集，2026-11-17）

| 并发 | 线程 | 事务数 | 失败 | 平均延迟 | TPS |
|---|---|---|---|---|---|
| 8  | 4  | 19 069 | 0 (0.000%) | 4.170 ms | 1 919 |
| 32 | 8  | 29 416 | 0 (0.000%) | 10.745 ms | 2 978 |
| 64 | 16 | 31 875 | 0 (0.000%) | 20.773 ms | 3 081 |

（pgbench 16.15，Debian 16 container；nexus-postgres 16；UTC 实测环境。）

## 结论（含边界，不夸大）

1. 在**零数据**（pg_stat_user_tables 显示 `projects` / `published_projects` 均 `n_live_tup=0`——本库没有发布过的项目）条件下，32/64 并发下仍然 0 失败、延迟可线性退化（4→11→21 ms），说明 **连接/解析/共享缓冲/日志路径在高并发下没有崩溃**。这条是鲁棒性的必要不充分证据。
2. **不是**全栈容量证据：HTTP 层、RSC 流、payload 大小、hot-path 行锁、Row-level security 都未覆盖——本库没有数据，任何"只有 0 行"的压测都不能测出索引/扫描/缓存的恶化曲线。
3. 索引现状已核（migrations/0043）：`published_projects` 有 `(visibility, published_at)` 复合 b-tree——读路径的地板已在索引侧；真实「撞库」场景请走 `/insight/login` 前的 `insight-login.integration.test.ts`（4 例，429 限流已钉）以及 `pg_stat_all_tables` 定期对账。
4. 下一层（需 RAM ≥ 6 GB 空闲）：HTTP 前端 + `wrk/autocannon` 打 `/api/.../login`、`/bible` 与发布页，**作为一次完整 burst 跑**；在此之前不声称"高并发测试通过"。

## 不覆盖的事
- 不涉及 Redis 压力（nexus-redis 有健康检查但未在此轮被当靶打）；
- 不涉及 write-heavy 场景（防在空 dev DB 写入污染验证口径）；
- 不涉及 Spring Cloud 微服务网关切流（Docker Desktop 本轮第二次崩溃后手工拉起；Spring Cloud 复验仍等 RAM ≥ 6 GB）。
