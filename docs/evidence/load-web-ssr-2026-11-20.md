  - 新实例 PID 39104（NODE_OPTIONS=--max-old-space-size=1024，端口 3475）仅为本次压测存活；
    **压测结束后已 kill**，不留 permanents。

## 方法
- 协议同 2026-11-17 §LOAD：warm（每路 3 次串行）→ steady（/bible ×40 · 16 sockets · keep-alive）
  → burst（/bible ×30 · 64 sockets · 瞬发）→ /bible/quiz ×20（16 sockets）。
- 全部 GET，全无 provider 调用、全无写；hot route = /bible 与 /bible/quiz（已编译）。
- 判据：status 200 数、时延分布（p50/p95/max）、freeMB 读数。

## 读法（不粉饰）
1. **这不是生产能力数字**：开发路环境 + 磁盘 / 内存吃紧。信号是：
   16–64 并发 GET /bible（hot）即可让 **4.1GB RAM 整机的 web 路径坍塌**——
   60s 内只完成 5/40。生产 CDN + `next start` + 预构建 chunk **可能**不同，
   但本次证据不能证明。
2. **rail 的边界**：burst 端全部 30/30 是 **20s 客户端超时**（无 HTTP 响应），
   不是 5xx；dev compile 排队长 + GC 抖动 + 内存压力是主因，不是路由逻辑错误。
   零 5xx、零数据库压力（该 route read-only · no-DB）。
3. **机器是第一约束**：当空闲内存掉到 ~850 MB，dev 路不可用作容量门；换成
   prod 构建+prod 启动+预存热页并在 RAM ≥2GB 时重测，才能换成真的 HTTP 数字。
4. **关系数据库压测保持绿**（§STRESS-1 复测 TPS 5,694 / 9,108 · 0 失败），
   网关共享限流 Lua 6/6 直连真 Redis（见 stress-2026-11-19.md §B）；
   两条都不依赖 Node dev 路径，仍是当月最新的可复现一手事实。
