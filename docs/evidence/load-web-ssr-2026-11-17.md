# web 侧高并发实测 2026-11-17（v777 之后；dev 路径探针 —— 不是生产定容）

> 用户长期点名项："做一些压力测试 模拟大量用户或者高并发用户 来测试高并发高可用容灾能力"。
> 本篇记录两次实测：**第一次（失败现场，如实保留）**与**第二次（分档 sweep）**。
> **不讨论做成 SLA**（§159）——这是本机一次实测，dev-mode 窗口内的读数。

## 机器现况

- free ≈ 1.1–1.5 GB（WSL2 VM ≈ 4.3–5 GB；`vmmemWSL` 是大头）。
- next dev -p 3401，apps/web（Turbopack dev，含 double-render 与未去除开发开销）。
- 本次没有做生产构建（`next build` 在这一档内存里出不了干净 build；工作量也超出压力测试片）。

## 读法

1. **先修 `/about-nexus` 才有的"高可用错觉"**：第一次的 0/170 彻底解决后，这台页面在同一路径、同一口径下才是真 200；它帮我们抓到了一个**一直躺在 HEAD 里的 live 500**（§159：单页面错误率≠容器崩）。
2. **dev 路径下 P50 ≈ 7–22 秒**是 Turbopack dev 双渲染 + 这台机器的 CPU/内存压力的叠加（WSL2 VM 里 ~4.3GB vmmemWSL，free ≈ 1.1–1.5GB）：同一批字节在 tier-12/24/48 的 p50 ≈ 19–22s，差异在噪声里，而非并发本身。
3. **连接裁掉只出现在 48**（4/100 重置），tier-6/12/24 零丢失——单 Next dev server 的队列上限大致在此附近（§159：这是**这台机器 + dev**的读数，不是"系统并发极限"）。
4. **DB-free 路由选取**：`/bible`、`/guide`、`/about-nexus`（v779 后）全部不连业务库；`/discover`、`/n/*`、`/search` 没有纳入（本机 Postgres 自动停摆风险 + 生产口径下才成立）。
5. **生产路径仍欠**：没有做 `next build` 的高并发测量（这台机器给不了干净构建窗口）；真生产窗口应在"构建通过 + free ≥ 3 GB + idle DB"再跑一次，记录 p50/p95/queue-shed 才能对照本篇。

## 固定在三个核对里

1. 错误率不推断：96/100 还是 100/100，都写直方图；不写"大概稳定"。
2. 不做 SLA：本篇是**容量感知与回归基线**，不是 SLO（§159）。
3. 不做外推：dev → prod 的换算必须另量一次，不能拿本篇数。
