## 经验（本轮最值钱的部分）

1. **vitest 里 spawn 外部进程会被沙箱挡住**（`spawnSync python EBUSY`，`unzip` 同样），
   但 **Bash 工具里可以**。所以"用真解压器验"这类主证据的正确做法是：
   **在 Bash 侧跑一次、把结果写进 commit message 与 ROADMAP**，
   而不是把一条依赖外部解释器的用例留在门禁里——那会让门禁在别人机器上以与环境有关的
   原因变红。用例里守的是**按格式从头解析的读端**（不复用写端的任何函数），
   它能抓住"偏移量记错一处"这类两端不会同时犯的错。
2. **"一条写在原文里、但 ROADMAP 从没提过"的要求是最高价值的发现**。§144 就是这样：
   四件事一件没做，而且它**没进过任何一张清单**，所以没人知道它欠着。
   方法：拿原文的条款号去 grep 文档，grep 不到的条款要挨个核对代码。
3. **接手别的会话的在途工作时**：先读 ROADMAP 末尾的"交接点"（那里常写着
   "只 git add 自己改过的路径"这类并发约定），再用 `git commit -- <paths>` 做部分提交。
   本轮遇到的情况是**别人接着做我的切片**——这时把两条线合成一个 commit 比硬拆开更诚实。
4. **数据库约束会替你做决定**：写 ADR-0025 时最有价值的一步是去看
   `projects.ownerId` 的 `onDelete`——它是 `restrict`，所以"硬删用户"根本不是风格选择，
   是数据库自己会挡。**写判决书之前先读约束**，能省掉一整轮空谈。
5. **exhaustive 的 `Record<Kind, T>` 是加枚举时的导航器**：加 `'build'` 通知那一类时，
   typecheck 直接把两处必须补的地方点了出来（`NOTIFICATION_KINDS` 与 `KIND_LABEL`）。
