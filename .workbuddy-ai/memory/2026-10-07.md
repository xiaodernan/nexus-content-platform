## 找到的 bug（真、有证据）

`POST /api/marketplace/[id]/download` 与同一个仓库里"匿名可写"的参照实现
`/api/published/visit` 比，少了三样：

1. **没有 CSRF 校验**。而 `MarketplaceItemRow.tsx` 里同一个组件的 DELETE / PATCH
   **都带着 `csrfHeaders()`**，只有下载这一处漏了——**客户端与服务端两边一起漏，所以一直没红**。
   `middleware` 给每个访客（含游客）都签了 `nexus_csrf`，不存在"匿名就没有 token"这回事。
2. **没有限流**。`downloadCount` 是印在列表与详情上的**给人看的数字**，一个脚本能把它灌成任意大。
   今天这一格不参与排序（排序按 `createdAt`），所以现在只是"数字会变成假话"；
   但数字一旦假了，排序真接上那天就是直接可刷。
3. **错误形状不合规**：回的是 `{ error: 'Item not found...' }` 这种英文裸报文，
   与全站统一的 `{ error: { code, message } }` 不是一个形状。

**修法**（照 `/api/published/visit` 的三道边界）：服务端补 `csrfOk` → 403、
按 `IP + 条目` 限流 60 次/小时 → 429、报错走 `jsonError` 且用中文、
不存在与已下架统一 404（403 会泄露"这个 id 存在"）；客户端那处 fetch 补上 `csrfHeaders()`。

## 经验（补）

1. **`jsonError` 的形状**：`{ error: <码>, ...extra }`。人话在 `extra.message`。
   别想当然写成 `{ error: { code, message } }`——**断言错形状会让一条本该绿的用例红**，
   而那种红会让人去改被测代码。
2. **接手别人停下的工作时，"红"分三种**：lint 红（残留文件、未使用导入）、
   测试红（新枚举值没同步到镜像）、**调试脚手架没清**（console.log / 未使用变量 / 缩进跑飞）。
   三种都要清，但**第三种最容易漏**——它不红，只是脏。
3. **删别人的残留文件之前先移进 `.scratch/`**：本仓的 `.scratch/` 是双覆盖的指定临时区，
   移进去既修了 lint 又完全可逆。3.5 小时无动静 = 会话已停，但仍不值得直接删。
4. **加一个枚举值/步骤时，要同步的地方比想象的多**：能力镜像、步骤表、计划状态表、
   事件计数、进度刻度（分母变了，**每一格都要重算**）、通知标题里的 "N/N 步"。
   全量回归是唯一能把它们一次找齐的手段——单跑一个文件只会一条一条地红。
5. **"执行序"与"声明序"是两个东西**：断言按哪个序推，要看被测的那条链路跟的是哪个。
   进度刻度跟执行序，计划表跟声明序。混了会红得让人摸不着头脑。

## 经验

1. **"两边一起漏"是最难发现的一类**：客户端不带 CSRF token + 服务端不检查 CSRF，
   功能照样能用、测试照样绿，因为两边是自洽的。**发现它的方法不是跑测试，是横向对比**
   ——把同一类端点（都是"匿名可写"）摆在一起看，差异自己会跳出来。
   `/api/published/visit` 就是这个仓库里"匿名可写"的参照实现，它的注释里写着三道边界。
2. **同一组件内的一致性可以做探针**：`MarketplaceItemRow` 里 DELETE / PATCH 都用 `csrfHeaders()`，
   只有 POST 不用——**局部不一致比全局不一致更容易被看见**。
3. **`downloadCount` 这类"给人看的数字"要有明确的抗灌声明**：要么限流，要么在界面上写明限度。
   数字假了比没有数字更糟。

## 晚场：把 413 那一格量掉（`docs/TESTING.md` 第 12 条最后一项）

`[ ]/[~]` 里能自主推进的已经不多（Video Studio 与 Java 域服务两个 `[ ]` 都要外部条件）。
翻到 `docs/TESTING.md` 第 12 条：只剩 **413 没被真请求证过**，本页两处记过"没量"，
理由写的是"128MB 真字节会把 16GB 机器的空闲内存吃光"。

**量完之后，那个理由有一半是错的**：

```text
POST /api/projects/import（声明 2GB）→ 413
  响应：{"error":"too_large","reason":"整包 2048MB 超过导入上限 128MB"}
  正文写了 2147483648 字节，耗时 11502ms
```

1. **413 是真的**（状态码、错误码、理由里那句带上限的话都来自真路由）。
2. **"吃光内存"不成立**：2GB 是**流式排掉**的，11.5 秒跑完，空闲约 2.5GB 的机器没有 OOM。
   当初那条顾虑是按"先读进内存再判"的写法推的，而路由不是那样写的。
3. **"早拒就省下正文"也不成立**（这条是新知道的）：服务端**把 2GB 正文全读掉了**，
   响应在正文排完之后才到。`content-length` 那道关只说明**判定**早，不说明**字节没被收下**。
   省下的是"解析/落库"，不是"带宽与时间"。
