fix(spring-cloud): wire the topology + load-balance + auth + actuator smokes and Spring Cloud proof

The merged branch refused to let its topology gateway find the domain-service:
the gateway pointed at a config server the proof did not spawn, and the shared
config profile enabled discovery-registration by default, which made Java
services register with the lab registry. The smoke services now pass enabling
env vars and pick the config server configured locally.

- verify-topology.mts: domain-service, nexus-api, gateway all point at the
  spawned config server (NEXUS_CONFIG_SERVER_URL) rather than the private 18888
  IP convention, so a fresh rebuild registers and is selectable by lb://.
- verify-auth.mts / verify-loadbalance.mts: pass NEXUS_EUREKA_ENABLED=true to
  both domain service and gateway, so clients fetch the registry even when
  started standalone.
- java-gateway/application.yml: packaged Redis default 6379 -> project redis
  56379, so the smoke actually connects.
- nexus-config/src/main/resources/nexus-config/application.yml: the shared
  default denies discovery explicitly, so once NEXUS_CONFIG_ENABLED=true the
  clients of that lab config enable eureka client and register registration on
  the lab registry (which matches the verify:topology expectation).
- tsconfig.tools.json: add "jsx": "preserve" so SSR probes can import server
  components without tripping the TS6142 JSX setting.
- spring-cloud-proof.mjs: run each Java service on a dedicated fixed port that
  the parent picks, instead of 0 (port-0 left the registry with 0, and the
  load-balancer with a dead port); spawn SERVICE directories by the registry
  family the README tells it to use (nexus-gateway/nexus-registry/...) so the
  panorama and the Spring Cloud topology agree.

- npm run verify:actuator     PASS  5/5 service actuator truth pinned
- npm run verify:lb           PASS  two domains resolve through the LB
- npm run verify:auth         PASS  every auth door refused and honored
