## 第五个增量 SC-33 / ADR-0105（网关 88 → 90）
- 缺口：retry 有两条触发源——`setStatuses(503)`（GatewayEdgePolicyTest 已测）与 `setExceptions(IOException, TimeoutException)`（后端连接层直接断，**从没测过**，恰是最常见真实故障）。注释承诺「只重放 GET」，异常路径方法门没被 wire 验证 → 若失效则一次投稿变两次（数据级事故）。

- **源码订正（猜错即改）**：初判 PrematureCloseException 是 RuntimeException 匹配不上 IOException → 查 reactor-netty-http 源码发现 `PrematureCloseException extends IOException`（是活的）；再查 `RetryGatewayFilterFactory.RetryConfig`：status 谓词 `retryableMethod && retryableStatusCode`、exception 谓词命中后 `return retryableMethod`——**两条触发源都套 `setMethods(GET)` 门**，POST wire 恒 1 是必然。

- 经验：**当断言对象存在时序浮动时，钉稳定不变式（写不重放/重试上限/答复诚实），把浮动量记为已知边界，绝不 pin 一个会 flaky 的精确读数**；把重复采样本身编进断言来证明稳定性而非一次侥幸。

### SC-37 / ADR-0109：Bulkhead 从沉默默认变显式承诺
- **前提订正（反编译，不猜）**：`ReactiveResilience4JCircuitBreaker{,Factory}` 都持 `ReactiveResilience4jBulkheadProvider`，auto-config 默认注册；`run()` 字节码 = `decorateMono → CircuitBreakerOperator → Mono.timeout → onErrorResume(fallback)`，舱壁最内层。`create(id)→create(id,id)`，id=`setName(service)`，与 yml 实例名同源。默认 `DEFAULT_MAX_CONCURRENT_CALLS=25`。
- **生产**（零 Java 改动）：`application.yml` 两后端各声明 `bulkhead.instances.<svc>.max-concurrent-calls=${NEXUS_GATEWAY_BULKHEAD_MAX_CALLS:25}` + `max-wait-duration:0`；默认仍 25 行为不变，变的是「平台显式决定、env 可调」。exposure 加 `bulkheads`。
- **诚实边界**：resilience4j 2.2.0 `BulkheadEndpoint` 只给名字列表、`/actuator/bulkheads/{id}` **404**、无实时在途数——是「哪些 route 有边界」不是并发仪表，绝不包装成容量指标（写进测试断言 + ADR）。auth-on 独立 context 测 401/200/health 开放。
- **wire 判据 `GatewayBulkheadWiringTest`（3/3，连跑 3 次）**：`StubUpstream.holdNext(n)` 占住前 N handler + `awaitHeld()` 握手证明在途，再发第 N+1。钉：满时 503/`cause=BulkheadFullException`、拒绝**在 wire 之前**（后端只见 N 条）、breaker 全程 CLOSED（≠ `CallNotPermitted`，容量减载≠后端故障）、释放自愈。
- **三条硬约束（新约定）**：①并发占用必须 `startConcurrent()`（串行 HttpServer 会假读 wire，SC-34 同类）；②等待有界 `await(5s)` + `@AfterEach` 无条件 `release()`（SC-36 hang JVM 9 分钟教训）；③并发腿用**非阻塞 `WebClient`**，`WebTestClient.exchange()` 阻塞发不出两个在途——**一次性探针编译阶段就拦下这个选型错**。

### SC-38 / ADR-0110：响应中途断开不说谎 + context 缓存根治
- **第四种后端故障**（前三种：5xx / 连接拒绝 / 响应前断连）：`200+headers+部分 body` 后 `Content-Length` 未满足就 close。探针（`StubUpstream.truncateResponses()`，GET/POST 各 3 轮）实测：caller 得**连接级** `PrematureCloseException: ... DURING response`，**从不** 200+截断 body；wire 恒 1（GET 不重试：已拿 200 头进 body 阶段才断，两 retry 触发源都不覆盖）；健康基线 200/42B 不污染。
- **`GatewayTruncatedResponseWiringTest`（3/3，连跑 2 次）**，**不改生产**：①不返回成功响应、失败带真实 PrematureClose cause；②GET/POST wire 恒 1；③健康仍真 200。诚实边界：caller 见连接异常而非干净 503，因 200 头已提交（`already committed`，ADR-0101）；要 503 需响应提交前全量缓冲 body 的更大改动，另立片，**不假报已做到**。不 pin 耗时与包装异常确切类型。

## §SC-44：新作品即时进发现页——独立 `globalEpoch` 键段（ADR-0116，本地 commit 待做）

### 最关键纠错（探查阶段就推翻了初始直觉）
- 想"bump `globalGen` 让所有键拼不出来"是**错的**：`globalGen` 是"给**新 viewer** 分配 generation 的单调水位线"，匿名 generation 恒 0、已缓存 viewer 直接读缓存值——**两者都绕过 globalGen**，++它一个现有键都失效不了；清 `viewerGen` 表也一样（匿名不在表里）。
- 正解：独立正交键段 `discover:v1|<globalEpoch>|<generation>|<JSON([viewerId,sort,limit])>`。`globalEpoch`（内容新鲜度：public 发布/下架/rejected +1，含匿名所有旧键一次作废）⊥ `generation`（隐私新鲜度：block/follow 只失效一人）。两者都**跨 reset/热重载保留**防旧键复活（与 globalGen 同陷阱）。
- **经验：给缓存加"全局失效"前，先确认现有水位线到底拼不拼进每个键、匿名与已缓存条目走不走它。** 名字像"global"的变量未必是全局版本号。

### 帧格式单向兼容（`v:1`/频道都不动）
- `InvalidationFrame` 加可选 `global?:true`，全局帧带它 + 空 `viewerIds`；不升 v2/换频道（会切断旧实例双向互收）、不塞全站 id（撞 `MAX_VIEWERS_PER_FRAME=128`）。
- `parseInvalidationFrame` 校验两帧**互斥**（全局必空、定向必非空+id 护栏、`global` 必须字面 true）。**单向兼容**：新实例收旧帧；旧实例解析新帧因空数组撞护栏 fail-safe 丢弃（不把空集误当要 bump 的人），混部靠 TTL 15s 收敛、升级后自动生效。
- 订阅回调加第二参 `global?:boolean`，旧 `(ids)=>...` 忽略多余实参、向后兼容（改动面安全）。`applied` 对全局帧记 1 次（不是 0 个 viewer，否则四账显示"收到却没做事"的谎）。

### 写路径精度 + 首跑两条真信号
- 三处精确挂钩（只在发现页收录状态真改变时清）：`publishProject` 成功尾部 `input.visibility==='public' || existing?.visibility==='public'`；`unpublishProject` 撤下前是 public；`resolveCase` rejected 且那条是 public。private/unlisted 与 approved 不改收录、不清（避无意义惊群）。
- **真信号①**：正交性判据红在"invalidate **不立即** bump globalGen、generation 是**懒分配**"（invalidate 只删条目，下次取键才 ++）——断言时机错，修正后反把真实实现钉更准。
- **真信号②（生产 bug）**：`unpublishProject` 最初用 `UPDATE ... RETURNING visibility` 判断旧值，真库 epoch 没 +1（7≠8）当场红。**Postgres `UPDATE ... RETURNING` 返回的是更新后的行**，撤 public 时读到已是 `private`、判断永远 false。改"先 select 旧 visibility 再 update"，诚实记下 select→update 窄竞态（unlisted→public→此刻下架的并发窗口可能漏清一次，最坏残留一个 TTL、URL 已即时 404、不丢数据；要绝对原子需 CTE 取 OLD，不值得为低频操作引入）。resolveCase 无此问题（set 的是 moderation、不改 visibility，returning 拿到原值）。
- **经验：Postgres/Drizzle 里要拿"更新前"的列值，`UPDATE ... RETURNING` 拿不到；要么先 select，要么 CTE+OLD。写判据用真库能当场戳穿这类"看代码以为对"的 bug。**

### 判据与验证
- 四层：内核 `discover-cache.test.ts`+3（匿名+2viewer×4sort 预热→全局失效→`calls 9→18` 每键重载含匿名、正交性、epoch 跨 reset 不归零）；帧 `invalidation-bus.test.ts`+4（全局帧解析/互斥护栏/旧实例 fail-safe/两种 bus 收发/applied 记 1）；多实例 `discover-cache.multi-instance.test.ts`+4（A 失效→B epoch bump→匿名与登录键都变都重查、定向不误伤、fail-open、退订）；真库端到端 `discover-cache.integration.test.ts`+3（public 发布→所有 viewer 立刻看到且 author 屏蔽名单仍不串味；下架→立刻消失；rejected→立刻消失；各验 epoch+1 + loads 增长）。

## §SC-45：发布冷启动「惊群」先观测不设闸（ADR-0117 / ROADMAP §SC 第四十五片）

### 反向判断：拒绝写通用并发闸门
- ADR-0116 为即时可见加 `globalEpoch` 时留的诚实边界："全局失效≈冷启动，singleflight 只合并同键不跨键、打库量随活跃 (viewer,sort,limit) 组合上升"。本轮正面回答"要不要写跨键并发闸门"，结论**不写**：
  - **上界是个位数**：`limit` 两入口都不传恒 24（键退化成 `(viewer,sort)`）；RSC 一次导航只请求一个 sort（不是四个）；匿名键 ≤4（generation 恒 0）；登录键受 `maxEntries=2048`/`maxViewers=512` + 活跃人数封顶。
  - **已有三道天然舱壁**：singleflight 同键合并 / **DB 连接池 `postgres(url,{max:NEXUS_DB_POOL??5})` 是物理硬上界**（超出 SQL 在池里排队、压不穿库）/ 网关 `SemaphoreBulkhead`。物理层已封顶，再加应用层 semaphore 重复。
  - **通用闸门 5 类净损失**：①permit 泄漏（loader 抛错/中断/热重载忘 release）；②排队饿死（permit 数无先验）；③`inFlight` 读数失真（SC-43 已接面板的诚实读数被污染）；④延迟稀释 SC-44"发布后立刻看到"；⑤**不减总 SQL**（只摊平并发、对连接池收益≈0）。无实测尖峰证据→为不存在的问题引入新失败模式是负收益。
- **经验：面对"会不会有惊群"的直觉，先查真实调用面上界 + 盘点已有舱壁 + 列清新方案的新失败模式，再决定动手。很多"该加个限流"的冲动经不起这三问。**

### 有界失效波采集（只记不拦）
- 每次 `globalEpoch` 跳变记一波：`loadsDelta`=`cache.stats().loads` 差值（精确打库数）/ `peakInFlight`=读后瞬时 inFlight 采样最大（**非锁存精确峰值**，ADR/面板都如实标）/ `firstFillMs`=失效到首击延迟、无人读为 **`null` 不是 0** / `settled`；进 `DiscoverCacheStats.waves`/`.waveConfig` → route → 面板。零新 DB 查询、零行为变化。
- **最深陷阱（专设判据钉死）**：`BoundedCache.getOrLoad` 是 async，但**同步段就完成 `inflight.set` 与 `loads+=1`**，`fromLoad` 在 `await load` 才暂停。若等 `await` 返回才采 `inFlight`，`fromLoad finally` 已清掉 → `peakInFlight` **恒 0**、把惊群谎报成"没有"。正解：`loadFromStore` 里 `getOrLoad(...)` 调用**后立刻**采一次（抓"我+其它并发重填"的瞬时在途峰值），`await` 收尾（含失败）再采一次定稿。判据"两键卡 gate → `peakInFlight≥2`"：采样点挪到 await 之后就红。
- **经验：采样/可观测代码尤其要验"采样点在哪个时序"——异步函数同步段与 await 段之间状态会变，采错位置得到的是恒 0/恒满的假读数，比没有读数更危险。**

### 主业隔离 + 有界 + 多实例
- 内核 `bumpEpochAndOpenWave(s, now)`：先 `globalEpoch+=1`（主业、fail-open 最后一道）再开波（`try/catch` 兜）。**本机写路径 `invalidateAllInStore` 与两处远端全局帧订阅回调（attachBus + isolated factory）共用这一内核**——多实例收到发布帧那台也开自己的波，否则面板只有发布那台尖峰可见、又一处 `null≠0` 式谎（我曾试图只改一处，replace_all 两处相同代码行一次改到位）。
- `loadFromStore` 两次采样都 `try/catch`：观测抛错绝不破坏缓存失效、绝不吞 loader 异常（判据"loader 失败不崩、异常不吞"专钉）。
- `waves` 进容量 12 环形缓冲超了丢最旧；**波不跨 reset**（旧进程波带旧 epoch 撞值误导），与 `globalEpoch` **必须**跨 reset 保留**相反**——判据把两条钉在同一条里；惰性定格靠 `stats()` 与下一读驱动、**无定时器**。
- isolated 测试工厂同步补齐：`config.waveWindowMs/waveCapacity`、Store 的 `now/activeWave/settledWaves`；stats 组装抽成共用 `statsFromStore(s)`（全局门面与 isolated 共用，杜绝两处漂移）。

## §SC-46：上游失败 stale 兜底先重算键（ADR-0118 / ROADMAP §SC 第四十六片）

### 缺口：声明很久却没在这条链兑现的能力
- `BoundedCache.peek()` 注释早声明"供上游失败时 stale 兜底"，`gateway/client.ts:236` 已用成生产范式（失败→端旧值标 stale→无值 unavailable 绝不画 0），唯独发现页热读链（`discoverCached→loadDiscoverCached→discover`）没接——`GET /api/discover` 与 `/discover` 页无 try/catch，`discover()` 一抖整页 500。而 `getOrLoad` 遇 TTL 过期会重载、失败后旧条目**仍留在表里**——stale 所需旧值一直都在，只是没人 peek。

### 最深的一条：SC-41「不删缓存条目」的隐私债，只在降级路径暴露
- SC-41 纪律：`invalidateDiscoverFor` **只删 viewerGen 表条目、不删 cache 表条目**（旧键带旧 generation、单调水位线保证永不被拼出，正常读路径成立）。
- **降级打破前提**：`keyRequested` 是 loader 开始前锁定的字符串；若**打库期间**发生 block（generation 条目被删）或 public 发布（epoch+1），缓存表里 `keyRequested` 的旧条目**还在**，`peek(keyRequested)` 会成功拿到——那份可能是**拉黑前的视图 / 下架内容还在的那份**，直接端=隐私/收录回退。
- **根治：端旧值前重算键比对**。`serveStaleOrThrow` 三条件同时成立才端：①`keyFor(s,input)===keyRequested`（综合 epoch+generation，任一变就不同）；②`peek` 非 null；③`old.ageMs<=staleMaxMs`。期间 block 本 viewer / 发布→键变→**绝不端**；block 别人→键不变→可端（不误伤）；无失效→可端。否则 `throw cause`，上游原始异常一字不改冒泡，不吞错、不造空 DiscoverResult。
- **经验（可推广到任何 stale-while-error）**：「缓存里有旧值」与「旧值能端给这个人/此刻」是两件事。若缓存 key 编码了隐私/世代维度、而失效只删索引不删条目，则 `peek(旧key)` 是隐私陷阱——**降级路径必须重算当前 key 校验归属**，只做 peek 不校验必踩坑。判据用"loader 内部先 invalidate 再抛错"精确模拟"打库那一刻正好有人拉黑/发布"。

### 有界 / 不嵌套 / 透明可观测
- `peek` 的 expired 条目 `ageMs` **无上界**（键长期没人读会过期滞留到 LRU 淘汰）→ config 加 `staleMaxMs`（默认 `ttlMs*2`、`NEXUS_DISCOVER_STALE_MAX_MS` 可覆盖），超界宁可报错。
- 降级只做**同步 peek**、不重入 `getOrLoad`——否则重演 SC-41 真库判据曾踩的同键 nested singleflight 自等待死锁（90s 超时）。判据"N 个同键并发失败各自 peek、`staleServed` 精确=N、不死锁"钉死。
- **不污染领域类型**：返回仍是纯 `DiscoverResult`、不新增 stale 字段、不改 `route/page`、不改共享 `BoundedCache`（发现页本无"此刻"承诺，读用户察觉不到降级）。**但运维必须看得见**：`DiscoverCacheStats.staleServed`（进程内累计、不跨 reset）经既有 `describeDiscoverCache→route→面板` 端出；面板加"上游故障降级"节 + `staleNote` 讲四边界（`0` 只表示还没抖过、**不是**降级没开，开关是 `staleMaxMs`，同 `null≠0` 家族）；`isKnownReadout` 纳入 `staleServed`/`config.staleMaxMs` 防画 `undefined`/`NaN s`。零新增 token。
- isolated factory 同步：`staleMaxMs` config + `staleServed:0` 初始化。

### 判据与验证
- 内核 `discover-cache.test.ts` +11：正向降级（`staleServed=1`、`loads`+1）/无旧值抛错 size=0/超界报错/**隐私红线**（loader 内 block 本 viewer→不端+抛错+gen 增大+恢复后不复活拉黑前视图）/**收录红线**（loader 内发布→不端+新 epoch 生成 gen-2 非 gen-1）/**隔离**（block 别人→仍可端）/并发 N=4 不死锁计数精确/健康路径零影响异常不吞/字段形状不变/账不跨 reset。
- 展示判据 `discover-view.test.ts` +5（形状门正反 + 旁注 0 次不说"没开" + 四边界 + 秒数跟入参）；路由层 `admin-discover-cache.integration.test.ts` +1（真实降级后端到端可见、读数 `stats.loads` 不变即不打库）。SC-46 相关 7 文件（含横向门）**141 passed**；`style-tokens` **24/24**；typecheck **EXIT=0**；SC-45 判据零回归。**全仓 vitest 404 files passed | 1 skipped（405 total）/ 5828 tests passed | 1 skipped（5829 total）、EXIT=0**（对比 SC-45 基线 404/5812+1 skipped，净增 16；540.60s）。
- **首跑真信号（判据自检）**：展示判据首版红在**断言与文案字面不一致**——判据凭记忆写 `toContain('只读用户看到的是正常卡片')`，文案是"读用户看到的是正常卡片"（措辞也别扭）。非实现 bug；借机把文案改自然（"普通访客照常看到卡片、察觉不到这次降级，这笔账只记在运维面板里"）、判据对齐。**教训：判据断言必须来自真实文案，不能凭记忆编一句"应该会说的话"**，否则要么误红、要么文案真出疏漏时反而不红。
- **仍欠**：共享权威 gen/epoch 存储、实例粒度 breaker/bulkhead 聚合、连接层黑洞看门狗（SC-36）、CI topology job 经真实 push、3 条既存 .mjs TS8016、SC-45 减载预案待实测。未改 `discover` 函数体/DB/索引/依赖/两个入口/领域类型。未 push。详见 ADR-0118 / ROADMAP §SC 第四十六片。

## §SC-47 探查起点（本轮只探查、未实现；先把失败模式钉死防重踩）

- **盲区**：SC-46 的 stale 兜底只在 loader `reject` 时触发。上游**永不回答**（慢查询 / 连接池排队 / 锁等待）时 `discover()` 既不 resolve 也不 reject，catch 永远不进——stale 旧值在表里却端不出来，首屏焊死。
- **读码确证的事实**：`server/db/client.ts` 只设 `postgres(URL,{max:NEXUS_DB_POOL??5})`，**无 connect_timeout / idle_timeout / statement_timeout / query deadline**；全仓 `AbortSignal.timeout` 只用在 `fetch` HTTP 出站，DB 查询链零 deadline。`discover()` 主查询含 3 个 `SELECT count(*)` 子查询 + 三表 join，慢库有长尾风险。`max=5` 是 SC-45 依赖的物理 bulkhead，但只让超出者**在池里排队**、不设等待上界。
- **关键失败模式（别直接 `Promise.race` 软 deadline）**：`BoundedCache.getOrLoad` 的 singleflight 把 hung loader promise 存进 `inflight`、只在 `fromLoad` 的 `finally` 清。若 `loadFromStore` 外层 `Promise.race([getOrLoad, timeout])`：① race 超时返回 stale 后**底层 hung promise 仍挂在 inflight**，后续同键请求 await 它一起 hang（超时形同虚设）；② 每个超时请求各起 race，底层 hung 查询不断堆积、占满 5 连接，把单键慢变成**全站发现页雪崩**。在 race 层加超时更糟。
- **本轮决定：不仓促加 DB 超时**（同 SC-45"无实测尖峰不加并发闸门"的克制）。下一步先做**loader 耗时观测**（复用 SC-45 受控时钟 + 有界环形缓冲，只记不拦：`maxLoadMs`/`slowLoads` 进 stats+面板），用真实数字回答"发现页加载到底有没有秒级长尾"——最慢 <100ms 则 deadline 是伪需求；若确有长尾，正确做法是给 `BoundedCache` 加可放弃 inflight 的 `abandon(key)` 原语、或用 Postgres `statement_timeout`（波及全站、高危、须单独评估），**都不能在 race 层做**。
- **经验（可推广）**：给带 singleflight 的异步层加"软超时"前，必须先想清"超时后底层 promise 与 in-flight 索引的归属"——`Promise.race` 不取消底层，若底层仍占着共享索引/连接池，超时不但没救、还会堆积放大成雪崩。观测优先，先量再治。

## §SC-47 交付（ADR-0119 / ROADMAP §SC 第四十七片）

- **接住 SC-47 探查结论**：先量再治，本片**只做 loader 墙钟观测、不设任何 deadline**。零新 DB 查询 / 零行为变化 / 不碰共享 `BoundedCache` 与 `db/client.ts` / 不改 `discover` 与两入口 / 不改 `DiscoverResult`。
- **生产**：`loadFromStore` 把注入 loader 包一层 `withLoadTiming(s, epoch, loader)` 再交 `getOrLoad`，量真实打库墙钟；stats 加 `maxLoadMs`/`slowLoads`/`loadsTimed`/`recentLoads{epoch,durationMs,ok,atMs}`，进程内只增不减、**不跨 reset**；`slowLoadMs` 阈值（默认 1000ms / env `NEXUS_DISCOVER_SLOW_LOAD_MS`）只是分类旋钮、超过只 ++ 不 abort；`recentLoads` 进容量 12（`NEXUS_DISCOVER_LOAD_SAMPLE_CAPACITY`）环形缓冲有界、聚合不丢。面板加"加载耗时观测·只记不设闸"节 + 三条纯判据 + 形状门；零新增颜色 token。
- **本片最值钱的一条（差点做错）**：**必须包 loader，不能在 `loadFromStore` 外层用 `s.now()` 掐表**。`getOrLoad` 的 singleflight 只对 leader 真调 loader、跟随者 await 同一个 inflight promise 根本不进包装函数、缓存命中更不调——包 loader 天然只记真实打库那一次。挪到外层，N 个同键并发会把一次打库记成 N 次、把"等 leader 的墙钟"误算成查询耗时，**用观测亲手造一份"并发越高越慢"的假长尾**，正是 ADR-0117 那类"读数失真"诚信事故的另一副面孔。判据"N=5 并发只记 1 次且不含等待"专钉。**经验：给 singleflight 层加观测，计数边界要挂在"真正干活的那次调用"上（包 loader），不是挂在"每个请求"上（外层掐表）——否则观测本身制造它本该度量的假象。**

## §SC-49 交付（ADR-0121 / ROADMAP §SC 第四十九片）

- **主题**：`BoundedCache.clear()` × singleflight 在途回写泄漏，落数据结构与算法 / 缓存 / 操作系统竞态。**最要紧的一句：范围诚实交代**——唯一生产入口 `clearCache()` 全仓**零调用点**，这是**底座 latent 债、不是正在发生的事故**，绝不包装成"修了生产事故"；但 `BoundedCache` 是复用底座，`clear` 声明与实现分叉就该钉死（发现页 test reset 走重建实例、不受此 bug 也不受本修复影响）。
- **bug 机制**：leader `getOrLoad` 在 `fromLoad` 里 `await load` 挂起 → `clear()` 清 `map`/`inflight`/计数 → loader resolve 后 `fromLoad` 继续 `this.set(k,value)` 把值写回刚清空的 map → `size=1 / loads=0` 自相矛盾假账（follower 各再 set 一次）。
- **修复（generation token）**：单片程单调 `generation`、`clear()`+1、`getOrLoad` 同步段捕 gen（leader/follower 都捕）、`fromLoad` 写 map 前比对 `genAtStart!==generation` → **值照常交回等这一发的调用者（数据是真的、不能凭空变 undefined 造读失败）但不落库不计数**。**最关键的一处（别写错）**：`finally` 的 `inflight.get(k)===load` **刻意不加 gen 判断**——被 clear 时 `inflight` 已清空、`get(k)` 要么 undefined 要么是 clear 后同键**新一发的 promise（≠旧 load）**，两种情形都不误删新一发；若画蛇添足在 finally 加 gen 判断，反而可能把新一发删掉。判据⑤专钉。**经验：修并发竞态时，先穷举"旧操作的清理逻辑"会不会误伤"清空后新建的同键操作"——这是最容易修出二次 bug 的地方。**
